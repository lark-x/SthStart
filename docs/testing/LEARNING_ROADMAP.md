# SthStart 测试学习路线

更新时间：2026-10-13

## 学习目标与方式

使用 Python 在 VS Code 中为 SthStart 设计、编写、运行和维护测试。项目业务代码仍是 TypeScript；测试先用 pytest 与 httpx，浏览器阶段使用 Playwright Python，MCP 阶段选择适配现有服务启动方式的 Python MCP 客户端。练习以隔离的测试服务、临时数据库和独立项目为基础，不向日常创作数据写入测试内容。

采用模块式练习：每个模块一次给出完整范围和验收项，学习者自己完成代码，助手负责核对、运行、讲解失败并维护进度。通过测试不自动代表掌握；还要能解释测试保护的行为，并处理一个变化后的场景。

当前实践的完整任务、接口数据流、环境准备、运行入口和验收标准见 [Story 垂直路径测试学习指南](STORY_VERTICAL_TESTING_GUIDE.md)。下方长线阶段保留为知识范围，首期任务以该指南中的小型代表流程为准。

## 长线阶段

### 阶段一：Python 与后端 API 回归测试

目标：掌握 HTTP 状态码、JSON 契约、权限、输入边界、状态变化、版本冲突、数据隔离与提案审阅。学习采用代表性闭环，不以覆盖全部 Story API 为目标；当前集中练习先完成提案状态与版本冲突，随后转入 Story 模块的浏览器和 MCP 纵向实践。

完成标志：测试可独立运行且顺序无关；同时验证响应和持久状态；能解释 400、401、404、409 的区别；新增案例不依赖其他测试留下的数据。

### 阶段二：pytest 测试结构与稳定性

学习 fixture 的作用域、依赖和清理；把重复的项目/文档准备步骤整理为可读的 fixture 或工厂；使用参数化覆盖边界；为慢测、浏览器测和真实 AI 评估使用 marker；验证单测、整套测试、不同顺序运行都不会互相污染。练习检查子进程退出、临时数据隔离和失败诊断信息。

### 阶段三：前端浏览器测试（Python Playwright）

从用户可见行为验证页面：打开项目、编辑章节、保存成功、刷新后内容仍在；验证空标题提示、加载失败和保存冲突提示；贯通作者查看并接受或拒绝提案。使用 role/label 等稳定定位方式和自动等待，不用固定时长 sleep；失败时保存 Playwright Trace、截图和报告。数据与测试后端隔离。

### 阶段四：MCP 确定性测试

通过 Python MCP 客户端验证真实协议的工具发现与调用，不把 REST 桥接接口测试误称为 MCP 协议测试。覆盖工具名称/参数 schema、正常及异常响应、分页与正文截断、令牌无效/撤销、跨项目拒绝、浏览器来源拒绝、只提交提案而不直接改正式正文。先以固定输入和隔离服务验证程序行为，不调用真实模型。

### 阶段五：Skill 与真实模型评估

为“剧情连贯性检查”和“小说转剧本流”建立固定场景集，包含明确冲突、人物知识疑点、分页资料、正常改编、纯动作与心理描写、授权但版本已变化等案例。对照相同模型和资料运行“加载 Skill / 不加载 Skill”；记录模型标识、Skill 内容哈希、输入、输出、工具轨迹、耗时及可获得的用量。自动断言工具参数、提案状态、正式数据变化和编译结果；人工按证据准确性、冲突判断、人物知识及改编忠实度评分。探索运行可单次，正式比较每个场景重复三次；真实调用单独手动运行，不纳入普通 CI，不自动换模型或重试。

### 阶段六：报告与持续集成

把确定性 Python API、浏览器和 MCP 测试接入自动化；将真实模型评估留作手动入口。报告区分通过、失败、跳过和环境不可用；浏览器保留 trace；测试失败能定位到断言、请求和测试数据。后续再扩展性能、安全、迁移、视觉回归与其他 MCP。

## 当前集中练习：PY02-BATCH-01 Story 提案 API 闭环

范围只保留最能学习状态变化的提案流程，不要求完成 Story API 的所有边界测试。继续使用 Python、pytest、httpx、现有 `client`/`admin_headers` 和隔离服务；不调用 AI。项目、章节、会话、提案 ID 都从本次响应取得。项目默认包含 outline，章节必须按创建响应的 ID 或 `kind == "chapter"` 查找。

将 `tests/python/story/test_story_proposals.py` 中的流程逐步拆成独立场景：

1. **待审与拒绝**：提案创建后为 `pending`，正式章节标题、正文、revision 不变；拒绝后提案为 `rejected`，正式章节仍不变。
2. **接受**：用当前章节版本创建一份新的提案并接受；提案为 `accepted`，正式标题和正文更新，revision 增加 1。
3. **已处理提案再次接受**：拒绝一份提案后尝试接受同一提案；预期 409、错误码 `story_proposal_decided`，状态仍为 `rejected`，正式章节不变。
4. **过期提案**：基于版本 N 创建提案；作者先用 `expectedRevision=N` 手动保存，版本变为 N+1；再接受旧提案。预期 409、错误码 `story_proposal_stale`，提案仍为 `pending`，作者保存的内容和版本不变。

接口数据依赖：创建章节响应提供 `chapter.id` 与 `chapter.revision`；`POST .../sessions` 的响应提供 `session.id`；创建提案时传入 `sessionId`、`kind`、`targetId`、`baseRevision`、提案标题/正文和 reason；提案响应提供 `proposal.id`。成功的决定接口返回 200；错误响应从 `response.json()["error"]` 检查业务错误码。创建 session 和管理员 proposal 不会调用模型。

当前证据：先前组合提案流程曾单独运行 1 项通过；2026-10-13 核对的新目录版本已补 rejected 和 story_proposal_decided 断言，并通过 collect-only 收集到 1 项。本次未执行最新业务测试；下一步补接受状态、失败后数据状态和过期提案场景，并拆分独立用例。通过不等于掌握，仍需能解释每个 ID 的来源、提案依据版本及失败后数据状态。

## 下一阶段：PY03 Story 模块小型纵向实践

选择 Story 剧情工作室，因为仓库已有跨浏览器、服务 API 与 Story MCP 的代表流程。`tests/e2e/learning-story.spec.ts` 可作为行为参考：它准备项目和章节，在浏览器保存正文，通过 MCP 读取并提交提案，再由作者接受或拒绝。该参考用例是 TypeScript；学习者将按阶段用 Python 重现少量代表行为，不需要复制整份测试或覆盖所有 Story 功能。

1. **Python Playwright 浏览器测试**：用 API 准备独立项目/章节；打开故事页面，编辑正文并保存；等待用户可见的保存完成信号；刷新页面，并通过页面或 API 读回确认正文持久化。再选择一个代表性的接受或拒绝提案交互。
2. **Python MCP 协议测试**：在隔离项目上启动 Story MCP 客户端，发现并调用一个读取工具；随后提交一份提案，验证工具返回、提案状态为 pending、正式正文仍不变。由管理员决定提案后，再验证正式数据变化。
3. **串联与排障练习**：把一个浏览器保存结果交给 MCP 读取，再由作者审阅提案；至少制造一次确定性失败，利用状态码、响应、浏览器 Trace 或工具返回判断失败发生在哪一层。
4. **Skill 观察练习**：上述确定性链路稳定后，选择一个现有 Story Skill 与一个固定剧情场景，手动比较一次加载 Skill 前后的证据和输出；这是探索练习，不扩展为完整评测集，也不加入日常回归。

暂缓完整标题/正文参数矩阵、所有权限组合、跨项目枚举、修订恢复、视觉回归和其他业务模块。只有当纵向实践暴露具体风险时，再挑一两个用例补充。

## 完成后顺序

先完成 PY02 提案状态与 stale 冲突；再按 PY03 依次练 Python Playwright、Python MCP 和一条 Skill 观察场景。最后整理测试辅助函数与报告，并运行代表性回归。暂不追求全模块覆盖、全量 AI 评估或全面 CI 接入。
