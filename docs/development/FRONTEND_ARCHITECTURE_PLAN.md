## 1. 目标与范围

保留 React 和现有产品功能，通过职责拆分降低新增功能的影响范围，使页面、业务、状态、持久化和公共组件有清晰归属，并建立可持续的开发标准。

## 3. 实施原则与交付单位

1. 每个改动单元解决一个明确职责问题，列出改动路径、调用方、保留行为和验证范围。文件移动与行为优化分开提交或分开审查。
2. 先做依赖清理与公共能力整理，再做编辑器，最后收敛复杂制作、加载和样式。
3. 优先复用现有 `api-client`、Query、`DraftSaveQueue`、UI 和 URL 工具，不先造一套通用框架。
4. 旧导出可以用单向兼容入口保留；新代码使用新归属。移除适配前核对所有引用、测试和旧路由。
5. 不把大组件整体搬成大 Hook。按草稿、服务查询、动作、焦点和面板等独立职责拆分。
6. 每个阶段保留可恢复的代码基线；只回退该阶段自有改动，保留用户及其他工作的修改。
7. S0–S5 已按已授权范围连续实施；后续修复和 S6 验收继续在同一范围内推进，不要求每个小批次重新征求许可。代码落地不等于验收完成。

## 13. 已有命令与使用条件

下面命令于2026-11-10登记为实施检查入口，S6已按实际改动执行相关检查，结果见交付记录。保留命令供后续按影响范围选择，不表示每次修改都要重复全部检查。

```bash
# 对保存核心的定向测试；测试运行器使用临时数据目录
node scripts/testing/run.mjs --file app/lib/draft-save-queue.test.ts

# 架构边界静态检查；当前无例外文件时要求 0 violations / 0 stale exceptions
npm run check:architecture

# 架构检查脚本自身的规则测试
npm run test:architecture

# 机器可读结果，供阶段记录或前后对比
node scripts/architecture/check.mjs --json architecture-report.json

# 前端逻辑和门户桥接测试，不等于浏览器验收
npm run test:portal

# 类型检查会先构建 activity-playback，并检查各 workspace
npm run typecheck

# 共享请求/响应发生变化时才增加契约检查
npm run test:contracts

# 受影响浏览器文件；此命令先构建门户和服务
npm run test:e2e -- tests/e2e/pagination.spec.ts

# Story 学习流程需要专用隔离配置，默认 E2E 配置会忽略该文件
npm run test:e2e:learning

# 跨模块最终集成或实际 CI 所需
npm run ci:core
```

同一已验证构建可使用 `npx playwright test <文件>` 跑后续目标用例，不为每个文件重复完整构建。专用模拟服务测试使用对应配置。Playwright 配置负责独立测试服务、端口与临时数据，不复用生产服务；浏览器视觉检查仍需实际观察关键界面。

lint 优先选择改动文件；边界检查已由 S1 建立并接入 `ci:core`。检查通过后只有新改动、失败或未解决问题才重复。2026-11-10 的局部阶段报告记录为 562–574 files、1976–2034 local edges、0 violations、0 stale exceptions；S6 最终扫描为574文件/2035依赖，0违规和0过期例外；行为与性能证据另见交付记录。架构检查是静态依赖分析，不能替代类型、构建、浏览器或性能验收。

## 14. 风险、处理和恢复约束

| 风险 | 处理 | 恢复约束 |
| --- | --- | --- |
| 与已有未提交 UI 工作冲突 | S0 登记文件归属，编辑前读当前版本，按小批次审查 | 不整体 reset，不覆盖其他工作 |
| 保存顺序或编辑身份变化 | 先保留现有行为，验证连续输入/切换/冲突，再提取公共逻辑 | 原存储格式与键保持可读 |
| Query 键或失效范围漂移 | 搬迁阶段保持键值，跨业务失效集中协调 | 可恢复旧 Hook 与查询配置 |
| URL/嵌入状态被清空 | 明确参数归属并保留其他参数，测试前进后退 | 保留旧路由适配 |
| 主题首屏或 CSS 级联改变 | 检查 SSR 初值、样式加载顺序、主题和视口 | 样式批次单独恢复 |
| 服务实现进入浏览器 | 类型/运行时依赖分别检查，服务器代码独立入口 | 保留原代理接口，不泄露令牌 |
| 性能指标被网络或真实模型干扰 | 固定数据、生产构建和模拟任务，多次测量 | 未证实收益则保留较简单方案 |
| 静态未引用被误判为废弃 | 全仓库与兼容入口核对，业务确认保留需求 | 清理独立成批，可恢复文件 |
| 通用抽象过大 | 样板编辑器先验证，差异通过小适配表达 | 不强制所有模块一起迁移 |
| 架构检查规则遗漏或例外过期 | `check.test.mjs` 覆盖别名、重导出、动态 import 和例外匹配；新增例外写明 `reason`/`task`；S6 复跑 | 删除过期例外或补规则，不用整目录通配 |

未通过关键保存/兼容验收的批次不推进为新基线；可继续处理独立工作，但必须先解决该批次问题或恢复。后续如确需改变存储或接口协议，应单独补充迁移与恢复设计。

## 15. 后续开发的使用方式

1. 开始前阅读架构规范、当前模块代码和其待办，确认本次属于哪个职责层。
2. 新功能直接遵守标准，旧代码只整理本次涉及的部分；需要大范围整理时引用对应阶段。
3. 新增例外写明具体依赖、理由、收敛阶段，不用整个目录永久豁免。
4. 每批交付在日志记录“已实施、已验证、未验证”，更新 BACKLOG；涉及目标职责变化同步架构规范。
5. 浏览器 Computer Use 遵循当前会话/项目的模型与单桌面操作约定。测试工具可按授权使用；不得因计划写入自行更换指定模型。
