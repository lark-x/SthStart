### 1.4e 第五轮：左右分栏独立滚动

#### 1.4e-1 真正的主因：左侧导航列被拉成整页高度

第五轮先只改了页面内部的三处分栏，用户反馈「根本没生效」。复测后确认我改错了层级——真正的现象在**全站外框**，不在页面内部。

`.shell-root` 是 `grid-template-columns: auto minmax(0, 1fr)`，左侧导航列继承了 Grid 默认的 `align-items: stretch`，而 `.shell-sidebar` 只有 `overflow-y: auto`、没有高度上限，于是它被拉到与右侧内容同高。实测（1440×900，往 `.shell-main` 注入 2000px 内容）：

| 测量项 | 修复前 | 修复后 |
| --- | --- | --- |
| 导航高度（内容 1495px 时） | 1495px（=整页高度） | 900px（=视口高度） |
| `position` | `static` | `sticky` |
| 注入 2000px 后导航高度 | 3495px | 900px，不变 |
| 下滚 700px 后导航可见性 | 顶部 −595px，**整列移出视口** | 仍在视口内 |

这同时是用户说的两件事的同一个根因：「左侧不应该因为右侧内容变长而改变高度」和「下滚后右侧内容像是没显示全」——因为导航跟着页面跑掉，页面又被导航的整页高度撑出一个大滚动区间。

修法（`app/styles/shell.css`，仅 ≥1024px）：给 `.shell-sidebar` 加 `position: sticky; top: 0; height: 100dvh`。导航高度此后恒等于窗口高度、不随内容变化；条目真的放不下时（如 1440×520）由它自身的 `overflow-y: auto` 承接，而不是被页面拉长。窄屏 <1024px 侧栏本就是 `display: none` + 抽屉，不受影响；邻舍 `data-embed` 同理。

验收：三档宽度（1440/1280/1024）× 三条路由（角色库、日历、工作台）注入 2000px 后，导航高度始终等于视口高度、下滚 700px 仍在视口内；矮视口（520/700）下导航改为自身滚动（`scrollHeight 813 > clientHeight 520`），页面不被撑长。

用户反馈（连续两次澄清后确认的真实诉求）：「左侧工作区不应该因为右侧内容变长而改变自己的高度，左边应该是固定的长度」「两侧的滚动应该是独立的，左侧尽量不要滚动」。左右两栏的**视觉权重比例保持不变**，只改滚动归属。

根因：CSS Grid 的 `align-items` 默认是 `stretch`，并排两列会被拉成同高。右侧内容一长，左侧就跟着长出一大片空白，左侧真正的内容还会被拽出视口。此前只有首页 `.dash-grid` 与活动「设定」页的 `WorkbenchColumns` 显式写了 `items-start`，其余并排栏位都继承了 `stretch`。

新增共享原语 `app/components/shared/split-panes.tsx`（`SplitPanes`，92 行）：

- `align-items: start` 让两栏各自决定高度；
- 两栏共用同一个 `max-height` 并各自 `overflow-y: auto`：内容短的一栏（通常是左侧）保持自然高度、不出现滚动条，内容长的一栏在自身区域内滚动，不把页面撑长；
- 高度边界不写死：组件测量自己在文档中的纵向位置，用「视口高度 − 自身顶部偏移 − 24px 留白」算出可用高度写入 CSS 变量 `--split-available`，页头或工具栏换行时会自动跟上（监听 `resize` 与 `body` 的 `ResizeObserver`，并用 1px 阈值防止自激重测）；
- 窄屏（单栏堆叠）不启用，避免在手机上切出两个小滚动区。

### 1.4f 第六轮：滚动条自动隐藏

需求：滚动条在静止时隐藏、滚动时显形。

**只改颜色，不碰宽度**是本轮唯一的关键取舍。给滚动条声明宽度（`scrollbar-width` 或 `::-webkit-scrollbar { width }`）会让浏览器从 overlay 滚动条切换到占位滚动条，所有滚动容器凭空多出约十几像素沟槽，整页版式位移。所以实现只用 `scrollbar-color`：静止时把滑块与轨道都设为透明，滚动时换回主题色。

实测这一取舍成立（有头 Chromium，1440×900，即真实浏览器的占位滚动条环境）：

| 测量项 | 规则生效 | 临时禁用规则 |
| --- | --- | --- |
| 页面滚动条沟槽 | 15px | 15px |
| `.shell-main` 宽度 | 1201px | 1201px |

沟槽与内容宽度都不变，即「自动隐藏」没有带来任何布局位移。

新增 `app/components/shared/auto-hide-scrollbars.tsx`（挂载于 `AppShell`）：

- 在 `document` 上用**捕获阶段挂一个**监听。`scroll` 事件不冒泡，但捕获阶段仍会经过祖先，因此这一处就能收到所有后代的滚动——不必逐个容器接管，也不会随页面增删失效。
- 只给**正在滚动的那个元素**打 `data-scrolling`，而不是给根元素打：否则一个面板滚动会让所有溢出容器的滑块一起冒出来。
- 停止约 800ms 后摘掉标记；视口滚动的 `event.target` 是 `document`，标记落在根元素上以命中 CSS。

样式（`app/styles/shell.css`）覆盖 `html`、`.shell-sidebar`、`.shell-drawer`、`.split-panes > *`，以及 `[data-autohide-scroll]` 这个显式开关。弹层渲染在 portal 里、不在外框作用域内，所以 `dialog.tsx` 与 `drawer.tsx` 的内容容器显式声明了该属性。

两个补充决定：

1. **指针悬停容器时也显形**（侧栏、抽屉、双栏面板）：滑块平时不可见，若不留悬停显形，用户没有可以抓住的目标。页面级滚动条不在此列——鼠标几乎总在页面上，那样等于始终可见。
2. **深色表面用浅色滑块**：控制中心日志面板是深底，深色滑块即使显形也看不见。该容器带 `data-scroll-dark`，滑块改用浅色令牌。

新增常驻测试 `tests/e2e/scrollbar-autohide.spec.ts`（2 项）：静止透明 → 滚动显形 → 停止复隐，且只标记真正滚动的元素；另一项守住「相关选择器保持 `scrollbar-width: auto`」这一前提。

### 2.2 Playwright 端到端

> 运行方式注意：Playwright 每次运行都会自行拉起 portal+service。若在同一条命令里首尾相接连续跑多次，前一进程尚未释放端口就会让后一次的 `webServer` 启动失败，表现为 `Lifecycle script 'start' failed` + `net::ERR_CONNECTION_REFUSED` 并连带整批用例失败。这属于测试编排问题，不是界面缺陷；逐次单独运行（或等上一次完全退出）稳定全绿。

在独立端口（portal 4373 / service 4300）拉起生产构建 + 独立测试库运行：

```

```

### 2.9 首屏公共 shell 的代码分割实测（计划 §11.5）

计划要求「首屏公共 shell 不导入整个角色编辑器、媒体播放器、工作流编辑器或所有业务图标模块副作用；大型详情与媒体预览按需加载」。这条不是靠读代码判断，而是在构建产物上核对分块：

1. 全量 chunk 扫描：`角色编辑分区` 只出现在 `character-editor-*.js`，`新增镜头`/`回放编排与设备模拟预览` 只在 `activity-studio-workspace-*.js`，`ComfyUI API JSON` 只在 `generation-client-*.js`；承载外框的 `app-shell-*.js` 中这些探针**全部不存在**，只含 shell 自身代码。
2. 实际首屏载荷：请求 `/` 的 HTML 只引用 4 个脚本（`rolldown-runtime`、`framework`、`vinext`、`index-*`），逐个核对后**未包含任何重型编辑器代码**。

结论：大型详情与媒体/工作流编辑器都在路由级分块里按需加载，没有被打进公共 shell。计划 §11.5 关于「新依赖造成首屏增长超过约 40KB 需说明」的触发条件也未发生——本轮没有新增任何依赖（§1.6）。

正文这一项取样时显式区分了两类表面：**多行正文输入**（活动阶段描述、人设正文、企划要求）按 16px 判定；**等宽 JSON / 工作流代码编辑器**（`font-family` 为等宽字体）按代码可读性保留 14px，不计入正文下限。卡片里的作品名、状态、摘要属于辅助信息，按 12–14px 判定。判定规则写进了取样器注释，避免以后有人把「代码编辑器用 14px」误当成缺陷、或把卡片元信息当成正文放宽。

## 3. 本轮修复的缺陷（含取证）

### 3.1 测试依赖实时数据导致的基线漂移

工作台两块面板的内容来自真实数据库，视觉基线在「载入中/载入完成」两帧之间摇摆（桌面 863px 与 1137px 两套高度反复出现）。修复：面板载入态改用与真实列表同构的骨架（行高、行距、分隔线一致），视觉测试等到载入结束且行数达标后再截图；行内易变文本单独遮罩。现在基线同时校验面板结构、行数与行距，不再依赖数据到达时序。

### 3.2 移动端一次性横向溢出（409px > 390px）

用逐帧探针定位到：首页主区栅格的工具类媒体查询在 hydration 首帧出现一次单列轨道被内容最小宽度撑破（`.dash-grid` 容器 390px，面板瞬间 393.5px，`scrollWidth` 409px）。修复为明确的 `.dash-grid` 规则（`minmax(0, …)` + 子项 `min-width: 0`）。

验证：8 路并发 × 6 次重复加载（18 次页面加载）逐帧采样，溢出次数为 0（修复前每次加载命中 1 次）。

### 3.3 测试用例的时序脆弱点

以下三处是测试自身的时序假设，在并行跑用例时窗口变长而失败，已改为确定性写法（断言意图不变）：

- `portal.spec.ts` 命令面板：快捷键监听在 hydration 后才挂载，改为在对话框出现前重试按键。
- `portal.spec.ts` 公共服务「新建模板」：按钮首帧即由 SSR 渲染可见但点击会被丢弃，改为重试点击直到表单出现。
- `calendar.spec.ts` 新建活动的日历回显：改为 `expect(...).toPass()` 重试「打开当天详情并确认新活动在列」。

本轮又定位并修掉三处（同样只改测试自身，不放松断言强度）：

- **叙事视觉基线截到半加载画面**：连接器卡片来自异步查询，初始是空数组，截图偶尔只拍到 1 张卡（基线 148979 px 差异）。修复为在数据源区域加 `data-testid="narrative-connectors"`，截图前断言两张卡片都已渲染。这是真实的不确定性，不是「接受现状」。
- **公共服务用例击穿 30 秒上限**：该用例串行走完「新建模板→获取模型→保存→复制→编辑→建应用→绑定→解绑」，独占跑约 23 秒；与其余用例并发、且测试库模板逐次累积（已到 121 条）后超时。修复为该用例显式 `test.setTimeout(90_000)`，断言内容不变。
- **工作台视觉基线稳定化超时**：运行状态条持续轮询触发重渲染，默认 5 秒的「两帧一致」窗口在 42 项并发争用下不够。修复为截图断言 15 秒上限，像素比较仍然生效。

把并行度降到 4 之后，之前被后端过载掩盖的几条**真实测试缺陷**才稳定复现，逐条修掉：

- **叙事导入的 strict mode 歧义**：导入完成后「雨夜来信」会同时出现在左侧目录树和右侧正文标题里，`getByText` 命中两个元素。改为明确断言 `getByRole('heading', { name: '雨夜来信' })`——语义比「页面上随便出现一次」更强，不是放宽。
- **活动创建后的 URL 等待过短**：创建活动要在服务端落库并做角色快照，5 秒默认窗口在高负载下不够。改为 20 秒显式等待，仍然断言进入了详情路由。
- **新增的对比度/排版扫描超出单用例 30 秒上限**：两个 spec 各要顺序走完 10–12 条路由并逐页取样 DOM，本身就需要 20 秒以上。为这两个 spec 配置 `test.describe.configure({ timeout: 120_000 })`，断言内容与阈值完全不变。
- **窄屏导航抽屉打不开**：`frontend-experience.spec.ts` 在 `page.goto` 后立刻点击「打开导航」，该按钮由 SSR 先行渲染、hydration 前点击会被丢弃。采用与命令面板、「新建模板」相同的既有修法：重试点击直到抽屉真正出现，断言仍是「窄屏下能从导航抽屉到达每个应用」。
- **控制中心分区标签点击被丢弃**：`portal.spec.ts` 的 `local admin session` 用例在 `page.goto` / `reload` 后立刻点「自启与服务」，同样的 hydration 窗口。改为「重试点击直到面板内容出现」，断言仍是切到该分区能看到运行参数面板、且刷新后配置值仍在。
- **公共服务用例依赖「新建项在列表首屏」**：该用例每跑一次就在测试库里留下一条模板，本轮已累积到 160+ 条，列表首屏不再保证包含刚建的那条（断言 15 秒仍找不到）。改为用本次运行的唯一后缀在搜索框过滤后再断言——仍然验证「保存后记录真的出现在列表里」，但不依赖列表规模与排序；后续复制/改名步骤同样在该过滤结果内完成。

### 3.5 排版下限实测发现的真实缺陷

第二轮已经清过笔记里 9.5/10.5px 的脏值，但仍有几处「低于 14px 的可点文字」藏在不同位置，都是这次逐页取样才暴露出来的：

| 位置 | 修复前 | 修复 |
| --- | --- | --- |
| 笔记标签输入框 | `globals.css` 里 `.notebook-tags-input { font-size: 12px }` 压过了工具类 | 提升为 14px（并加注释说明为何不能再降） |
| 活动列表搜索框与「活跃活动/已归档」分段 | 12px | 搜索框 `text-xs`→`text-sm`；分段控件 `text-xs`→`text-sm`，内边距 `py-1`→`py-1.5` |
| 日历日期格与季度标题行 | 12px | `text-xs`→`text-sm`（日期数字与事件标题都更清楚） |

日历日期格和邻舍按钮这两处属于「改了会动到既有观感」的取舍，这里选择服从计划 §11.3 的量化下限；日历单元格本身就是整格可点区域，提升字号后仍未溢出（1440 与 390 两档均无横向滚动）。

共享 `Textarea` 这一条是**系统性问题**，值得单记：笔记正文一直是 16px，但全站 19 个页面用的多行输入基类是 14px，等于「正文标准」只落在一个页面。把基类对齐到 16px 后，活动阶段描述、人设正文、试演建议等所有长文输入一次性统一；代价是角色编辑器与活动新建页的视觉基线重新生成（已肉眼确认版式无挤压、行高正常）。

### 3.6 并排分栏被 `align-items: stretch` 拉成同高

同类根因在外框还引起了一个更严重的缺陷，见 §1.4e-1：左侧导航列没有高度上限，被 Grid 拉到整页高度，滚动时整列移出视口。它和页面内分栏是**同一个 `stretch` 默认值**的两种表现，因此一并按「给容器明确高度上限 + 自己滚动」的方式修掉。

定位方式是往每个候选容器的右侧塞 2000px 假内容、再比对左侧高度是否变化，而不是只看截图是否「显得空」。全站 11 条路由跑下来，唯一被拉长的是外框的 `.shell-sidebar`；页面内部三处分栏在第五轮已修好。

前几轮把各页送进统一外框时逐页重做了页面内部构图，但并排两栏仍沿用 Grid 默认的 `stretch`。后果不是「看起来不齐」，而是耦合：右侧内容一变长，左侧面板就跟着长出一片空白，左侧真正的内容还被推出视口；页面级滚动条随之出现，想继续看右栏必须先滚过左栏的空白。

沟通中我先后把现象误读成「右侧内容被裁切」和「左栏留白过多」，实际是同一处耦合的两个表现：测量显示日历页左右两栏在 1440 宽下各为 546px，完全相等；把右侧内容换成 1800px 假内容后左栏跟着变成同等高度。

修法是让两栏各自成为滚动所有者（见 §1.4e），列宽与视觉权重完全不动。验收：注入假内容后逐帧测量，左栏高度与滚动条状态保持不变——日历月历面板在右栏内容 2024px 时仍为 502px。

10. **全量套件对机器负载仍然敏感**：本轮已把并行度降到 4 并修掉确定性缺陷，但机器上还有多个其他线程留下的长驻 Node 进程（4173/4273/9330 与 Codex 辅助进程）。在这种负载下偶发 `503`/`ERR_NO_BUFFER_SPACE`/Node 自身崩溃仍可能出现。判定口径：**单条用例单独跑通过 + 报错是环境类别**，即不计为界面缺陷；若要稳定的 CI 结果，建议把套件放到独立、无其他长驻服务的机器上跑。这里没有用重试或放宽断言来掩盖它。
11. **回放页左栏在矮视口下仍会出现滚动条**：设备模拟预览是固定 300×580px 加进度条（约 678px 高），1440×900 这类较矮视口下可用高度只有约 536px，左栏需要滚动才能看到进度条；1440×1080 下自然放下、无滚动条。这是内容固有高度，不是被右栏拉长——右栏独立滚动已成立（右栏内容 2074px 时仍锁在 536px 内）。要让左栏在矮视口下也不滚动，需要让设备预览按可用高度等比缩放，会改变预览的显示比例，属视觉取舍，未擅自改动，待确认。
12. **左侧导航固定高度依赖页面级滚动，而非把导航挂在 `100dvh` 外框内**：本轮把 `.shell-sidebar` 钉住后，导航视觉上稳定、不再随内容跑掉，但整个应用仍是「页面在 `.shell-content` 里自然增高、整页滚动」的结构（§1.4e-1）。这一步刻意没有改成 `100dvh` 内框滚动，因为那会同时改变移动端软键盘行为与离线页的滚动归属，超出本次诉求范围。若后续要彻底做到「右侧内容区自己滚、页面本身不滚」，需要单独一轮并把移动端键盘态一起回归。
13. **滚动条自动隐藏没有淡出动画**：`scrollbar-color` 在 Chromium 里不是可过渡属性，所以滑块是直接显隐、不是渐变。要做淡出必须改用 `::-webkit-scrollbar-thumb` 配合 `transition`，但那样会触发浏览器切换到占位滚动条模式、带来布局位移（§1.4f 的取舍），因此没有采用。
14. **滚动监听在水合之后才挂上**：`AutoHideScrollbars` 是客户端增强，SSR 首帧到水合之间滚动不会触发显形。这是渐进增强的固有边界，不是缺陷；`tests/e2e/scrollbar-autohide.spec.ts` 以「重试滚动直到标记出现」的既有写法覆盖这个窗口。
15. **页面级滚动条只响应滚动，不响应悬停**：内层容器（侧栏、抽屉、双栏面板）悬停即显形，便于抓取；页面级滚动条若也悬停显形，等于始终可见，失去本功能的意义。代价是用鼠标拖拽页面滚动条时需先滚动一下让它出现。
