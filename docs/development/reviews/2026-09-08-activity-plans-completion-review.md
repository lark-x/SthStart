## 3. 需要优先处理的问题

以下 P1 表示阻断核心功能或计划验收；P2 表示应在交付前完善的一致性/质量问题。

### F01 · P1 · 已分配工作流仍无法创建生图任务【已复现】

位置：`apps/service/src/activities/image-attempts.ts:148`、`apps/service/src/generation/task-store.ts:49`。

活动调用 `createGenerationTask` 时直接传入 `workflowId`、`workflowVersion`，但没有进入公共服务允许的内部调用语义。公共服务会拒绝这种客户端指定工作流的请求。

在隔离环境成功创建 engine、workflow、发布版本并配置活动用途后，请求仍返回：

```text
HTTP 400
error: image_attempt_failed
message: 工作流由管理控制台统一分配，客户端不可直接指定 workflowId 或 workflowVersion。
```

影响：IMG-R01、IMG-R02、IMG-A03/04 的生成主路径无法通过。不是简单的“还没配置 ComfyUI”。

修复方向：通过公共服务的用途分配或经过验证的内部冻结执行计划接入；保留公共 API 禁止任意指定工作流的边界。补一个确实创建 attempt/task 的已配置成功测试。

### F02 · P1 · 图生图参考图没有进入准备请求，成功响应也与前端约定不一致【代码确认】

位置：`app/features/activities/components/image-workbench.tsx:211`、`:254`，`app/features/activities/api.ts:437`，`apps/service/src/activities/routes.ts:1236`。

用户选择参考图后，准备配方请求只根据选择状态传入 `denoise`，没有传入 `references`。编译器读取请求中的 references，默认空数组，没有从槽位的 `referenceAssetKeys` 自动解析为 Artifact 输入。因此界面选图并不等于实际请求包含参考图，后续用途判定也可能仍按文生图执行。

此外，前端将创建结果声明为 `{ attempt, task }` 并读取 `res.attempt.id`，后端返回的是裸 `GenerationAttempt`。修复 F01 后，即使后端已接受任务，前端仍会在读取结果时出错。

修复方向：统一引用图到 Artifact 的契约和准备请求；统一响应结构，消除虚假的 TypeScript 返回类型保证。验证“选图→准备→预览引用图→实际工作流上传/绑定→收到任务”全过程。

### F03 · P1 · 来源跳转没有接入，记录入口的采用操作为空操作【代码确认】

位置：`app/features/activities/components/activity-studio-workspace.tsx:474`、`media-workstation.tsx:430`、`image-workbench.tsx:265`、`:691`。

`PromptSourcePanel` 的定位委托给 `onLocateField`，但两个 `ImageWorkbench` 挂载位置都没有提供这个回调。因而来源面板虽能展示资料，无法按计划跳转到具体角色、阶段或镜头字段修改。

从记录进入工作台时，还缺少 `onAdoptSlotAsset`；点击采用时处理函数直接返回。媒体工作区入口有采用回调，但来源定位同样缺失。

影响：用户最关注的“发现图像不符合预期→追到原始提示词源头→修改→再次生成”没有形成闭环。对应 IMG-R05/09、IMG-A09。

修复方向：建立统一实体/字段导航，明确历史值与当前编辑值；所有工作台入口复用同一套采用动作。用真实组件入口验证，不能只测解析来源的 API。

### F04 · P1 · 预览执行计划没有真正冻结，实际发送快照不完整【代码确认】

位置：`apps/service/src/activities/image-prompt-compiler.ts:71`、`:406`、`:434`，`image-attempts.ts:116`、`:132`、`:194`。

具体缺口：

- 编译器接收 `nodeBindings`，但没有使用它验证有效参数。渠道名固定输出多个别名，参数只是多层对象合并，不能保证预览显示的参数实际有节点接收。
- 前端准备请求没有携带工作流版本，准备路由也没有把当前分配解析成冻结的工作流输入。执行计划哈希可能包含空工作流，且不包含引擎或工作流图哈希。
- 提交端虽然注释写着“验证 assignment 与编译计划一致”，实际只检查 assignment 是否存在，没有在分配变化时拒绝静默切换。
- 提交端允许 `customInputs` 覆盖编译内容，但这部分不进入业务请求哈希。
- 新生成链路只插入 `prepared` 快照，上传映射初值为 `{}`；没有找到在实际发送边界记录上传后节点文件名、最终 graph 的写入路径。

影响：IMG-R03/08、IMG-A02/05/14/18 未满足。当前保存的是准备信息，不能据此承诺“这就是当时实际发送给 ComfyUI 的全部内容”。

修复方向：准备时冻结 assignment、引擎、工作流图/版本和有效输入；提交时核对冻结计划；执行器在实际发送边界写不可变快照，处理上传映射和未知发送结果。

### F05 · P1 · UI 完整导出缺溯源，工程导入后来源断链【已复现】

位置：`app/features/activities/api.ts:356`，`apps/service/src/activities/exports.ts:420`、`:480`，`imports.ts:636`、`:647`。

存在两个独立问题：

1. UI 发送 `mode: 'full'`；新增来源资料只在 `format === 'project'` 时打包。UI 当前完整导出走默认 HyperFrames 工程格式，没有携带溯源资料，也没有提供选择这种工作工程的对应契约。
2. 显式按 `format: 'project'` 导出后，导入器为 SourceRef 创建新 ID，却没有同步重映射 `PromptBlock.sourceRefIds`。导入接口成功不代表来源关联正确。

隔离复现结果：

```text
project_export: HTTP 200, provenance=true
import_sources: HTTP 201, refs=7, danglingBlockSourceIds=7
ui_full_export: HTTP 200, provenance=false
```

影响：IMG-R12、工程恢复及来源跳转。计划允许阅读包、视频工程与工作工程各有用途，但 UI 必须提供准确选择，工作工程往返必须保持可追溯关系。

修复方向：对齐前后端导出格式；为所有引用建立完整 ID 映射，包括来源块、实体、修订、Artifact 和派生关系。导入后检查每条引用实际可解析，并验证可以据此创建新尝试，而不仅仅检查资料条数。

### F06 · P1 · 应用预览与成片不是同一实现，已有样片无音轨【代码确认＋媒体检查】

位置：`app/features/activities/components/playback-workstation.tsx:283`，`packages/activity-playback/src/compile-hyperframes.ts:145`、`:165`、`:182`。

应用预览仍只渲染前 8 条聊天文字；展开媒体显示“视频播放中/照片查看中”等占位界面，没有加载对应真实媒体，也没有使用 ADR 所称的同编译器 iframe。

HyperFrames 编译器还存在这些差异：

- 滚动位置用消息序号乘 240、帖子序号乘 300，未使用真实布局测量；长文字、图片和不同高度记录会导致定位偏差。
- 未完整处理协议中的逐条显现、评论显现、输入状态、阶段卡等动作；切换聊天未按指定 conversation 过滤，不能视为全部回放动作已实现。
- 视频通过时间轴回调动态修改 src、再用 GSAP 推进 `currentTime`，没有按计划建立静态可解析的媒体片段时序，`volume` 未在该编译路径处理。

本次使用 ffprobe 检查：

```text

packages/activity-playback/fixtures/camp_video.mp4
duration=5.000; streams=[video,audio]
```

测试回放对视频配置 `volume: 1`，ADR 又声称音频正常播放；现有成片不能支持该验收结论。

影响：主计划 R11、R12、R14，尤其是用户需要的“模拟手机录屏聊天与朋友圈、点图和播放视频”。这属于原计划功能缺口，不是视觉精修。

修复方向：统一预览与导出编译结果；补真实布局和动作语义；使用 HyperFrames 的媒体时序契约。对导出包做实际渲染、音轨检测、顺序播放与随机 seek 对比，更新 ADR 为实测事实。

### F07 · P1 · 全活动生成没有本批前序剧情上下文；输出验证直接标为成功【代码确认】

位置：`apps/service/src/activities/text-jobs.ts:68`、`:76`、`:85`、`:117`。

`whole-text` 依次调用每个阶段的生成，但每次仍使用同一个原始 document。刚生成的上一阶段候选没有进入下一阶段 prompt。新活动连续生成时，阶段二无法看到本批阶段一刚建立的事实，容易出现人物行为、物件归属和事件结果不一致。

生成结果在 JSON 解析后直接保存 `validation: { valid: true }`，该路径没有完成计划要求的结构、实体引用与事实一致性验证。

影响：主计划 R05/06/08 与全活动连续叙事要求。

修复方向：维护本批临时候选上下文，将前阶段已验证事实/记录纳入后阶段提示词，不自动采用到用户当前版本。对模型输出执行结构和语义校验，错误作为可见的失败或待修复结果，不直接标记 valid。

### F08 · P1 · ZIP 解压限制信任包内声明，可被实际内容绕过【已复现】

位置：`apps/service/src/activities/zip.ts:360`、`:385`。

当前累加 ZIP 中央目录声明的 `uncompressedSize`，随后调用无限制 `inflateRawSync`，没有依据实际输出核对长度或限制解压输出。只需让声明尺寸小于实际内容即可绕过总量限制。

本次使用仅 4 KiB 的无害测试内容，将声明长度改为 1，并设置总量上限 100。读取器仍返回 4,096 字节。

影响：主计划明确要求的导入规模/ZIP 炸弹防护没有达到要求，大包可能超出预期内存边界。

修复方向：限制实际解压输出、校验声明与实际长度/校验和、按实际字节累计；为压缩流超限设置提前中止。继续保留已有路径穿越检查。

### F09 · P2 · 自动种子破坏相同请求幂等，现有同名测试未覆盖成功路径【代码确认】

位置：`apps/service/src/activities/image-attempts.ts:73`，`apps/service/src/activities-images.test.ts:330`。

未指定 seed 时，在查询幂等记录之前生成随机种子，并把它加入请求哈希。同一请求、同一幂等键再次提交会得到新的随机数，通常被判为不同请求并返回 409。应复用首次解析种子，或先根据稳定业务输入命中已有尝试。

名为“Scoped Idempotency and Attempt conflict (409)”的测试实际只验证未配置引擎时返回 400、没有孤儿记录，没有创建一个成功尝试，更没有覆盖重复提交。这也是 106 项通过仍遗漏 F01 的直接原因之一。

此外，全活动文本任务在没有活动用途分配时回退到通用 LLM Profile（`text-jobs.ts:43`）；交接时应核对这是否符合原计划的显式模型分配要求，并如实显示实际使用模型。
