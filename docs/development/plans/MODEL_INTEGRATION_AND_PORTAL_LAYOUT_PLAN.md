## 1. 用户目标与已确认决策

用户希望完成两件事：修复活动企划找不到模型的问题，检查其他模块有无类似接入遗漏；让活动及门户其他主要页面展示更多有效内容，减少大屏留白和寻找主要操作时的下滑。

| 决策 | 已确认选择 |
| --- | --- |
| 整体布局 | A：双栏工作台；不是三栏工作台，也不是仅压缩单栏间距 |
| 页面范围 | 门户全部主要页面，包括活动、角色、日历、笔记、叙事、创作中心和配置页 |
| 邻舍范围 | 检查公共模型接入兼容性；不重做邻舍内部聊天、设置等界面 |
| 当前配置修复 | 活动工作室、角色库的文本角色若仍为空，绑定现有 `ds-jy` |
| 原有选择 | 保留已有应用绑定、角色专属配置及多模态绑定 |
| 后续默认行为 | 不引入全局默认模型，不在每次启动时自动绑定模型 |
| 视觉风格 | 保留现有配色、正常字号、护眼模式和主要交互习惯 |
| 验证方式 | 自动化测试使用隔离数据和模拟模型；不自动发送用户角色资料进行真实收费生成 |

### 1.1 成功标准

1. 活动工作室和角色库都能在「公共服务 → 应用路由」出现、保存模型选择并在重启后保持。
2. 已授权的空文本绑定得到修复；活动企划不再因该配置遗漏而失败。
3. 未绑定或配置失效时，用户能看到具体原因，并直接到达正确应用的配置区域。
4. 模型已保存但列表加载失败、模型配置可读取但上游不可调用等状态，不再被混为一个成功或失败提示。
5. 桌面新建活动页同时展示设置和 AI 企划入口；用户不必先滚过全部阶段才能生成企划。
6. 宽屏列表突破固定三列限制；阅读正文仍保持适合阅读的行宽。
7. 页面布局调整不破坏草稿、候选企划、角色快照、版本冲突处理和原有保存行为。

## 4. 模型接入修复方案

### 4.1 应用注册与接入审计

在 `generation/consumers.ts` 给 `activities`、`characters` 增加 `llm`。将消费者能力数组约束为共享 `PublicCapability` 类型，防止字符串随意扩展后再次遗漏契约。

复用 `ensureGenerationConsumerApps` 当前的插入/冲突更新流程同步存量能力；不新增数据库表，不重建已有模型、凭据或绑定。不要同时重构系统令牌生命周期。

扫描全部 `resolveAssignedLlmProfile`、`resolveCharacterLlmProfile` 和实际模型调用路径，产出审计表，至少包含：应用 ID、调用场景、所需角色、绑定来源、能力声明、UI 入口、错误提示及测试覆盖。`narrative` 没有直接文本模型调用就不增加 `llm`。外部应用仍按显式授权能力使用接口。

### 4.2 模型状态的统一定义

新增服务器内部状态解析 helper，模型实际调用和配置状态查询共享规则；实现可放在 `providers.ts` 或其相邻模块。

结构配置判定顺序：应用存在且启用 → 角色绑定存在 → profile 存在且为 LLM → profile 启用 → 能力标签包含所需角色 → 模型 ID 非空。返回细分原因，不能把所有失败都折叠成“未配置模型”。角色专属调用继续采用“有专属绑定就使用专属绑定，否则使用 characters 对应角色”；专属绑定失效时显示错误，不静默改用另一个模型。

建议新增共享 `LlmBindingStatusSchema`，确定使用如下字段：

```ts
type LlmBindingStatus = {
  appId: string;
  role: 'text' | 'multimodal';
  status: 'ready' | 'app_disabled' | 'unassigned' | 'profile_missing'
    | 'profile_disabled' | 'capability_mismatch' | 'model_missing';
  ready: boolean;
  profile: { id: string; name: string; model: string | null } | null;
  credentialSource: 'keyring' | 'environment' | 'none';
  message: string | null;
  configurationPath: string;
};
```

`ready` 仅表示当前结构配置满足该角色调用条件，不表示已对上游进行联网探测。凭据来源独立展示，绝不返回凭据值、自定义认证头或包含敏感参数的 URL。

**凭据兼容约定：**仓库现有调用允许空密钥，可能连接无需认证的本地服务。本次不新增“缺少密钥一律禁用”的限制，也不引入认证方式设置。`credentialSource=none` 时提示“未配置凭据；若服务要求认证，请补充 API Key”，真实上游 401/403 才归为认证失败。保留系统凭据库和环境变量回退。这是对前期“缺少凭据就不可用”概括的明确收敛，避免破坏现有服务。

### 4.3 接口约定与兼容

1. 管理端增加 `GET /api/v1/admin/apps/:appId/llm-status`，返回 `{ appId, text, multimodal }`，两个角色均使用上述状态结构；不存在的应用返回 404。继续使用现有管理员鉴权和门户代理，不另开未鉴权端点。
2. 在 `GET /api/v1/admin/activities/capabilities` 中保留 `llm`、`llmProfile` 等原字段，新增可选 `llmStatus`，内容为活动文本角色状态。`llm` 与 `llmStatus.ready` 一致；`llmProfile.name` 使用真实显示名称。
3. 保留 `/api/v1/app/config` 的原字段、null 表达以及聚合 `llm.ready` 语义；逐角色 ready 改由统一规则产生。文本功能依赖 `text.ready`，不能要求多模态也配置。
4. 新状态契约与服务器、前端同批构建。老数据没有新增字段时，前端回退到原能力字段，并展示一般配置入口，不崩溃。
5. 本次绑定继续调用现有 `PUT /api/v1/admin/apps/:appId/llm-assignments`，提交文本和多模态两个字段。该接口未提交的角色可能被清除，因此不得只发送文本字段。
6. 新增字段不替换旧接口，不改变模型选择优先级，不增加数据库迁移版本。

### 4.4 页面提示、任务预检与错误归类

活动企划区在生成按钮附近显示“文本模型：ds / deepseek-flash”或明确未就绪原因，并提供“配置活动模型”。模型状态请求失败显示“暂时无法确认模型配置”和重试，不显示“模型不存在”。

结构配置未就绪或状态仍加载时，禁用 AI 生成入口；“直接创建活动”仍由原有表单有效性控制。模型预检不影响手动填写活动。

服务端在创建生成任务前检查配置；未就绪时返回 409 和现有错误响应风格中的机器码、可读信息、配置路径。任务执行前再次检查；若排队后配置发生变化，任务进入失败状态并记录准确原因。恢复队列中的任务也必须使用同一规则。

| 场景 | 文案含义 | 用户操作 |
| --- | --- | --- |
| 未绑定 | 活动工作室尚未选择文本模型 | 配置活动模型 |
| 模型已失效或停用 | 当前绑定的模型不可用，需要重新选择或启用 | 打开对应应用路由 |
| 能力不匹配 | 所选模板不支持当前文本或图文角色 | 更换模型或修正能力标签 |
| 无凭据 | 若上游要求认证，需要补充密钥 | 编辑模型模板；不自动禁止无认证服务 |
| 上游认证失败 | 模型服务拒绝认证 | 检查该模板的 API Key |
| 上游超时/限流/异常 | 服务请求失败，配置可能仍有效 | 明确可重试，不要求重复添加模型 |
| 生成格式错误 | 模型返回结果无法解析成企划 | 保留会话与原内容，允许重试 |

角色生成、试演和识图沿用同类提示，不在用户界面裸露 `llm_profile_not_assigned` 等内部代码。业务日志保留必要机器码，过滤密钥和认证头。

### 4.5 配置定位、状态刷新与草稿保护

- 统一配置链接：`/settings/public-services?section=routing&app=activities`，角色库使用 `app=characters`，邻舍使用 `app=linshe`。
- 页面读取白名单 section 值；routing 分类挂载后定位并短暂强调目标应用行。目标不存在时保留路由分类并显示未找到目标的提示。
- 兼容 `#app-model-routing`：自动打开路由分类。若 URL 已含明确 section，则以有效 query 值优先。
- 切换分类更新 URL，支持刷新、浏览器前进和后退。一个分类变更不重置其他分类中已输入的草稿。
- 活动页配置链接默认新标签打开，防止在尚无服务端企划会话时离开页面而丢失本地表单。回到原标签触发状态刷新，同时保留手动“刷新模型状态”。
- 模型保存、删除、停用、能力修改和绑定保存后，失效公共概览、runtime 概览、活动 capabilities 和新增应用模型状态 query。角色专属配置保存后刷新对应角色状态。
- 给新增 query 使用稳定 key，例如 `providerKeys.llmStatus(appId)`；不要因整页 refetch 无条件 reset dirty form。

### 4.6 当前环境一次性绑定

先修复注册与接口，再操作现有配置：

1. 重新读取 `activities`、`characters` 的全部角色绑定，以及 `ds-jy` 的启用状态、模型 ID、能力和凭据来源。
2. 仅当该应用文本绑定为 null，且 `ds-jy` 仍存在、启用并支持文本时，写入 `textProfileId=ds-jy`；多模态字段使用刚读取的原值。
3. 若已绑定其他模型则跳过，不重新分配；不修改邻舍和角色专属配置。
4. 记录修复前后非敏感快照，回读验证，并在容器重启后再确认。
5. 若 `ds-jy` 已不存在或失效，完成代码修复但不猜测替代模型，在交付中明确待选择项。

这一步属于当前部署修复，不写进每次启动的通用初始化逻辑。不得用“数据库最早的模型”作为隐式回退。

## 5. 布局规范与共享组件

### 5.1 尺寸与断点

| 项目 | 规格 |
| --- | --- |
| 页面容器 | `width:100%`，最大 1920px，居中；最大宽度包含内边距 |
| 左右内边距 | 小于 640px 为 16px；其他宽度为 24px |
| 外部区块间距 | 12–16px；面板常规内边距 16px，紧凑信息区 12px |
| 普通双栏 | 小于 1280px 单栏；1280px 起使用 `minmax(0,2fr) minmax(0,3fr)` |
| 主区＋侧栏 | 小于 1280px 单栏；桌面 `minmax(0,1fr) 360px` |
| 阅读正文 | 保留约 65–85 个字符的理想行宽；不得因容器扩大而让长段落铺满屏幕 |
| 列表卡片 | 使用 auto-fill，最小宽度约 280px；少量卡片不拉伸到占满整行 |
| 按钮 | 桌面主要操作高度约 36–40px；触屏主要点击区域至少 44px |
| 字号 | 不全局缩小；正文以现有 14–16px 为基础，辅助信息不低于 12px |

自适应网格需使用 `min(100%, 280px)` 等方式避免手机视口下最小列宽导致溢出。所有 grid/flex 主内容单元显式考虑 `min-width:0`。

### 5.2 共享实现边界

新增轻量的页面容器、工具栏和双栏容器组件，放入 `app/components/shared/`。组件只负责尺寸、间距和布局，不接管业务状态或数据请求。给 PageHeader 增加显式 compact 配置，逐页采用；不要用广域 CSS 选择器统一重写所有页面标题。

压缩标题区重复说明和概览大卡，短说明保持一行到两行，技术细节放进可展开帮助。过滤项与常用操作尽量在同一工具栏，空间不足自然换行。

不新增全局布局切换、密度偏好、拖拽分栏、无意义统计卡。沿用现有 tabs、输入框、弹窗和主题 token，避免另建视觉系统。

### 5.3 滚动、固定操作与状态生命周期

普通列表和表单采用整页滚动，不给每张卡片设置滚动条。现有叙事、预览或编辑器内部滚动有必要时保留。长侧栏不强行固定，避免视口高度不足时无法访问底部内容。

活动创建/保存工具栏使用吸底区域，预留同等底部空间并兼容移动端安全区；不覆盖错误提示、最后一个输入框或弹窗。长页面导航可吸顶，控制层级和滚动定位偏移。

响应式布局只移动已有组件位置或调整 CSS 网格，不在不同断点同时挂载两份表单。严禁因为窗口 resize、切换布局或 refetch 而重新初始化草稿。

```text
──────────────────────────────────────────────────────
左栏：活动设置约 40%          右栏：企划与阶段约 60%
┌ 模板选择（紧凑选择器） ┐    ┌ 当前模型状态 / 配置入口 ┐
│ 基本信息，字段两列     │    │ AI 指令 / 生成按钮       │
│ 参与角色与快照摘要     │    │ 候选企划 / 应用结果      │
│ 寿星选择等关联设置     │    │ 阶段列表与阶段编辑      │
└──────────────────────┘    └────────────────────────┘
──────────────────────────────────────────────────────
表单或企划状态                直接创建活动 / 使用企划创建
```

- AI 入口位于右栏顶部，而不是阶段列表之后。首屏必须露出指令框、生成按钮和模型状态。
- 模板改用紧凑选择器并保留模板说明、切换确认和原有预填逻辑；不在顶部展开大面积模板介绍。
- 左栏显示参与角色摘要、数量和添加入口；人设长文在原有详情或展开区查看。保持快照冻结和草稿变化检测。
- AI 指令框默认约三行，可扩展；空白时使用合理占位提示，不固定成大面积空白。
- 生成结果使用现有候选机制，不创造新的正式活动。候选选择、应用与阶段修改的状态分开，应用新结果前保留原有覆盖保护。
- 阶段采用紧凑标题列表；展开当前编辑项，标题、顺序、说明和结束条件均可编辑，增删阶段不丢失其他输入。
- 原始 JSON、会话完整 ID、技术状态移入调试详情。用户区域显示“企划已保存/生成中/生成失败”等可读状态。
- 单栏顺序固定为：模板与基本信息 → 角色 → AI 企划 → 阶段。创建操作保留可见。
- “使用企划创建”仍受候选有效性、角色快照冲突和表单校验控制，不能因为重排布局而提前放行。

### 6.2 活动列表与活动编辑

列表：顶部合并数量、搜索、归档筛选、新建、导入；卡片保留标题、状态、日期、地点、角色与版本等已有关键字段，长描述截断但详情可读。采用自适应列数，复制、归档、删除等动作保持原有语义和保护。

编辑：保留记录、设定、素材、回放分类；标题、保存状态、生成入口、版本相关操作组成紧凑工具栏。设定分类将基本信息和角色放左侧，阶段放右侧；记录分类保留记录编辑主区，现有辅助信息在侧栏；素材和回放优先扩大内容与预览区，不硬塞成两块窄区。

保留 expected revision/head version、草稿冲突比较、候选应用、素材引用与回放关联，不在布局工作中改动版本模型。

### 6.3 角色库与角色编辑

角色库：使用自适应网格；保留作品、标签、收藏、搜索、批量整理和筛选 URL。顶部批量操作只在有选择时出现，避免常驻大块空白。头像比例固定，长姓名和标签不撑宽卡片。

角色编辑：保留身份、人设、外观、关系、发布等已有分区；主栏编辑当前分区，360px 侧栏展示头像/摘要、当前模型状态与相关辅助操作。来源或发布辅助信息只在相关分区出现，不重复堆放全套表单。

模型区域清楚区分“沿用角色库模型”和“角色专用模型”。新角色尚未保存时不请求不存在的角色绑定。保留 V2 草稿、导入、头像、试演和发布工作流。

### 6.4 日历

已有双栏可直接复用，调整为日历主区＋360px 详情栏。月份导航、搜索、作品与类型筛选收进紧凑工具栏。当天生日、活动、选中角色和创建入口放详情栏；无选择时提供明确引导，不添加填空统计。

小屏详情放日历下方，日期格保持可点选，多条事件用数量与简短摘要，不用长内容撑高每个格子。保留月份、筛选、选中日期及多人生日预填行为。

### 6.5 创作笔记

列表采用自适应卡片/现有列表组件和紧凑工具栏。编辑页使用正文＋360px 元信息栏，侧栏放既有标签、关联对象、附件或保存状态；正文内部保留阅读宽度，媒体预览可比文本宽。

不改动自动保存、离线存储、同步冲突和附件上传。错误和离线状态靠近保存状态显示，不能因新的固定工具栏而隐藏。

### 6.6 叙事档案

已有目录树＋阅读主区视为已符合双栏方向，不推翻。调整标题区、目录宽度和外部留白；阅读正文保持行宽，导入与连接器界面利用宽屏并排展示配置与结果。保留作品/节点选择、搜索、阅读位置、导入任务状态及现有视口内滚动。

### 6.7 创作中心

保留已有参数＋结果双栏，减少顶部模式选择和说明的高度，扩大结果区。生成参数、提交状态可见，任务记录与结果复用现有组件。横纵媒体按比例 contain 展示，不为填满空白裁掉内容。不更改工作流、Worker 或模型路由策略。

### 6.8 门户、公共服务和管理配置页

- 门户首页：紧凑欢迎/导航区，应用入口自适应网格，已有状态与最近内容自然并排；不添加不存在的数据面板。
- 公共服务：保留之前已做的状态栏、模板搜索和弹窗；扩大内容宽度，完善应用路由状态与深链接。在模型卡显示使用方或未分配提示，保存后提供“分配给应用”入口，不静默绑定。
- 控制中心：保留分类，压缩顶部指标，配置表单与状态详情并排，日志继续使用宽主区。
- 生成配置：引擎、能力或工作流列表与当前配置详情采用两栏；复用已有编辑组件，弹窗只承载短操作，不把复杂配置塞进狭窄小窗。
- 空数据、错误和加载态保持简洁；不得把页面剩余高度都填成一个巨大提示卡。

## 7. 实施顺序与交付切分

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 基线 | 工作区差异、数据和页面基线、调用入口审计 | 明确已有变更与真实绑定，形成审计表 |
| P1 服务修复 | 能力声明、类型约束、状态 helper、兼容接口、任务预检 | 服务级回归通过，旧客户端可继续读取 |
| P2 配置闭环 | 应用路由、深链接、状态提示、查询失效、角色回退显示 | 未绑定到完成配置的路径可走通 |
| P3 活动布局 | 共享布局组件、新建活动、列表、活动编辑 | 重点视口首屏与草稿回归通过 |
| P4 全门户 | 角色、日历、笔记、叙事、创作中心、门户和配置页 | 逐页验收完成，无宽屏浪费或手机溢出 |
| P5 发布 | 构建镜像、备份、更新容器、一次性空绑定 | 重启后代码与配置持续生效，完成运行核对 |

每阶段只提交相关变更；不要夹带无关项目清理。模型修复应能独立回归，避免必须等全部视觉修改结束才能验证。

## 8. 测试与验收矩阵

### 8.1 服务和契约

- [ ] 创建空数据库后，activities 与 characters 均含 `llm`；已有数据库初始化后能力补齐，绑定不变。
- [ ] 每个实际 LLM 消费模块都有对应声明，消费者能力满足共享契约；overview 全量响应通过 TypeBox 校验。
- [ ] 状态接口在未绑定、停用、缺模型 ID、能力不匹配、失效引用等场景返回正确状态；读取不泄露凭据。
- [ ] 环境变量凭据回退和无认证本地服务保持兼容。
- [ ] 仅文本就绪时，活动文本生成可用；不要求图文模型。
- [ ] 角色专属模型优先，空值才继承应用配置；失效专属模型不静默回退。
- [ ] 任务提交预检和执行前复检一致；失败后企划会话、角色快照及表单内容仍保留。
- [ ] 用模拟模型完成企划生成、候选应用、正式创建；生成候选阶段没有新建正式活动。
- [ ] 模型引用保护覆盖角色专属及应用绑定；若发现真实保护缺口，只补相关用例与行为，不扩展到无关权限重构。

### 8.2 前端操作

- [ ] 模型保存成功但 refetch 失败时提示“已保存，列表更新失败”，不诱导重复添加。
- [ ] 应用绑定保存后状态刷新，刷新页面和服务重启后选择不丢失。
- [ ] 未配置入口直接打开对应应用；旧锚点能打开路由分类；前进/后退与刷新一致。
- [ ] 配置页在新标签打开，返回活动页后状态刷新，尚未创建会话的表单也不丢失。
- [ ] 新建、编辑、复制模板表单状态分离；只读 ID 仍随编辑提交；密钥警告不会被 reset 清掉。
- [ ] 网络失败不显示假空列表、不把未加载的绑定保存为空。
- [ ] 各种配置状态只禁用相关 AI 功能，不阻塞手动创建或其他无关功能。

### 8.3 布局场景

固定检查 1920×1080、1440×900、1280×720、390×844 四种视口，并在 200% 缩放下核对主要操作可达。

| 页面/场景 | 验收要求 |
| --- | --- |
| 新建活动，初始状态 | 桌面首屏展示基本设置、AI 模型状态、指令和生成入口，创建操作可见 |
| 多角色、多阶段、长候选 | 两栏不互相撑宽；展开、删除、应用候选不会清空其他编辑 |
| 活动和角色列表 | 1920px 下每行至少可容纳五张标准卡片；少量记录不拉成巨卡 |
| 日历 | 月历与详情并排，密集日期可点选，小屏详情仍可访问 |
| 笔记和叙事 | 正文行宽适宜，目录/元信息利用侧边空间，阅读滚动不退化 |
| 所有配置表单 | 错误信息和底部按钮不被吸顶/吸底元素遮挡 |
| 手机 | 不出现整页横向滚动，表单单份挂载，弹窗内容可滚动，关闭按钮可达 |
| 两种主题 | 配色、焦点、禁用态和警告对比可辨识 |

截图用真实结构的测试数据，不为截图隐藏错误、固定伪造数量或删除功能。长名称、长 URL、空列表和加载失败必须各覆盖一次。

### 8.4 推荐检查流程

按当前 package scripts 核对后运行：类型检查 → 相关服务与契约测试 → 目标前端 lint → 生产构建 → 相关 E2E → 四视口人工核对。现有 `playwright.config.ts` 使用独立端口与 `e2e` 数据库，继续保持隔离；不要把自动化指向用户生产数据库。

需要新增的测试以真实回归为中心：能力注册与 schema 一致性、未绑定到绑定的恢复链路、角色覆盖优先级、布局切换不丢草稿。布局变化导致的快照差异必须人工检查后更新，不能批量接受所有截图。

## 9. 部署、持久性与回滚

1. 部署前记录当前镜像标识、容器映射和健康状态。使用项目现有 SQLite 一致性备份方式，不在运行中简单复制主数据库文件而漏掉 WAL。
2. 备份包含模型绑定等实际数据；凭据主密钥保持原配置，不重新生成、不打印、不写进仓库或报告。
3. 使用最终源码构建新镜像并在隔离环境验证，再替换当前本地容器。不要仅 `docker cp` 构建文件后把运行容器当成最终交付。
4. 沿用已有数据卷和端口，保留上一个镜像用于回滚。不要在更新时删除 volumes 或重新初始化数据库。
5. 服务健康后执行第 4.6 节已授权的一次性空绑定，再回读并重启验证。
6. 检查门户概览、活动模型状态、应用路由、角色回退和邻舍既有模型状态兼容性。绑定成功不等于真实外部推理成功，应在报告中区分。
7. 回滚代码使用上一镜像；本次能力新增与旧接口兼容，不删除新增能力或任意清空绑定。确需撤销本次绑定时，只恢复记录中由本次修改的两个文本角色，且确认此后用户未再次修改。
8. 仅当数据确已损坏时考虑完整数据库恢复；不要为视觉问题回滚整库而丢失用户新增内容。
