## 1. 产品决定与范围

### 1.1 本轮确定采用的方案

1. 默认简洁编辑，详细字段按需展开；不删除已有角色信息。
2. 添加角色有四个入口：搜角色卡、导入 PNG/JSON、粘贴资料、自己写。
3. 搜索和解析阶段只产生候选；用户点击“确认导入”才创建或更新正式角色。
4. 兼容酒馆卡的数据交换格式，不要求用户安装或启动 SillyTavern。
5. 外貌分为稳定辨识特征、命名造型、参考图；活动内再设置当场服装、姿态和场景。
6. 卡面图片默认是封面候选；用户明确选定后才能成为生图参考。
7. 公共角色发布版本与活动人物快照保持独立；修改角色库不自动改写旧活动。
8. AI 整理、识图和试演均先给候选结果，采用后才改变人设。
9. 复用公共模型配置、Generation、Artifact、工作流分配及活动生图溯源。
10. 首版实现可靠的单角色外观应用；多人多参考图按工作流能力开放，不宣称任意模型均支持。

### 1.2 必须完成的能力

- 完整 SillyTavern 聊天前端、世界书触发引擎、宏语言或插件运行时。
- CHARX 压缩包及所有 V3 多媒体资源的完整兼容；首版识别并明确提示。
- 全网聚合爬虫、角色卡市场账号同步、自动发布卡片。
- 自动下载模型、安装自定义节点、训练角色 LoRA。
- 所有云图像供应商的适配，以及任意多人合照的身份一致性保证。
- 视频生成模型接入或 HyperFrames 渲染功能重写。

以上排除项不影响现有活动视频工程导出；不要借角色库整改扩展为全面重构。

## 3. 页面与使用流程

### 3.1 角色库首页

保留“我的角色”的本地搜索，提供清楚的“添加角色”主按钮。在线结果出现在添加角色流程中，不混入本地列表造成“已经导入”的错觉。

角色卡显示：头像、名字、作品、一句话简介、方案名称、是否有可用外观、最近修改。来源详情和技术信息收起。首版过滤只保留作品、标签、最近使用；不要引入评分仪表盘或几十个筛选项。

### 3.2 添加角色流程

四个入口共用最后的候选预览和确认保存流程：

- **搜角色卡**：关键词 → 来源搜索结果 → 卡片详情 → 解析预览 → 确认导入。
- **导入文件**：拖放 PNG/JSON → 解析预览 → 确认导入。
- **粘贴资料**：识别已支持卡网址、普通页面或文字 → 提取/整理候选 → 确认保存。
- **自己写**：名字 + 描述 → 直接保存；AI 补充为可选按钮。

从活动选人窗口进入时，保留活动上下文。保存成功后返回原活动并加入服务端创建的人物快照，不要求用户再搜索一遍角色。导入失败或取消时，活动原有内容保持有效。

### 3.3 默认简洁编辑

常驻字段：名字、作品、头像。正文分三个区：

1. 人设：一个自然语言编辑区，显示/编辑 `identity`；一句话摘要 `summary` 可选。
2. 说话方式：语气与示例，显示/编辑 `speech.tone` 和专门的对话示例结构。
3. 外观：辨识特征、当前默认造型、参考图。外貌细项放“展开细节”。

详细模式继续支持背景、性格、喜恶、关系、边界和原卡信息。简洁页可显示“另有 N 项详细设定”，避免用户以为只剩页面里的三段内容。

**不新增一份自动与全部详细字段双向同步的巨大自由文本。** 简洁编辑明确更新其字段；AI 将段落拆解为其他字段时，显示逐字段差异再采用。切换模式不触发模型、不写库、不重新归一化整份人设。

自动保存写草稿；“保存并使用”先保存，再显式发布版本并加入活动。按钮旁说明“将使用当前内容创建角色版本”，一个操作完成，不额外弹出纯确认窗口。详情页的“保存”可以只存草稿，版本历史位于更多菜单。

### 3.4 导入预览

预览至少包含：卡面、名称、作品候选、作者、来源链接、卡作者版本、原始描述、说话示例、原卡场景和开场白、世界书条目数量、拟导入字段及兼容说明。

默认主要显示“导入后的人设”，可切换“原卡内容”。原文只读；编辑候选不会修改原卡。用户可选择封面、启用的外观参考、是否保留原场景作为本角色设定。

若卡片实际是“原神 RPG 世界”或多人场景卡，显示“场景卡候选”。用户可以保留为自定义角色素材，但不自动将所有登场角色拆成若干官方人设，也不伪装成单一角色。

重复卡提供“打开已有角色”“新建另一种演绎”“比较并更新草稿”。默认不覆盖；同名不等于同一角色。更新时需要基于用户实际看到的旧版本进行条件提交。

### 3.5 轻量试演

预设三种：收到生日邀请、群里有人迟到、为合照写朋友圈配文；支持自定义一句场景。一次默认一个短输出，可再次生成。

试演使用与活动一致的人设编译规则，带具体草稿哈希、编译器版本、模型配置快照；不会进入活动内容或影响正式版本。允许“语气太正式”“口头禅太多”等反馈，返回修改建议并展示差异，不自动改角色。

未配置文本模型时，仍然可搜索、解析、手动编辑和导入；仅试演/AI 整理显示配置入口。

## 4. 在线来源策略与最小真实接入

### 4.1 名称和事实边界

界面名称建议为“搜索酒馆角色卡”，说明兼容 SillyTavern 常见卡格式。SillyTavern 提供角色管理和导入，并非本计划可以假设存在的统一官方卡商店。[SillyTavern 官方角色文档](https://docs.sillytavern.app/usage/characters/)

| 来源 | 本轮查询依据 | 实施优先级与边界 |
| --- | --- | --- |
| Chub | 存在 [公开 API 文档入口](https://gateway.chub.ai/docs)；本轮网页工具不能直接读取其完整接口定义 | 第一候选。先验证实际搜索、详情、下载协议、认证与限制，再决定上线适配 |
| Character Tavern | [目录页](https://character-tavern.com/search/cards)可读取，有搜索入口和角色目录 | 第二候选。目录可访问不等于已有稳定公开 API；先核查文档或允许的访问方式 |
| Bangumi | 有 [API 文档](https://bangumi.github.io/api/) | 后续身份/作品资料来源，不能用其人物搜索代替角色卡搜索验收 |
| HoYoWiki、原神 BWIKI、萌娘百科 | 可用作用户指定的资料线索 | 首版提供资料网址/粘贴入口；未验证正文适配的网站不显示“已接入” |

原神外观参考可以由用户从 [HoYoWiki](https://wiki.hoyolab.com/pc/genshin/home) 等资料入口寻找并上传。保存具体图片出处，不将所有社区内容标为官方资料。

### 4.2 接入验证任务必须先做

建立 `docs/development/reviews/character-source-provider-spike.md`，逐项记录：

1. 文档/接口依据、核查日期、访问方式、是否需要用户配置密钥。
2. 一个中文名字和一个英文名字的真实查询；默认不假设翻译或别名检索一定有效。
3. 搜索结果是否有稳定 ID、作者、封面、详情地址、下一页。
4. 对同一个结果获取详情与可解析原卡，核对名字和作者一致。
5. 下载是否重定向，图片/JSON 是否保留实际卡定义。
6. 429、401/403、空结果、超时的实际或模拟响应处理。
7. 保存去敏后的响应形状作为契约样例；不将密钥或大批第三方卡片提交仓库。

优先完成 Chub；若其当前协议不适合接入，再选择第二来源。至少一个来源通过真实闭环才能签收 R03。若两个都受外部条件阻塞，交付其他模块及准确阻塞报告，不能用搜索引擎摘要冒充站内搜索。

### 4.3 适配器契约

下列是**项目内部建议接口**，不是第三方已确认的 URL 或 SDK：

```ts
interface CharacterCardProvider {
  id: string;
  capabilities: {
    search: boolean;
    detail: boolean;
    download: boolean;
    importUrl: boolean;
  };
  search(input: {
    query: string;
    cursor?: string;
    limit: number;
    signal: AbortSignal;
  }): Promise<CardSearchPage>;
  getDetail(externalId: string, signal: AbortSignal): Promise<CardRemoteDetail>;
  download(externalId: string, signal: AbortSignal): Promise<CardDownload>;
  parseSupportedUrl(url: string): { externalId: string } | null;
}
```

统一结果包含 providerId、externalId、name、author、summary、sourceUrl、thumbnail、tags、language、remoteUpdatedAt、formatHint。第三方缺失字段置空，不由模型补成“检索结果”；卡作者版本与本地角色整数版本分别保存。

首版默认单来源，可在下拉框切换已启用来源。每个来源独立分页，cursor 不混用。搜索防抖约 300ms，取消前一个请求并拒绝迟到结果覆盖新关键词。重复结果按 providerId + externalId 去重，不按名字。

缓存建议：查询结果 5 分钟、详情 15 分钟；导入时以实际下载的原卡建立快照，不能拿过期摘要代替原卡。单次调用建议 10 秒、下载 30 秒超时，可配置并展示重试。不要预下载整页所有原卡或无限轮询。

### 4.4 获取失败的界面

区分无结果、站点暂不可用、被限流、需要认证、格式不可解析。提供保留关键词的重试和手动文件导入；外部网站按钮明确写“去网站查看”。

社区分级按来源提供的数据展示；缺失则显示未知。已有筛选选项按用户选择传递，不声称所有来源的标签一致可靠。

## 5. 角色卡解析与活动适配规则

### 5.1 文件范围

| 类型 | 本轮支持级别 |
| --- | --- |
| 旧 V1 JSON | 识别核心字段，转为统一候选 |
| V2 JSON | 解析核心与扩展字段，显示活动适配情况 |
| 带 `chara` 数据的 PNG | 从原始字节解析角色元数据，再生成预览图 |
| V3 JSON、带 `ccv3` 数据的 PNG | 支持基础人设映射，保留其他内容，报告未启用项 |
| 普通 PNG/JPEG/WebP | 作为外观/头像图片，不宣称含角色定义 |
| CHARX、APNG 等未验证格式 | 识别并解释当前支持范围，不尝试不受限解包 |

按实际版本校验，不因存在 `data` 就认定是 V2。PNG 同时存在有效 V3 与兼容 V2 时优先 V3；V3 数据损坏但 V2 有效时允许明确选择降级解析，并显示原因。先提取元数据再裁剪/转码，防止头像处理把角色信息抹掉。[V3 规范](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)

### 5.2 映射规则

| 卡字段 | 本地处理 | 默认进入活动运行提示吗 |
| --- | --- | --- |
| name | displayName | 是 |
| description | identity，原文保留；summary 只做明确的简短摘要 | 是，按上下文预算 |
| personality | personality；保留原始段落映射，避免强行按标点猜字段 | 是 |
| mes_example | 专门保存对话块和角色占位符；兼容映射到 speech 时保持块边界 | 选取适量示例 |
| scenario | 原卡场景归档；用户选择后才写入长期设定或活动素材 | 默认否 |
| first_mes / alternate_greetings | 开场素材归档，可预览 | 默认否 |
| creator / creator_notes / tags / character_version | 作者和来源元数据；tags 可选择导入 | 作者备注否 |
| system_prompt / post_history_instructions | 原样归档、标注未作为本应用系统指令执行 | 默认否 |
| character_book | 保留条目和设置、显示条目数量及未启用状态 | 默认否 |
| extensions / 未知字段 | 保留结构和原文件，不执行脚本、HTML、工具请求 | 否 |

V2 规范区分作者备注和提示词字段。本应用采用“数据导入与活动适配”，不会完整复刻酒馆运行时对系统提示、世界书和宏的默认行为，界面必须明确这一兼容边界。[V2 规范](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md)

识别 `{{char}}`、`{{user}}`、`<START>` 等常见示例标记，但只实现有测试的最小替换规则。活动没有确定 `user` 对应对象时保留或显式提示，不盲目替换成活动创建者。未知宏作为文字保留，不执行表达式。

### 5.3 可选 AI 适配

解析成功后才能提供“整理为活动人设”。模型输入为明确圈定的数据字段，输出 schema 校验的候选 patch 与说明。模型不直接写正式草稿，不擅自推定作品、官方出处、未记载外貌或人际关系。

长卡超出模型预算时说明参与整理的片段和省略内容；原始保存不可随模型截断。用户可不调用模型，直接采用确定性映射结果。

导出分为“下载导入时原卡”和“导出当前编辑后的兼容 JSON”。前者保持原始字节；后者说明本地字段映射与无法表达的变化。不要覆盖原卡归档来制造无损往返的假象。

## 6. 外貌怎样获取：产品与数据方案

### 6.1 外观不是角色名字自动附带的数据

酒馆卡重点在扮演设定，可能包含外貌描述和一张封面，但不保证有完整、准确、适合生图的视觉资料。采用以下四条渠道，合并为候选后由用户选择：

| 获取渠道 | 适合获得什么 | 如何使用 |
| --- | --- | --- |
| 角色卡描述 | 发色、服装、配饰等文字线索 | 提取外貌候选并定位原文字段；没写的保持未知 |
| 角色卡封面 | 一张方便开始的形象图 | 先作为封面候选；用户勾选“用作生图参考”后才启用 |
| 用户上传设定图、游戏截图、立绘或其他参考 | 实际可见的脸部、体型、服装、配色 | 保存出处与原文件；选择角色、造型和参考用途 |
| 多模态模型辅助识图 | 将可见细节整理成可编辑文字 | 生成候选、证据及不确定项；确认采用后写入外貌 |

没有参考图也可以使用文生图，但只用名字依赖图像模型自己的知识，表现会随模型变化。对于指定二次元人物，推荐补充一张清晰立绘，必要时再加面部图和本次服装图。

没有既定视觉形象的原创角色，可以先依据文字生成设计候选，用户选定后作为自己的参考图。标记为“AI 设计”，不能回写成“资料证实的官方外貌”。

### 6.2 外观分层

| 层 | 示例 | 保存位置 |
| --- | --- | --- |
| 稳定辨识特征 | 发型、发色、眼睛、明显配饰或印记 | 角色外观档案 |
| 命名造型 | 默认造型、某剧情时期、另一种形态 | 角色外观方案，发布时冻结 |
| 当场服装 | 生日会礼服、围裙、运动装 | 活动人物快照/覆盖项 |
| 姿态与场景 | 切蛋糕、看镜头、站在舞台左侧 | 活动阶段、媒体槽或镜头说明 |
| 画面风格 | 动画截图、水彩、手机照片感 | 活动生图配置或单次配方 |

不把卡面画风强行变成角色身份，不用本次服装覆盖库中默认造型。稳定特征和造型都允许用户定义，原作向、同人改编和原创需要可区分。

普通界面只展示“外貌描述 + 默认造型 + 参考图”；结构化细节和模型参数放高级区。

### 6.3 参考图的信息

每张图保存：referenceId、asset/artifact 关联、内容哈希、尺寸、来源页、原下载地址（可空）、作者/说明、所属角色、造型、用户备注、启用状态，以及用途。

用途最少区分：

- `avatar`：聊天头像，主要服务展示。
- `identity`：人物辨识参考，脸部/全身可用子标签区分。
- `outfit`：服装参考。
- `pose`：姿态/构图参考。
- `style`：画风参考。
- `init_image`：普通图生图的起始画面。

一张图可以有多个候选用途，但具体一次任务必须选择明确绑定。卡面可能是多人图、裁剪图、文字封面；允许选取主体区域，保存原图及裁剪变换，不把裁剪结果冒充原图。

首版管理界面允许多图，单次执行数量由工作流能力决定。推荐用户先准备 1–3 张清晰参考，这是使用建议，不是系统硬上限或一致性保证。

### 6.4 识图候选流程

选择参考图 → 选择识别对象/区域（必要时）→ 调用已配置多模态模型 → 外貌字段候选 → 对照原图修改 → 选择采用。

建议输出：description、hair、eyes、build、accessories、observedOutfit、unknowns、conflicts、evidence。每个候选记录图片 hash、区域、模型配置/模型名称、提示词快照、生成时间与结果原文。

规则：

1. 只描述图片可见信息。脸部头像不能推断完整鞋子、背部饰品或身高数值。
2. 不根据图片猜测身份、剧情时期或精确年龄；原图已有名字也只是候选线索。
3. 遮挡、低清、左右眼和镜像关系不确定时明确标记；左右以角色自身为参照。
4. 文字与图片冲突时展示两个候选，不按来源顺序静默覆盖。
5. 模型不可用时仍可手写外貌与选参考图；不能用纯文本模型假装已看图。
6. 用户采用某字段只更新该字段，同时保留先前值、来源和本次修改记录。

### 6.5 不同图像能力的实际作用

| 路径 | 本项目怎样传入 | 能力边界 |
| --- | --- | --- |
| 文生图 | 外貌文字 + 当前服装 + 场景动作 + 风格 | 名字或文字提示不保证稳定复现角色 |
| 普通图生图 | 起始图 + 正向/可用的负向提示 + 工作流参数 | 起始图会影响画面整体；不能将它等同于专用身份参考 |
| 身份/风格参考工作流 | 按工作流声明把参考图绑定到对应输入 | 需要实际模型和节点支持；未配置时不显示为可用 |
| 已配置角色 LoRA | 模型兼容的 LoRA 及显式触发词、权重 | 作为后续高级增强；不自动联网下载或训练 |
| 多人图片 | 角色分组的文字、参考图、位置或区域 | 必须有真实多角色控制支持；普通合照容易串脸、串衣服 |

ComfyUI 官方图生图例子以参考图作为额外输入，`denoise` 会影响与输入画面的差异；这类工作流本身不是人物身份锁定系统。[ComfyUI 图生图文档](https://docs.comfy.org/tutorials/basic/image-to-image)

LoRA 能作为工作流中的模型适配层，但具体文件、基础模型及加载设置必须匹配。首版可保留配置扩展点，后续按真实环境验证。[ComfyUI LoRA 文档](https://docs.comfy.org/tutorials/basic/lora)

## 7. 数据模型与存储设计

优先扩展现有角色表和版本表，不新建平行的完整角色主表。以下为建议实体，开发者可适度合并表，但必须保持语义和验收能力。

### 7.1 必要实体

| 实体 | 建议字段/责任 |
| --- | --- |
| 角色草稿扩展 | draftRevision/ETag、默认外观方案 ID、方案名称；沿用 CharacterDraft 主体 |
| 外部来源快照 | providerId、externalId、sourceUrl、作者、远端版本/时间、fetchedAt、payloadHash、原始文件关联、解析器版本、格式、原始结构 |
| 导入会话 | id、当前操作者作用域、状态、expiresAt、sourceSnapshot、previewRevision、previewHash、候选、兼容报告、目标角色、baseDraftRevision、commitResult |
| 字段来源 | fieldPath、valueHash、来源快照及原字段指针/图片证据、类型、派生关系、确认状态 |
| 外观方案 | id、characterId、label、稳定特征、造型服装、referenceIds；可变草稿在发布时整体冻结 |
| 视觉参考 | id、媒体关联、hash、用途、造型、来源、裁剪变换、启用状态 |
| AI 候选任务 | 所属角色/导入会话、输入哈希、输出、模型/提示词快照、状态；可复用合适的公共任务能力 |
| 角色发布版本扩展 | 冻结人设、外观、参考图描述、来源映射、编译器版本及关系 |

字段来源状态建议：`source_extract`、`card_author`、`user_edit`、`ai_inferred`、`image_observed`、`legacy_unknown`。是否“官方”另作为证据属性，不因为来自某个域名就自动判定。

字段 JSON Pointer 统一，例如 `/appearance/hair`。数组采用稳定条目 ID 或将整个数组作为来源块，不能只存会随排序变化的下标。来源映射允许一对多；模型改写只能标块级派生，不能伪装逐字证据。

### 7.2 版本原则

- 角色 ID 表示一份长期演绎档案；同名不同作者/平行设定可创建不同角色 ID，并通过可选 family/identity 关联。
- 本地整数 version 表示这份档案的发布修订；不与作者的字符串版本混用。
- 同一角色的视觉造型有独立稳定 ID，发布版本冻结其具体内容，不能只保存“当前造型 ID”。
- 保存草稿使用条件版本；过期提交返回冲突，允许查看差异，不能最后写入者静默覆盖。
- 已有活动不被角色库更新、来源重抓或参考图替换自动修改。
- 对没有已发布版本的角色，“保存并使用”创建版本后引用；不得写死版本 1 或伪造 sourceVersion。
- 历史活动有缺失/不可信 sourceVersion 时保留其原有人设内容，标记来源版本未知，不倒推绑定最新版。

### 7.3 原始归档和资产

导入原卡保持原始字节、hash 和解析数据。暂存数据和正式归档分开管理；确认导入时建立正式引用，取消后按 TTL 清理暂存。初始建议 TTL 24 小时。

图片统一使用公共媒体生命周期。现有 `character_assets` 不能立即废弃：增加 artifact 映射或迁移桥接，保留旧头像访问路由。引用模型须覆盖角色草稿、角色版本、活动版本、配方、任务和导出。

同一文件可以在底层按 hash 去重，但所有权、引用和使用记录不能因字节相同而混为一条业务记录。删除角色也不能清除仍被活动历史引用的媒体。

## 8. 导入状态机与内部 API

### 8.1 状态机

建议状态：`fetching → parsing → ready → committing → committed`；失败为 `failed`，取消为 `cancelled`，过期为 `expired`。

本地文件从 parsing 开始；搜索结果和远端详情本身不是正式导入。AI 整理/识图在 ready 状态产生候选更新，不自动进入 committing。

每次修改候选产生新的 previewRevision/hash。确认提交携带最近预览版本、目标行为、新建/更新目标、baseDraftRevision 和幂等键。服务器提交的是已暂存的那一份原卡与候选，不在确认后重新下载可能已变化的内容。

同一幂等键重试返回同一导入结果；同一键不同请求返回冲突。提交成功后会话转只读。过期会话不能提交，要重新准备预览。不要在用户只看预览时创建空角色占位。

### 8.2 建议新增接口

以下路径以现有管理员角色 API 为基础设计，实施前确认路由代理前缀；它们不是第三方 API。

| 方法与路径 | 请求/结果责任 |
| --- | --- |
| `GET /api/admin/characters/card-providers` | 来源能力、启用状态、缺少配置说明，不泄露密钥 |
| `GET /api/admin/characters/card-search` | providerId、q、cursor、limit；返回真实候选及下一页 |
| `GET /api/admin/characters/card-detail` | providerId + externalId；返回可预览详情，不创建角色 |
| `POST /api/admin/characters/import-sessions` | 文件、支持的网址、来源 ID 或文字，类型明确且互斥 |
| `GET /api/admin/characters/import-sessions/:id` | 状态、候选、原卡、映射、外观和兼容报告 |
| `PATCH /api/admin/characters/import-sessions/:id` | 条件更新候选及采用项，返回新预览哈希 |
| `POST /api/admin/characters/import-sessions/:id/commit` | 原子确认新建/更新，返回角色 ID 和版本状态 |
| `DELETE /api/admin/characters/import-sessions/:id` | 取消未提交会话并安排清理 |
| `POST /api/admin/characters/:id/auditions` | 明确草稿版本/候选哈希与场景，返回试演结果或任务 |
| `POST /api/admin/characters/:id/visual-references` | 上传或采用暂存图片，保存用途及来源 |
| `POST /api/admin/characters/:id/appearance-extractions` | 明确图片和草稿版本，创建识图候选任务 |
| `POST /api/admin/characters/:id/appearance-extractions/:taskId/apply` | 选择字段、校验版本、采用候选 |
| `POST /api/v1/admin/activities/:id/actors/from-character` | 角色 ID、实际版本、造型、活动覆盖，服务端返回/提交快照 |

尽量复用现有发布、保存、媒体查询和任务查询接口，不因为表中列出了能力就重复新增同义端点。动态 `/:id` 与静态 `card-search` 等路由的解析要有测试。

旧 `import-tavern` 若必须保留，作为“客户端已明确提交导入”的兼容入口复用同一解析/提交实现；新版 UI 不直接调用它跳过预览。不能维护两套字段映射。

### 8.3 提交事务与文件失败

正式写入需覆盖：角色草稿、来源归档、字段映射、参考图关联和会话结果。更新角色时在事务内检查 baseDraftRevision。

文件先写受控暂存并校验，进入可用状态后再在数据库事务中建立正式引用；失败采用补偿与可重试清理。进程在文件准备后或事务提交后崩溃，重试不得产生重复角色、丢失原图或留下永久不可清理的悬空记录。

## 9. 活动人物快照与跨应用图片接入

### 9.1 统一服务端快照构建

抽出 `buildActorSnapshotFromCharacterVersion`，所有选人入口和创建活动入口共用。浏览器只提交角色、版本、造型、允许的活动覆盖；人物原始设定、版本和引用由服务端加载。

确定统一 Actor persona 表示。建议保留结构化 CharacterDraft 作为可追溯原件，提供专门的活动运行投影和视觉投影，不把同一个 `persona.appearance` 同时定义为对象和字符串。

必须有旧数据兼容读取器：

- appearance 为字符串：保留为 description。
- appearance 为对象：完整读取 description/hair/eyes/build/outfits/accessories。
- 缺失外貌：保持空并提示可补充，不用说话语气或默认“热情友好”补齐外貌。
- 未知字段保留在原始快照中；运行投影只选择支持字段。

修正错误表名 `character_revisions`，使用真实 `character_versions`；版本读取失败必须明确处理，不能悄悄回退最新草稿制造错误来源。

### 9.2 头像、参考图和 asset key 分离

`avatarUrl` 是展示地址，`artifactId` 是媒体记录，`assetKey` 是活动包内的资产键，三者不能互代。服务端创建有效资产登记后再返回键；UI 通过资产解析器取 URL，不能 `<img src={assetKey}>` 直接猜路径。

历史 URL 型字段先识别是否为本系统已登记媒体，能验证才转入；无法解析时保留旧展示兼容和“尚未纳入活动资产”的状态，不伪造 assetKey。不批量下载来源不明的任意 URL。

### 9.3 跨应用媒体的建议实现

保持 Generation 的同应用输入检查。新增受控的“将角色参考图转入活动”领域服务：

1. 验证操作者可访问角色版本和目标活动。
2. 从该版本中查找 referenceId，不接受任意磁盘路径或客户端自报 ownerAppId。
3. 验证原图 ready、内容哈希和允许的媒体类型。
4. 为目标应用创建它拥有的 artifact，或使用现有明确支持所有权转入的 API；底层可去重，首版可安全复制文件。
5. 建立活动资产键、来源角色/版本/引用 ID/原图 hash、持久引用和转入记录。
6. 生图提交使用目标应用的 artifactId；导出使用活动包内相对路径。

幂等键至少涵盖目标活动、来源引用和内容 hash。转入必须限制范围，不能成为任意应用读取其他资产的通道。已有只读 grant 不自动视为符合 Generation 输入条件。

## 10. 复用公共模型与 ComfyUI 服务

### 10.1 服务职责

| 角色库负责 | 公共服务负责 | 活动模块负责 |
| --- | --- | --- |
| 人设、外貌、来源、候选、试演上下文 | 模型配置、凭证、能力、请求执行、任务、工作流、产物 | 活动覆盖、快照、媒体配方、内容回溯、活动导出 |

UI 不直连 ComfyUI 或供应商，不保存第二份密钥。角色库的图片请求也使用公共 Generation，不另建私有轮询器或专属下载路径。

### 10.2 文本与识图模型

为 `characters` 配置 text 与 multimodal 角色，复用 `resolveAssignedLlmProfile` 等公共能力。消除 `generateDraft` 对 `linshe` 的固定绑定。

兼容旧用户：迁移时可将现有配置引用作为角色库初始绑定，记录迁移来源；只复用 profile ID，不复制密钥，不要求启动邻舍。配置缺失时提供准确入口，不自动改其他应用的绑定。

识图必须发送服务端读取的、经过权限和尺寸校验的图片内容，采用所选提供方实际支持的多模态消息格式。仅有 `multimodal` 配置名还不算支持：以能力校验与一次真实图像请求验证。敏感凭证、带鉴权远程 URL 不写入来源或导出文件。

### 10.3 生图用途与工作流

保留现有 `character-avatar` 用途；活动复用 `activity_image_text`、`activity_image_edit` 等既有分配。若需要专门的角色外观试图用途，可以新增明确的 purpose，但不能绕过同一执行基础设施。

外貌管理页的“试生成一张”返回候选产物；用户选择“设为头像”或“加入参考图”，两个动作分开。生成产物加入参考图时建立派生关系，防止它的文字解释被误标成外部证据。

工作流输入声明至少能表达：支持文生图/编辑、接受的 inputKey、媒体类型、数量、最大尺寸/字节、required，以及输入语义。语义包括 init_image、identity、outfit、pose、style；未声明的用途不能仅凭 LoadImage 节点存在就判定支持。

前端预检展示：这次实际使用的外貌、服装、参考图及用途、工作流/模型、可调参数。不支持的参考用途提示选择兼容工作流或改为可用模式，不能静默丢图后显示“已使用人物参考”。

首版单参考图必须实际进入执行计划与上传绑定。多图工作流如果当前输入映射只接受单值，必须先扩展有序输入/独立 inputKey 和上传逻辑；不能仅增加 maxCount 就声称支持多图。

### 10.4 “模型生图”与云供应商的处理

ComfyUI 本身运行图像模型；角色视觉档案不绑定某一个模型品牌。若用户使用独立图像 API，采用同一视觉档案，经过对应供应商适配器投影成它支持的 prompt、images、size 等实际参数。

本轮必须明确列出哪些引擎在当前项目确实可执行。已有 cloud 枚举但未实现供应商协议时，不能把它当成可用功能。默认先交付现有 ComfyUI 文生图/图生图闭环；独立云 API 作为单独扩展任务，选定一家后完成能力、请求、错误、费用提示、产物下载和快照测试。

保留字段不等于发送字段：部分模型没有负向提示、seed、strength 或 LoRA 参数。执行快照必须区分“用户想要的设置”和“实际发送/服务端返回的设置”，不支持的参数不能伪造为生效。

## 11. 提示词、参考图与修改入口的溯源

### 11.1 生成链路

```text
原卡字段 / 用户文字 / 参考图
    → 解析、AI 候选、用户采用记录
    → 角色草稿及外观方案
    → 角色发布版本
    → 活动人物快照 + 本场服装/造型选择
    → 生图提示块与参考图绑定
    → 冻结配方、工作流和执行计划
    → 实际请求、产物、导出清单
```

视觉编译器需输出 prompt blocks + source refs，复用当前活动 sourceRef 机制。扩展角色库来源引用时，明确 ownerKind/entityKind、版本及字段路径，不能把角色库来源 ID 塞进含义不同的活动 revision 字段。

### 11.2 每次图片尝试需要的记录

- 角色 ID、真实发布版本、活动人物 ID、外观方案快照和本场覆盖。
- 提示词原始块、用户修改块、最终实际发送文本、语言转换及编译器版本。
- 参考图 hash、角色归属、用途、顺序/inputKey、裁剪/缩放等变换。
- 工作流 ID/版本/hash、实际节点图、模型标识、可获得的模型文件 hash、实际参数。
- 引擎类型、任务 ID、请求时间、结果、产物 hash；随机种子可获得时记录实际值。
- 原始资料与 AI 派生链；数据不存在时标未知，不事后补写成当时事实。

### 11.3 点击来源后的动作

| 用户点击的内容 | 定位位置 | 修改后的效果 |
| --- | --- | --- |
| 本次外貌文字 | 当前活动人物快照字段 | 生成新的活动内容修订，重新编译受影响图片配方 |
| 本次服装 | 本场人物服装覆盖 | 只影响当前活动的新生成 |
| 当前参考图 | 当前活动人物参考设置 | 新的引用选择/配方，不改旧任务 |
| 公共角色出处 | 对应角色发布版本的只读字段，再提供“编辑当前草稿” | 发布新版本后可选择比较并更新本场人物 |
| 原卡文字或来源图片 | 来源归档及对应字段/区域 | 原始证据只读；用修正值或新来源覆盖下一版 |

入口可以使用页面路由参数 `characterId/version/fieldPath`、`activityId/actorId/fieldPath`，或等价的类型化定位协议。必须实现滚动定位与高亮，不能只跳到角色库首页。

从旧图片进入时先展示当时值，再展示当前值。回到活动后只标记受影响的图片为“设置已变化，可重新生成”，用户选择后才创建任务；不要因为改了一项人设自动重跑整个活动或产生费用。

### 11.4 冲突与优先级

稳定特征来自人物快照；当场服装覆盖所选造型的服装部分；镜头动作来自当前内容；风格来自生图配置；单次手动提示覆盖块必须显式显示并保留来源。

冲突检测提醒“参考图服装与本场礼服不同”等具体问题，允许用户选择优先依据。不能简单把所有文本拼接后声称已解决冲突。翻译或模型扩写记录派生关系，不保证每个生成 token 都能精确映射到原字段。

## 12. 导出、历史和旧数据迁移

### 12.1 活动导出

在现有导出 manifest 的版本化扩展中保存：使用的人物快照、外观资料、prompt provenance、参考图和生成媒体的包内路径及 hash。导出历史来源不依赖之后再次访问原网站。

导出至少打包实际用于本活动的参考图与产物；完整原卡原文件可提供“附带原始资料”选项，默认不把未使用的整套素材或不相关世界书塞进视频工程。作者、来源链接和说明保留；本地路径、鉴权 token、密钥不进入压缩包。

HyperFrames 工程保持既有接口；新增媒体使用包内相对路径，不引用管理员 API、临时签名 URL 或角色库当前头像 URL。换一台机器、断开原网站后仍可加载活动实际使用的媒体。

### 12.2 迁移策略

1. 先做数据库与关联文件备份，读取当前迁移编号，再追加新迁移。
2. 旧角色保持 ID、slug、版本和关系；新增来源状态为 legacy_unknown，不编造历史证据。
3. 旧 character_assets 逐项桥接到 Artifact；可重复执行，记录成功/失败和 hash 校验结果。
4. 已发布版本不根据现有草稿重建；新字段可在兼容投影中给默认值或显式未知。
5. 字符串/对象 appearance 通过兼容读取处理，迁移不能破坏历史内容 hash 或历史导出。
6. 旧活动错误的 sourceVersion 不能通过盲目替换为 latest_version 修复，保留快照事实并提示来源待核对。
7. 在副本数据库验证升级、重启、导出和文件缺失情况；不以重置数据库代替迁移。

回退首先关闭新搜索/导入入口或回退业务代码；数据库已升级后不要运行不兼容旧代码。需要整体回退时使用匹配的数据库+文件备份，明确升级后新增数据的处理方式。

## 13. 输入与可靠性约束

这些约束放服务层，不转化成让用户反复确认的页面流程。

- 所有新接口沿用现有管理员认证/应用能力检查；导入会话绑定现有操作者作用域，不为本轮凭空搭建多租户系统。
- URL 导入走专用受控获取器：只允许 HTTP(S)，核查 DNS/IP 与每次重定向，阻止本机、内网、元数据地址和 DNS 重绑定绕过。不要把这些限制错误应用到用户主动配置的可信 ComfyUI 内网地址。
- 远端下载需要来源适配器或明确的用户网址输入；不要执行卡内任意资源 URL、脚本或工具指令。
- 初始可配置限制建议：JSON/解码角色数据 2 MiB、PNG/参考图 20 MiB、解码图片 40MP、重定向最多 3 次、JSON 深度 64；超过明确报错，不静默截断归档。
- 校验真实 MIME、文件签名、图片尺寸和 PNG chunk 边界；防止伪扩展名、超大元数据及解码膨胀。涉及压缩 chunk 时限制解压后大小。
- 文件名服务端生成，路径不能由卡片或原始文件名决定。卡片 HTML/Markdown 用安全渲染，不执行脚本或带事件属性的标签。
- 第三方失败、模型失败和本地校验失败有不同错误码；错误信息去除凭证，不把原始私密提示词写入普通日志。
- 缓存容量、暂存 TTL、任务超时和孤立文件清理有边界。重启后可恢复会话结果和任务关联。

## 16. 验收与测试矩阵

### 16.1 必要的自动化用例

| 编号 | 输入/操作 | 必须验证的结果 |
| --- | --- | --- |
| T01 | 只有名字和描述的新角色 | 能保存、发布、进入活动，版本真实 |
| T02 | 有关系/偏好/细项的旧角色，简洁页只改语气 | 未编辑字段和关系完全保留 |
| T03 | 两个窗口编辑同一草稿 | 后提交旧版本返回冲突，不覆盖新值 |
| T04 | V1、V2 JSON、V2 PNG、V3 JSON/PNG | 正确映射、头像正确、原始 hash 可核对 |
| T05 | 普通 PNG、损坏 chunk、超限数据、伪扩展名 | 明确错误或图片导入分支，不创建假角色 |
| T06 | 卡含作者备注、系统提示、世界书、未知扩展 | 归档保留；不偷偷进入活动系统协议 |
| T07 | 对话示例有多行、占位符、分段标记 | 不按行破坏对话语义；未知宏不执行 |
| T08 | 预览后取消、过期后提交 | 无正式角色；过期不能提交 |
| T09 | 同一个确认请求重发/提交后重启再重发 | 只产生一个角色或一次更新 |
| T10 | 远端原卡在预览后变化 | 确认使用原预览快照，不偷偷换内容 |
| T11 | 同名异作品、同 ID 同 hash、同 ID 新 hash | 不按名字误合并；分别提示重复或更新差异 |
| T12 | 搜索旧请求比新请求晚返回；分页；429 | 新结果不被覆盖，cursor 不混用，错误准确 |

| T18 | 角色资产转入活动、重复转入、越权 referenceId | 活动合法持有输入；幂等；越权被拒绝 |
| T19 | 修改角色库、删除库中原图、旧活动回放 | 历史快照与被引用图仍有效 |
| T20 | 从旧图片点提示词来源并修改 | 能定位当时字段，产生新修订，旧尝试不变 |
| T21 | 工作流只支持一张图或不支持某参数 | 预检阻止/明确处理，不默默丢弃或伪造生效 |
| T22 | 导出后移走本地服务/断开原网站 | 使用的头像、参考图、生成媒体和来源说明仍可解析 |
| T23 | 提交前后崩溃、文件写失败、重复清理 | 无重复角色、永久悬空引用和误删历史媒体 |
| T24 | 无模型配置或模型超时 | 搜索、手工编辑、文件导入可用，AI 候选不覆盖草稿 |

解析器 fixture 优先使用自建虚构人物，构造所需 PNG 元数据；真实第三方卡用于人工接入验证，不需要把整张卡提交到测试仓库。

### 16.2 必须单独报告的真实验收

1. **来源**：实际搜索一个二次元角色，打开卡预览，取消一次后再确认导入；记录来源 ID、卡 hash、结果角色 ID。
2. **编辑**：桌面与约 390px 宽度完成搜索、预览、导入、修改和加入活动；对比旧字段是否保留。
3. **识图**：用户提供一张允许使用的参考图，真实多模态模型返回可见细节；修改候选并采用。
4. **生图**：对同一个角色文生图一次、单图图生图一次，检查实际上传图 hash、节点输入、执行参数及产物。
5. **溯源**：从生成图点击外貌来源，修改本场服装并重新生成，核对旧图/旧版本仍存在。
6. **完整活动**：至少两个人物、两个阶段，包含群聊和朋友圈以及图像；打包后在不依赖原来源网站的环境读取。

对同角色跨图辨识度做人工观察记录，不用“请求成功”替代效果验收；但也不把一次好图描述为模型永久一致性保证。多人图能力单独标注，不能以单角色测试证明。

### 16.3 工程检查

按实际修改范围执行角色、活动、Generation 和迁移的定向测试，再运行项目当前有效的 typecheck、test、build、lint。现有根目录提供 `npm run typecheck`、`npm test`、`npm run build`、`npm run lint`；执行前核实脚本仍有效。

浏览器测试扩展 `tests/e2e/` 的现有模式。遵守执行环境工具/技能约束；若无法执行，明确列为待验收，不沿用旧版本通过记录。真实外部站点和 GPU 测试不放入每次离线单测的强制依赖。

## 17. 工作量、优先级与减少改动的方法

这是涉及数据完整性和媒体流转的中等偏大增量改造，不能只按“加一个搜索框”估算。

| 模块 | 相对工作量 | 主要不确定性 |
| --- | --- | --- |
| 简洁编辑、添加流程、试演 | 中 | 现有表单/自动保存兼容 |
| 卡解析、预览、确认和来源 | 中到大 | 长卡、扩展字段、重复更新 |
| 一个在线适配器 | 中，波动较大 | 真实 API、认证、限流、下载格式 |
| 外貌与多模态候选 | 中 | 多模态提供方实际能力 |
| 快照、资产转入和视觉溯源 | 大 | 已有版本/媒体兼容及执行输入语义 |
| 联调、迁移、导出回归 | 中到大 | 真实数据库、模型环境和历史资产 |

控制改动量的具体做法：

- 默认只上一家真实卡来源，不首发全网聚合。
- 原有详细表单继续复用；简洁模式是受控字段视图。
- 字段来源先做到可解释的字段/块级，不开发任意文本逐字标注编辑器。
- 参考图管理可多图，执行先把单图工作流做实。
- 复用现有来源/版本/任务/Artifact，不新建平行基础服务。
- 人物关系沿用现有手工管理，不在导入时自动补全整部作品关系网。
- 先保证活动现有导出仍可用，不顺带重写聊天记录播放器。

不在外部来源和模型环境尚未验证时给固定交付日期。完成 M0 后，按真实接口和现有测试负担估算每个里程碑工时。

## 18. 推荐的首个完整演练

以“原神主题生日活动”为例；具体角色设定以用户选取的卡和参考图为准。

1. 搜索角色名与作品，选择一张现成卡，核对作者演绎与自己需要的剧情时期。
2. 预览导入后的人设；保留语气，原卡开场剧情不用于生日活动。
3. 卡面仅设为头像；上传另选的清晰角色立绘作为 identity 候选。
4. 识图补出可见的发型/配饰，用户校正并保存默认造型。
5. 试演“收到生日邀请”的回复，调整过度夸张的口头禅，保存并使用。
6. 在活动内给角色设置生日会服装，新增第二名角色；两个阶段分别准备与庆祝。
7. 生成群聊/朋友圈预览；为一个图片槽先做单角色文生图，再用选定参考试图生图。
8. 如果服装不合预期，从图片来源直接定位本场服装，修改并产生新图片尝试。
9. 对比新旧图；保留满意版本，打包活动、媒体、人物外观和来源。

这一闭环同时验证本轮核心价值：取得角色容易、编辑简单、外貌有依据、失败可调整、历史不丢失。
