# 活动工作室：产品方案与开发计划

状态：初版可行性方案，尚未进入实现。用户随后明确最终产物以聊天/朋友圈记录及 HyperFrames 模拟设备录屏视频为主，最新架构与范围以 [聊天内容与视频方案修订](activity-chat-video-proposal.md) 为准。本文的独立活动、阶段编辑、内容版本与完整打包要求仍然有效；完整生活模拟与邻舍运行联动不再作为建议的第一版范围。

## 1. 产品目标与已确认需求

在 SthStart 中增加完整、独立的活动应用，用于生日会、聚会、旅行、节日庆典、舞台演出、探险等多角色活动。邻舍作为角色互动体验的参考与可选连接对象，新增业务尽量不进入邻舍子模块。

已确认：

- 每个活动独立进行，不共享其他活动的进行状态与记忆。
- 可以选择主题、参与角色和地点。
- 活动至少有两个阶段，支持新增、删除，各阶段可描述“谁做了什么”等内容。
- 可以完全不写阶段内容，由 AI 安排；也可以指定部分或全部阶段要求，让 AI 补全细节。
- AI 根据所选角色人设生成可预览内容。
- 群聊、朋友圈等内容需要查看历史、修改、重做及恢复。
- 可以打包导出整个活动的文本、图片、视频。

建议默认值（待选择）：

- 群聊、朋友圈由新应用完整呈现；邻舍原生发布放在可选连接层。
- 用户默认是导演，可通过明确切换身份作为参与者发言。
- 先生成全局方案，再逐阶段生成详细内容、确认和继续；另提供整场文字预览。
- 所有核心内容有版本，重做保留旧版；默认导出当前选定版本，可额外导出完整历史。

## 2. 可行性与边界

| 需求 | 可行性 | 必要条件 |
| --- | --- | --- |
| 独立活动、角色选择、阶段编辑 | 高 | 独立活动数据模型，角色采用固定版本快照 |
| AI 自主安排、按指定阶段补全 | 高 | 结构化输出、约束校验、预览与确认 |
| 人设一致的多角色文字互动 | 可行，但质量需迭代 | 人设、关系、说话风格、角色知情范围及当前阶段事实进入上下文 |
| 群聊、朋友圈跨阶段保持一致 | 可行 | 统一活动事实与顺序；帖子和评论引用已发生内容 |
| 回溯并保留原版本 | 高 | 不可变版本、状态检查点、后续内容依赖关系 |
| 大量图片且角色、服装、场景一致 | 可行，但不能保证每张合格 | 外观参考、镜头结构、重拍和选片；多角色同框专门验收 |
| 生成式视频 | 有条件可行 | 真实可用的视频模型/工作流和目标设备测试 |
| 文本、图片、视频完整打包 | 高 | 收集实际文件、固定导出快照、校验清单和离线阅读页 |
| 不改邻舍，同时强制写入其原生群聊/朋友圈并完整回溯 | 当前不满足 | 现有接口不足；应调整呈现位置或增加上游扩展接口 |

静态资料与基础服务可复用，活动执行引擎需要新增。不能把“已存在群聊接口”直接等同于“已有独立活动与版本系统”。

当前代码证据：

- `upstream/linshe/agent-core/src/routes/groups.js` 支持建群、改成员、发言和读取消息。
- `upstream/linshe/agent-core/src/services/groupRoundUndo.js` 撤回最后一轮群聊，并删除关联消息、摘要和部分图片；不是保留多个活动历史版本的恢复机制。
- `upstream/linshe/agent-core/src/routes/moments.js` 的生成接口主要接收角色 ID，不能按外部活动要求直接发布指定内容和媒体。
- `upstream/linshe/agent-core/src/services/unifiedStreamBus.js` 为内存广播，不提供活动级持久事件重放。
- `apps/service/src/characters.ts` 已有角色资料、关系和发布版本，可作为活动角色快照来源。
- Generation 已有任务、重试、事件和工作流快照；Artifact 已有媒体文件、授权和引用保护。
- `generation_context_links.context_type` 当前限制为 `character`、`narrative`，增加活动消费者时需要扩展映射方式，不能直接当成已有支持。
- `scripts/database.ts` 的备份明确只包含数据库元数据和引用；不能替代带全部媒体的活动导出。

## 3. 产品页面与使用流程

### 3.1 活动列表

创建、搜索、复制、归档活动，查看主题、封面、参与者、阶段进度、当前版本和生成状态。复制活动默认仅复制设定，不复制进行中的任务或活动记忆；可显式选择复制当前内容。

### 3.2 创建与设定

区分容易混淆的三个字段：

- 活动类型：生日会、旅行、演出或自定义，用于提供模板，不限制底层能力。
- 活动主题与目标：例如“海边的夏日庆典，轻松、有一点小惊喜”。
- 风格与规则：温馨、搞笑、悬疑；遵循原作设定或允许自由改编。

其他字段：标题、时间与地点、参与者、活动内角色职责、关系设定、用户身份、媒体偏好。地点既可手填，也可保存为可复用场地；每个阶段可覆盖地点。

角色卡来自公共角色库；自建/导入的人设同样可选，也可通过邻舍角色接口一次性导入静态人设快照。选择角色后固定人设与外观版本，不导入邻舍其他会话的运行记忆。参考资料注明来源和版本；AI 补充的同人设定与原始资料分开保存。

### 3.3 阶段编辑器

默认显示“阶段一”“阶段二”，支持改名、新增、删除、拖动排序、复制。

阶段字段：标题、参与角色、地点、内容要求、必须发生的事实、可自由发挥的部分、结束条件，以及可选照片/视频需求。普通界面以标题和内容文本为主，其他字段按需展开。

- 草稿允许内容为空；提交正式方案时至少有两个有效阶段。
- 完全自主：不填写阶段内容，AI 生成至少两个阶段并展示预览。
- 部分指定：保留已写内容和锁定要求，AI 补充空白阶段或细节。
- 严格执行：不更改已指定的阶段顺序和关键事实，只补充对白、动作、氛围与镜头。
- 用户写明“甲把礼物交给乙”，必须转成可校验约束，不能被生成内容反向覆盖。
- 若要求矛盾或超出当前参与者范围，显示具体冲突与可选修正；不擅自换角色。
- 删除/重排已生成阶段会创建新方案版本，旧内容留在历史；当前方案仍保持至少两个阶段。

### 3.4 AI 预览

支持两种深度：

1. 方案预览：全局梗概、阶段目标、具体行动、预期转折、示例对话、朋友圈构想、镜头清单。
2. 完整文字预览：实际可采用的阶段叙述、群聊、帖子和评论；图片视频先用镜头卡占位。

可编辑、锁定、单项重写、整阶段重写和比较版本。预览不自动进行大批媒体生成；如用户需要，可先生成少量试拍。

用户已确认的详细文字直接成为采用版本，不在“正式开始”时无故再次随机改写。方案级预览则保留锁定约束，后续详细生成在其范围内展开。

### 3.5 活动工作台

桌面：左侧阶段，中央时间线/群聊/朋友圈，右侧人物、当前事实与镜头。移动端用页签与抽屉呈现同一功能。

主要操作：生成下一段、生成本阶段、编辑、重新生成、采用版本、继续阶段、暂停、从此处重做、拍照、添加视频、导出。

导演指令和参与者发言分开输入、分开记录。导演安排可以影响生成约束，但不伪装成角色听到的一条聊天消息。

时间线、群聊、朋友圈是同一活动内容的不同视图。一次送礼可以关联对白、旁白、照片和后续帖子，避免四套互不关联的事实。

## 4. 活动隔离与角色状态

共享层只保存静态角色资料、只读背景资料、模型配置与受引用保护的媒体文件。

活动层固定角色资料快照，并独立保存关系、当前情绪、职责、服装、物品、知情信息、时间与地点。修改公共角色库不能追溯改变已有活动。若主动升级角色版本，应预览差异并创建活动新版本。

所有活动记录和任务使用 `activityId`；版本使用 `branchId/revisionId`；阶段使用稳定 `stageId`，显示顺序可变化。服务端每次访问都检查归属，不能只靠前端过滤。

生成上下文只包括：当前活动的角色快照、有效分支的已采用内容、当前阶段约束、相关事实和参考资料。未采用草稿、其他活动和被放弃的后续内容不得进入记忆检索。

角色私密信息与导演全知信息区分；角色默认只知道其在场或通过已发生消息获知的事情，防止提前泄露惊喜和后续剧情。

第一版优先使用阶段摘要与结构化事实构建上下文；活动变长后再补活动/分支隔离的向量检索，不先堆叠复杂长期记忆系统。

新应用可在邻舍未启动时正常创建与执行活动。若以后同步到邻舍，属于明确的外部发布操作；新应用回溯不自动承诺撤销邻舍已产生的记忆和互动。

## 5. AI 执行与内容一致性

执行链：读取约束 → 生成候选 → 校验 → 保存草稿 → 用户或自动规则采用 → 更新本分支状态 → 派生媒体任务。

逻辑职责包括活动规划、场景/角色对白生成、事实校验、阶段总结和镜头设计。不要求每个角色都运行一个长期驻留代理；第一版可由一次结构化阶段生成产出多角色内容，后续交互按轮追加。

建议内容类型：旁白、行动、群消息、朋友圈帖子、评论、图片镜头、视频镜头、用户发言。每条内容引用参与角色和阶段事实，使用故事时间与生成时间两个字段。

生成输出必须满足结构、角色引用、阶段顺序、必需事实和长度限制。AI 质量检查只能辅助发现人设偏离与矛盾，不能视为绝对保证；用户始终可以直接编辑与指定重写原因。

朋友圈从已采用事实中生成，不作为另一条独立剧情引擎。评论按知情范围和时间推进。若改写仅是语气润色，可以保留事实；若改变了行动和结果，则进入依赖更新流程。

自动模式也必须有轮数、内容量、图片数、视频时长和重试上限，防止无限续聊和无限生成。开始批次前展示预计产出数量；费用只在已配置可靠价格时估算，否则显示调用量和任务量。

## 6. 回溯与版本：第一版必须具备

不要把回溯实现成数据库删除或重新请求同一个 prompt。恢复旧版是读取已保存结果；重新生成是创建新的候选，同样的模型/seed 不保证得到完全相同结果。

| 操作 | 用户看到的行为 | 数据处理 |
| --- | --- | --- |
| 查看旧版 | 随时阅读并比较之前的文字和媒体 | 读取不可变版本 |
| 重写消息/帖子 | 给出新候选，可以采用或恢复 | 旧版本保留；改变事实时提示影响范围 |
| 重拍图片/重做视频 | 文本与剧情保持，替换选中的媒体候选 | 新媒体任务绑定原内容版本 |
| 重做整个阶段 | 保留旧阶段，产生新版 | 从阶段开始检查点生成 |
| 从某条消息继续重做 | 当前点之前保持，后续产生另一版本 | 第一版可限制为完整生成轮次边界，随后扩展任意消息边界 |
| 修改早期阶段 | 展示后续内容受影响，允许从此处重做 | 派生分支，不覆盖原结局 |
| 切回旧版 | 恢复旧版文字、媒体选片与活动记忆 | 切换分支/采用指针，不能只恢复 UI 文本 |

检查点应包含：有效阶段与内容序列、活动事实、角色状态、摘要及其来源、媒体选片。未来若引入向量检索，也必须随分支过滤，不能让旧摘要泄漏未来信息。

后续依赖采取保守规则：改动某阶段关键事实后，后续阶段默认标为“需复核”；镜头和帖子按其来源版本标记。系统可以建议局部更新，但不能承诺自动精确理解所有语义依赖。

已锁定的后续内容不自动覆盖。若新前文与锁定内容冲突，用户选择保留原分支、调整前文或解锁重做。

后台任务必须记录提交时的活动、分支和内容版本。用户回溯后，迟到结果留在原版本，不得覆盖当前版本。暂停或取消可能只停止本地跟踪，不能保证远端推理立刻停止；界面显示实际状态。

历史媒体保持引用保护，直到用户明确清理对应历史。删除一个版本不能误删其他版本仍使用的同一文件。

第一版 UI 使用“版本历史”和“从此处重做”，无需暴露复杂分支树，但底层必须支持分支关系。

## 7. 图片与视频

活动固定外观参考、服装、地点与道具。镜头包含角色列表、站位、动作、景别、画幅、视觉风格、来源事实及参考媒体。

按阶段和镜头生成、重拍、选片，避免文字未确定就批量生成昂贵媒体。采用照片可成为后续视频参考。视频任务需明确是照片剪辑成片还是生成式动作视频，两者分别显示。

第一版的数据、界面、存储和导出就支持视频，也支持上传已有视频。真实生成式视频按配置就绪后开放；没有可用模型时不伪装成已生成，也不让视频失败阻断整个活动。

保留模型、工作流版本、参数和来源图片用于追溯；不能声称这些信息足以精确再现第三方模型输出。

## 8. 完整打包与再导入

导出不能只保存图片链接或当前数据库。必须包含离线可用的媒体文件，并将所有展示路径转换为包内相对路径。

建议提供两个预设，共用同一打包引擎：

- 阅读包：当前采用版本的全部文字、图片、视频与离线阅读页，用于保存和分享。
- 项目包：增加角色/场景快照、阶段设定、版本历史（可选）、任务元数据与结构化数据，用于备份和再次导入编辑。不能包含 API Key、应用令牌或机器敏感路径。

示例目录：

```text
活动名称.zip
  index.html
  assets/                 # 离线阅读页所需资源
  manifest.json           # 格式版本、导出范围、文件尺寸与 SHA-256
  activity.json           # 设定、角色快照、阶段、版本与关联
  story.md
  conversations/          # 群聊文字及结构化记录
  moments/                # 帖子、评论和关联
  media/images/
  media/videos/
  media/audio/            # 若活动使用音频
  history/                # 可选历史版本
```

离线页不依赖 CDN 或在线接口，使用本地文件即可阅读文字和图片；视频在支持对应编码的浏览器中播放。为通用播放提供可选兼容副本，原文件仍保留。JSON 数据应嵌入阅读页或预渲染，避免直接打开 HTML 时遭遇本地 fetch 限制。

导出先固定活动版本和媒体清单，再流式打包。进行中的任务需选择等待完成或导出已有内容；不把生成中的结果称为完整成品。缺失文件必须报明细，用户可修复或明确选择不完整导出，禁止静默跳过。

支持大包和 ZIP64，显示进度、取消与失败原因。项目导入校验格式和文件校验和，创建新的活动 ID、重映射引用，不覆盖原活动；导入只恢复内容和配置描述，不自动重启旧任务。

验收必须在停止本地服务后解压阅读，并在空白实例重新导入验证，不只检查 ZIP 文件存在。

## 9. 实现结构与数据实体

建议入口 `/apps/activities`，活动相关业务放在 `apps/service/src/activities/`，共享契约放在 `packages/contracts`。初期复用现有 Fastify 服务和数据库迁移体系，以活动专属表隔离业务；无需为每个活动启动独立邻舍进程或微服务。

建议模块：

- `activities`：生命周期与设定。
- `stages`：阶段顺序、约束与方案版本。
- `characters`：角色快照、活动内状态与知情范围。
- `planning` / `execution`：预览和持久化执行。
- `content`：旁白、群聊、动态、评论及关联。
- `revisions`：候选、采用、分支和检查点。
- `media`：镜头、任务绑定、选片和引用。
- `exports`：导出任务、离线阅读页与项目导入。
- `connectors/linshe`：可选邻舍连接，独立于核心执行。

概念实体：Activity、PlanRevision、Stage、CharacterSnapshot、Branch、Checkpoint、ContentRevision、Fact、Shot、MediaSelection、ExecutionJob、ExportJob。它们是数据职责划分，不要求每个概念都在第一版做独立服务。

持久化任务采用幂等键与版本检查；提交前写入任务意图，返回后按原版本落库。重启恢复任务时先查询已接受的生成任务，不能无条件重复提交。若供应商没有查询或幂等能力且请求结果不明，应显示“结果待确认”，由用户选择重新生成；不宣称跨外部服务可以保证恰好执行一次。

文本预览也需要持久任务记录；现有 Generation 偏媒体执行，不能只在浏览器保留 LLM 请求状态。活动内剧情推进串行，媒体按配置并发；不同活动共享资源队列，但不能共享上下文。

活动消费者拥有独立的模型用途配置和媒体归属。扩展现有消费者注册及关联表，不能偷用邻舍的运行身份或假定 `character/narrative` 关联可以容纳活动。

## 10. 开发阶段与验收门槛

以下是依赖顺序，不是工期承诺；真实视频模型、目标设备和预览交互选择明确后再估算时间。

| 阶段 | 开发内容 | 可交付与通过条件 |
| --- | --- | --- |
| P0 方案验证 | 确定呈现位置、用户身份、预览节奏；检查公共服务现有回归基线；用一组固定人设验证两阶段结构化生成 | 记录已有失败与新模块依赖，用户要求不被覆盖，群聊/帖子与行动一致，确认不依赖邻舍运行 |
| P1 应用骨架与隔离 | 活动列表、设定、角色快照、阶段增删排序、自动保存、活动归属校验 | 至少两阶段，两个活动无串数据，公共角色更新不改已有活动 |
| P2 预览与文字执行 | 全自主/部分指定/严格执行；方案与完整文字预览；群聊/动态/时间线；持久任务 | 从创建到结束能完成两种不同活动；刷新不中断已接受任务，采用文字不被重新随机改写 |
| P3 回溯与恢复 | 从 P1 开始的数据版本基础在此补齐 UI、检查点、局部重写、阶段重做、后续复核 | 可恢复旧剧情与状态；迟到任务不覆盖新版本；旧版事实不泄漏到重做后的内容 |
| P4 媒体闭环 | 镜头、外观参考、图片生成/上传、视频上传与可用生成适配、选片、任务恢复 | 文本、图片、视频绑定正确版本；重拍不重跑剧情；单项失败不阻断活动 |
| P5 打包与恢复验收 | 阅读包、项目包、流式打包、完整性报告、离线页、再导入 | 全部选定媒体可离线访问；空白环境导入后能继续编辑；缺失文件不伪报完整 |
| P6 后续增强 | 生成式视频实机优化、连续镜头、复杂分支可视化、活动模板、可选邻舍发布 | 按具体能力逐项验收；外部发布与内部回溯边界清楚 |

第一版正式交付范围为 P1—P5 的完整闭环；回溯、群聊、朋友圈和完整打包不是后续可选项。P6 不阻塞文本、图片和已有视频的完整活动应用。

版本结构必须在 P1 建立，P3 不是在已覆盖式存储的系统上临时补历史。

## 11. 重点验收场景

1. 同一组角色同时参与生日会和旅行，双方记忆、地点、服装和动态完全独立。
2. 所有阶段留空仍能生成至少两阶段预览；部分填写后锁定要求保持；活动不允许正式提交少于两阶段的方案。
3. 删除、插入或重排已生成阶段，旧版可恢复，后续影响可见。
4. 修改第二阶段的一次送礼，重做后的帖子不继续描述旧礼物；恢复旧版本后旧礼物与旧照片仍存在。
5. 重新生成一张照片，群聊文本、角色状态和其他已采用照片保持一致。
6. 回溯时有视频仍在生成，结果到达后落在原版本，不覆盖新版本。
7. 网络中断、页面刷新和服务重启后，任务状态可恢复，无重复发言或重复提交媒体任务。
8. 邻舍完全停止时，应用仍可执行独立活动。
9. 未采用的候选及另一分支的摘要不进入当前角色上下文；角色不知道尚未发生的惊喜。
10. 导出含图片、视频的整场活动，停止服务后离线阅读；再导入后阶段、文字、媒体和版本关联一致。
11. 导出期间修改活动，包内内容仍属于同一快照；磁盘不足或媒体缺失有明确结果。
12. 归档、删除历史或清理任务不删除其他活动/版本仍引用的媒体。

## 12. 暂不作为第一版前提

- 不要求每个角色有独立长期代理进程。
- 不要求通用拖拽节点编排器；阶段编辑已经能表达主要活动需求。
- 不自动把每场活动经历写回公共人设或邻舍长期记忆。
- 不要求原生邻舍群聊/朋友圈作为主存储或唯一呈现位置。
- 不承诺回溯能够追回已发生的模型费用，或撤销已发布到外部系统的内容。
- 不将真实生成式视频、多角色视觉一致性和外部模型就绪视为无需验收的既成能力。
