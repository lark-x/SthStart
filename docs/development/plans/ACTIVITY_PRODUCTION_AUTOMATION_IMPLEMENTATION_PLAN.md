## 0. 给接手模型的执行说明

请在当前项目上增量实现本文。先核对当前分支与现有功能；后续提交可能已经补齐某些条目，已经可用的部分复用并记录，不要再次开发。

本次目标：让用户从一份确认的活动企划，更少操作地获得群聊、朋友圈及对应图片/视频；不满意时只修改必要部分，最后导出阅读包、可继续编辑的工作工程或 HyperFrames 工程。

关键产品约定：

1. 每个活动独立，角色从人设库冻结到活动快照；修改本场活动不能静默修改全局角色。
2. 自动执行重复工作；在“采用文本”和“采用媒体”处保留明确选择。生成成功不等于用户已经采用。
3. 使用现有公共模型服务、Generation Core、ComfyUI/Worker 接入、Artifact、提示词来源与版本机制。
4. 视频交付方式保持为：应用导出 HyperFrames 工程，用户在外部渲染。不新增应用内渲染农场。
5. 活动页面继续围绕群聊、朋友圈和媒体记录。不要把核心产品改成独立的电影分镜编辑器。
6. 第一阶段以批量图片为主；已有视频上传、关联、播放、导出应继续可用。自动视频生成暂时沿用现有独立入口，不把所有引擎的视频批量兼容列为首版要求。
7. 不改造 `upstream/linshe`；不重做已经完成的话题库、MCP 研究、角色导入和企划向导。
8. 不引入 Redis、独立工作流平台、通用 DAG 编辑器或第二套生成调度器。必要状态存入现有 SQLite。
9. 测试聚焦“不会重复提交任务、不会覆盖满意内容、媒体与来源不断链”。不追求大规模测试体系或企业级验收。

执行顺序：M0 → M1 → M2 → M3 → M4 → M5 → M6。每个里程碑完成后应可独立使用；不要先做架构拆分、等所有模块齐备后再接通页面。

## 2. 产品路径和页面结构

### 2.1 默认路径

```text
素材库选点子 / 手动创建活动
  → 现有企划向导：人物、地点、阶段、多方案、补齐人设
  → 创建活动，进入生产概览
  → 生成文本候选：群聊、朋友圈、评论、事实、媒体描述
  → 预览、局部调整、采用文本
  → 确认媒体清单，批量生成图片
  → 对比并采用图片，补充或上传视频
  → 自动编排聊天/朋友圈播放顺序并预览
  → 导出阅读包 / 工作工程 / HyperFrames 工程
```

用户可以跳过不需要的步骤：纯文字活动不要求生图；只需要阅读包时不要求先制作回放；上传现成图片应与 AI 图片平等参与采用和导出。

### 2.2 活动工作室改造

保留现有“设置、记录、媒体、回放”四个标签，在工作室标题下新增常驻但可收起的 `ProductionOverview`。不新建一个与现有编辑器重复的全屏向导。

桌面示意：

```text
活动名称                 [历史版本] [导出]
企划已创建 → 文本待确认 → 图片 3/6 已采用 → 回放待更新
下一步：检查 2 个阶段的候选内容                 [预览文本]

[设置] [记录] [媒体] [回放]
当前工作区内容……
```

状态来自持久化的版本、任务、候选和媒体绑定，而不是仅存于 React state 的布尔变量。“已生成 6 张”和“已采用 3 个槽位”必须分开显示。

下一步按钮规则：

| 当前情况 | 主按钮 |
| --- | --- |
| 尚无实际聊天/动态 | 生成文本预览 |
| 有未采用文本候选 | 查看候选 |
| 文本已采用，有未补齐图片槽位 | 批量生成图片 |
| 有成功图片候选未选择 | 挑选图片 |
| 内容或媒体变更后，已有回放不匹配 | 更新回放 |
| 记录与所需媒体已就绪 | 预览与导出 |

失败不把整个概览清零。显示具体失败项和“继续处理”，已完成项仍能查看、导出或采用。

### 2.3 通用交互规则

- 简单选项默认展开，高级提示词、seed、引擎参数收在折叠区。
- 每个任务提供中文名称、阶段/槽位、状态、失败原因和回到对应位置的入口。
- 深链接可采用现有活动 URL 加 `tab`、`stageId`、`slotId`、`batchId` 等查询参数；先核实当前路由解析再扩展。页面刷新仍定位到对应实体。
- 页面离开不取消服务端任务；回来能恢复状态。未保存草稿先调用现有 `flush()`，失败或冲突时保留用户输入。
- UI 复用现有组件、设计 token、抽屉和提示，不顺便再做全站视觉重构。
- 角色或图像配置未完整时指出缺哪一项并提供配置跳转；不凭空声称角色外观准确或引擎已就绪。

## 3. 第一阶段：连通现有生产流程

交付重点：M0、M1、M2、M3。完成后，用户不需要为每张图单独打开工作台并重复配置。

### 3.1 M0：基线核对与最小依赖检查

工作：

1. 记录分支、HEAD、工作区已有修改，核对本文所列功能入口；不覆盖他人改动。
2. 用一个 3 阶段、3～5 名角色的示例活动检查：生成候选、采用、单图、图片采用、回放、导出。
3. 优先修复会阻断新流程的现存缺陷；在交付记录中区分现存修复和新功能。
4. 核实已有的锁定、取消、重试语义，不能仅凭按钮存在就认定链路完整。
5. 确认用于测试的 ComfyUI 工作流及用途分配；没有真实服务时保留明确待联调项，继续完成接口和页面。

最小生图预检与 M2 同步交付，不等待完整引擎架构重构：

- 公共服务用途分配存在、引擎可连接、选中的工作流版本可用。
- 必需节点可用；明确声明的模型输入能与引擎返回的可选模型对应。
- 图生图参考图可读取、类型符合当前工作流；不要求所有人物都有参考图。
- 预检结果绑定引擎和工作流版本，配置变化后失效；真正提交前仍由原执行链路校验。
- 对固定的 H3/Worker 用途，补齐 `FIX-001` 要求的具体依赖检查；不能只因目录存在就报就绪。
- 动态、自定义节点无法探测时显示“未能确认：某依赖”，不要冒充通过；已知必需依赖缺失则阻止该项提交。
- 首版不承诺 VRAM 精确估算、模型文件完整性校验、自动安装节点或自动下载模型。

### 3.2 M1：文本预览和采用衔接

#### 前端

在现有 `generation-modal.tsx` 上增强，或者把其候选区抽为复用组件，不复制整个生成弹窗。

- 生产概览提供“生成文本预览”；默认复用 `whole-text`。
- 用户可选全部未锁定阶段或指定阶段，填写统一风格要求。
- 左侧阶段列表：生成中、候选就绪、失败、已采用、已锁定；右侧用群聊/朋友圈样式展示候选。
- 候选预览显示实际文本、角色、评论、点赞、媒体描述占位，不只显示原始 JSON。
- 操作包括：采用此阶段、采用本批所选阶段、对当前候选提修改意见、返回继续编辑。
- 图片占位显示“准备生成什么、有哪些角色”，此步骤不自动发起图片任务。
- 生成失败时保留前面已经成功的阶段；主按钮变成“继续未完成阶段”，不是从头重跑。

#### 服务端

1. 复用 `runTextGenerationJob`、候选存储、模型绑定、校验和现有逐阶段上下文逻辑。
2. 对 `whole-text` 增加明确的 `stageIds` 范围；按阶段顺序执行，跳过锁定阶段，并把已锁定阶段的已有事实/记录作为上下文。
3. 取消检查覆盖每次模型响应之后、候选写入之前。取消后的迟到结果不能生成新候选。
4. 扩展 job 输入快照：选定阶段、冻结文档/修订、指引、成功阶段与候选关联。刷新恢复不能读取临时 UI 状态。
5. “原样重试”沿用冻结输入；“按当前修改重新生成”创建新的任务。页面要区分这两个动作。
6. 为部分失败批次添加继续能力，只处理失败/未完成阶段；前序成功候选仍作为上下文。
7. 用户改过前序候选或已采用内容时，比较相关上下文指纹；后续旧候选标为需复核，不自动宣称仍然连贯。采用之后的上下文变化规则见 M4。
8. 批量采用提供服务端入口，复用现有采用逻辑。先验证所有候选范围、来源版本、锁定、引用和当前草稿，再在一个本地事务中提交所选结果。
9. 单个候选重复采用应幂等返回或明确“已采用”，不能重复追加邀请、评论或动态。
10. 采用前必须校验相关内容是否被修改。只有目标 ID 仍存在并不足以证明旧候选可覆盖当前内容。

建议新增 `POST /api/v1/admin/activities/:id/candidates/adopt-batch`：

```typescript
// 新增契约示意；正式实现使用项目既有 TypeBox 风格。
type AdoptCandidateBatchInput = {
  candidateIds: string[];
  expectedHeadVersion: number;
  expectedDraftVersion: number;
  idempotencyKey: string;
};
// 响应返回最新 activity/headVersion/contentRevisionId，以及采用的 candidateIds。
// 候选过期返回明确冲突和 affectedStageIds，不静默合并覆盖。
```

M1 的基本阶段锁定立即生效：自动生成跳过锁定阶段；采用不能修改锁定阶段。M4 再扩展到单条记录与媒体。整批采用只接受同一活动、可兼容生成基线的候选；不把任意历史批次混起来顺序覆盖。

### 3.3 M2：批量图片生成与挑选

#### A. 媒体清单页面

在 `media-workstation.tsx` 上增加批量栏和过滤，不新建中央媒体库页面。

每一行/卡片显示：所属阶段、用于哪条聊天或动态、画面描述、角色、文生图/图生图、当前采用图、候选数、状态。

筛选：全部、未有采用图片、生成中、待挑选、失败、来源已变化；可再按阶段和角色筛选。

默认选中：当前内容版本下没有采用结果、没有同槽位在途任务、没有锁定的图片槽位。视频槽位独立展示“上传视频/使用现有生成入口”，不混入图片批次。

每阶段“生成配图”是选择该阶段已有槽位的快捷入口；没有槽位时打开“补充配图描述”，复用 `shot` 或手动新增流程，确认后再生成。

#### B. 媒体建议的处理

- 优先使用文本生成已经产出的 `mediaSlots`。
- 需要补图时，允许用户选择阶段和数量，让 AI 提出槽位候选；采用候选时一起建立消息/朋友圈的 `mediaSlotIds` 关联。
- 不默认每阶段生成相同数量的图；用户可以选择“仅关键画面”。
- 没有具体记录引用的槽位显示“暂未插入记录”，提供定位并关联入口；不能只生成一张不知显示在哪的阶段图片。
- 原有槽位稳定 ID 不因进入清单或重排而变化。

#### C. 提交前确认

批量面板默认只显示：勾选数量、画风/已有用途预设、每槽位候选数、参考图策略。

- 每槽位默认 1 张，允许 1～3 张；首次使用建议先选 1 个槽位试生成。
- 默认同一引擎串行提交/执行，沿用公共引擎已有并发控制；其他批次也受同一引擎限制。
- 图生图只用于有明确输入且用途支持的项；有角色参考图不等于所有工作流都能使用它。
- 混合文生图/图生图分别解析各自用途分配；缺配置的项指出原因，用户可以仅提交就绪项。
- 预览最终画面描述、来源角色/阶段、将采用的工作流、实际支持的参数；高级区可进入既有提示词来源面板。
- 不新设强制英文转换器。复用并核对现有语言/提示词策略；若需要 AI 翻译或润色，保留原文、转换结果与父级来源，最终送出的文本必须可查看。
- 不假设每个模型都有负面提示词、seed 或相同参考图节点；不支持的参数隐藏或说明不能传入。

#### D. 服务端批次模型

新增轻量“活动媒体批次”和“批次项”，只负责记录选择范围、冻结输入、关联已有 attempt/task 和协调下一项。它不是新的生成执行引擎。

建议新增表（名称是本次设计，不是声称仓库已有）：

| 表 | 必要字段 |
| --- | --- |
| `activity_media_batches` | id、activity_id、content_revision_id、image_config_revision_id、request_hash、idempotency_key、created_at、updated_at、stop_requested、options_json |
| `activity_media_batch_items` | id、batch_id、slot_id、candidate_index、slot_fingerprint、input_snapshot_json、recipe_id、compilation_id、attempt_id、generation_task_id、state、error_json、retry_of_item_id、created_at、updated_at |

约束：批次幂等键按活动隔离；一个批次内 `(slot_id, candidate_index)` 唯一；重试通过新批次项引用旧项，不抹掉历史 attempt。

同一活动同一槽位的默认批量操作需要在服务端原子检查在途占用，不能只在前端排除。两个页面同时提交时，后一个请求返回已在处理的项，避免不同幂等键重复生成。每槽位 1～3 张候选属于同一批次内明确允许的范围；其他批次待该槽位结束后再生成。

`input_snapshot_json` 保存冻结的输入与执行计划摘要；大的图像二进制继续在 Artifact。已经有 recipe/compilation/snapshot 保存的完整内容用 ID 引用，不复制一份可被独立编辑的来源数据。

批次项的本地状态可用 `waiting / preparing / linked / skipped / failed`；一旦关联 attempt，真实生成状态从现有 attempt/task 读取。批次汇总由所有项计算，可以缓存，但必须能重算。

建议汇总显示：准备中、运行中、部分完成、完成、已停止、需要处理。成功、失败、未开始、结果未知分别计数；不把结果未知算成可直接重试的失败。

#### E. 具体执行链路

```text
用户保存草稿并确认要采用的文本
  → 获取 contentRevisionId 与 imageConfigRevisionId
  → 建立批次，冻结选择范围、槽位指纹与参数
  → 对每个项复用 prepare recipe / compilation
  → 保存 recipeId / compilationId / executionPlanHash
  → 通过现有 image-attempts 创建 attempt 与公共 Generation task
  → 原执行器负责上传参考图、提交、恢复、回收产物及发送快照
  → 批次关联结果，显示候选
  → 用户采用后写入 MediaRevision.slotBindings
```

- 创建 attempt 必须使用稳定的业务幂等键，例如批次项 ID；先保存本地项再外部提交。
- 进程在“任务已建立、关联未写回”之间退出时，重启按同一幂等键找回，不再提交一遍。
- 准备配方后改变用途分配或工作流时，沿用既有冻结计划核对规则；不可静默换引擎。
- 入队后修改角色、阶段或画风，不修改在途任务输入；结果保留并标注“按旧版本生成”。
- 失败一项可以继续独立的后续项；引擎离线等共性失败暂停未提交项，避免连续发出相同失败请求。
- 首版不自动重试模型/GPU 生成，提供“重试失败项”。只重试明确可重放的失败；提交结果未知应先通过原恢复机制核对。
- “停止本批”停止未提交项，并向可取消的任务转发取消。已成功结果保留；远端可能继续计算时如实显示。
- 刷新、切换页面不影响执行。服务重启后先对账已关联任务，再恢复尚未提交的合法项；已被用户停止的批次不自动重启。

#### F. 结果挑选与采用

- 每个槽位对比当前采用图与本批候选，支持放大、查看提示词、跳转来源修改和重新生成。
- 成功图先进入候选区，不自动替换当前采用图。
- 提供“采用所选结果”；每槽位可以明确选定一张，沿用当前绑定支持的多媒体数量，不在首版强制扩展九宫格规则。
- 批量采用先验证活动版本、槽位是否仍存在、指纹是否变化、资源是否实际存在、锁定状态。复用 `selectMediaForSlots` 的业务逻辑并补齐不足。
- 只更新本次所选槽位，其他槽位的绑定完整保留；一个媒体修订完成本次采用。
- 若当前内容版本已变化，先重新评估兼容性；同一槽位输入未变化可显式采用，输入已变化显示差异并要求用户重新选择或明确保留旧图。
- 不为不存在的图片创建空 Artifact 来伪装采用成功。
- 采用后将相关回放标为需更新，不删除此前回放版本。

#### G. 建议接口

统一置于现有管理接口前缀，并复用鉴权与错误结构：

| 方法和路径 | 用途 |
| --- | --- |
| `GET /api/v1/admin/activities/:id/production` | 聚合文本、媒体、回放状态和建议下一步 |
| `POST /api/v1/admin/activities/:id/media-batches/prepare` | 预检选定槽位，返回就绪项、问题和将生成的数量 |
| `POST /api/v1/admin/activities/:id/media-batches` | 固定版本和幂等键创建批次；服务端再次校验 |
| `GET /api/v1/admin/activities/:id/media-batches` | 当前及历史批次 |
| `GET /api/v1/admin/activities/:id/media-batches/:batchId` | 各项状态、候选和原任务引用 |
| `POST /api/v1/admin/activities/:id/media-batches/:batchId/stop` | 停止批次 |
| `POST /api/v1/admin/activities/:id/media-batches/:batchId/retry-failed` | 创建失败项重试批次并保留来源 |

批量媒体采用优先扩展现有 `/media-selection` 规范入口，避免再增加一个内容相同但行为不同的 API。控制器只做输入/输出和调用，不在路由内复制执行器。

创建批次的最小请求建议如下；准备接口接收相同业务输入，但不提交外部生成：

```typescript
type CreateMediaBatchInput = {
  expectedHeadVersion: number;
  contentRevisionId: string;
  imageConfigRevisionId: string;
  items: Array<{ slotId: string; candidateCount: 1 | 2 | 3 }>;
  productionPresetId?: string;
  idempotencyKey: string;
};
// 各槽位具体参数先通过现有 ImageConfigDraft 保存并提交修订。
// preset 若参与本次请求，服务端解析并冻结实际版本与内容，不只保存一个可变 ID。
// 返回 batchId、acceptedItems、skippedItems/reasons 和状态查询入口。
```

准备结果只是说明当前是否可提交，创建批次时仍重新校验；请求包含不属于当前活动/修订的槽位则报错，不悄悄忽略。部分提交须对应用户在确认区选择“仅提交就绪项”，响应明确列出跳过项。

### 3.4 M3：轻量全局任务中心

目标：用户离开活动页后仍能知道任务有没有完成，并能直接回到对应结果。

#### 范围与架构

覆盖：话题采集、点子生成、MCP 研究、企划生成、活动文本任务、媒体批次/独立生成任务、已有导出任务。

```text
各业务已有任务存储 + 媒体批次关联
  → 只读查询适配器
  → GET /api/v1/admin/tasks
  → AppShell 全局入口与任务抽屉

用户点击取消/重试
  → 适配器校验业务能力
  → 原模块的取消/重试服务
```

不建 `global_tasks` 状态表，不把所有模块改成向新总线写任务。M2 的批次表保存新增的批量业务关系；M3 只聚合它们，二者职责不同。

建议接口：

- `GET /api/v1/admin/tasks?state=active|recent&limit=...&cursor=...`。
- `POST /api/v1/admin/tasks/:domain/:taskId/cancel`。
- `POST /api/v1/admin/tasks/:domain/:taskId/retry`。

`domain + taskId` 唯一标识任务；取消与重试路由必须验证实际任务所属业务，不依赖前端提供任意 URL。无法直接重试的业务，返回到原页面处理。

建议统一只读模型：

```typescript
type TaskSummary = {
  domain: 'topic_collection' | 'idea_generation' | 'research' | 'planning'
    | 'activity_text' | 'activity_media_batch' | 'generation' | 'export';
  taskId: string;
  title: string;
  activityId?: string;
  parentTask?: { domain: string; taskId: string };
  displayState: 'waiting' | 'running' | 'succeeded' | 'partial'
    | 'failed' | 'stopped' | 'needs_attention';
  rawState: string;
  progress?: { completed: number; total: number; unit: string };
  detail?: string;
  targetUrl: string;
  capabilities: { cancel: boolean; retry: boolean };
  cancelScope?: 'pending_items' | 'local_tracking' | 'upstream';
  createdAt: string;
  updatedAt: string;
};
```

保留 `rawState`，正确展示 `partial`、`result_unknown`、`abandoned` 等已有状态。没有进度数据时显示“正在生成第 2 个阶段”，不伪造 63% 之类的百分比。

#### 页面行为

- 改造真实路径 `app/components/shared/app-shell.tsx`，在顶栏加运行数量及抽屉入口。
- 抽屉分为进行中、需要处理、最近完成；显示任务标题、业务来源、进度和“查看结果”。
- 媒体批次与其子任务分组，默认只计一次；独立生图任务仍单独展示。
- 抽屉关闭时低频刷新，打开或有活跃任务时约 2～5 秒刷新，页面失焦降低频率；首版不用 SSE。
- AppShell 提供单一查询入口，其他页面复用 React Query 缓存，避免每个组件再增加一组轮询。
- “查看结果”直接定位活动阶段/槽位或对应企划会话；缺失对象提供友好说明。
- 完成通知只针对当前会话观察到的状态变化，同一任务不重复弹；首次加载的历史完成任务不全部弹出。
- 不支持取消的任务不显示取消按钮。首版不提供“一键取消全部”。
- “隐藏已完成”只改变展示，不删除业务记录、来源和候选；可以使用本地偏好。
- 某个模块查询失败时显示该模块状态暂不可用，不让整个抽屉失效。

进程恢复仍由原模块负责：远端已经接受的任务先查询远端，文本结果未知按既有规则提示；任务中心本身不把所有未完成任务写成失败或中断。

## 4. 第二阶段：降低返工成本和复用常用配置

### 4.1 M4：锁定、局部重生成、修改影响

目标：用户能够表达“这部分已经满意”，并在修改一个角色或一句话时看清需要检查哪些内容。

#### A. 三种锁定的语义

| 锁定对象 | 保留内容 | 仍允许的操作 |
| --- | --- | --- |
| 阶段：复用 `StageDefinition.locked` | 阶段定义及其文本记录/事实/槽位定义不被自动替换或删除 | 对既有槽位补图、查看候选、预览、导出；编辑受保护内容前解锁 |
| 记录：首版支持消息、朋友圈帖子 | 记录正文、角色、顺序和关联媒体；锁定帖子同时保护它的评论/点赞不被自动重写 | 查看与复制；同阶段其他未锁定记录可局部改写 |
| 媒体槽位的采用结果 | 当前采用的资源绑定 | 查看已有候选与来源；来源变化仍提示需复核，换图前解锁 |

提示词块已有的 `PromptBlock.locked` 是另一种能力：表示该提示词块不应被自动改写。保留原语义，不用它代替媒体采用锁。

建议在 `ContentDocument` 增加可选 `editingPolicy`，旧文档缺省为空：

```typescript
type EditingPolicy = {
  lockedRecords: Array<{ kind: 'message' | 'post'; id: string }>;
  lockedMediaSlotIds: string[];
};
```

这只是新增契约建议，实施前检查是否已有等价策略。阶段锁不再重复存进该字段。策略随内容修订、工作工程和恢复点保存；引用的记录/槽位必须属于该活动。

具体规则：

- 锁定/解锁走正常草稿保存；生成和采用时由服务端再次校验，不仅是禁用前端按钮。
- 阶段存在锁定记录时，不进行整阶段替换。提供“只改写未锁定记录”或“解锁后重生成阶段”，避免自动合并新旧剧情造成断裂。
- 未锁定的局部改写默认仅修改所选正文，保留记录 ID、引用、顺序和媒体关联。改变发言人、顺序等应是明确编辑。
- 删除锁定记录、删除其所属阶段、解除其媒体关联都要先解锁；普通删除已有的确认机制继续复用。
- 角色全局人设更新不会自动刷新活动快照；用户选择更新本场快照时才触发影响分析。
- 图片锁不代表图片永远符合新剧情：保留采用结果并标记“保留旧图，来源已变化”，由用户选择复核或解锁重做。

#### B. 统一“重新生成”入口

| 入口 | 默认范围 | 复用能力 |
| --- | --- | --- |
| 阶段菜单 | 当前未锁定阶段 | `stage` |
| 多选聊天记录/帖子 | 所选且未锁定记录 | `rewrite-records` |
| 图片卡片 | 当前槽位，使用当前确认的输入 | recipe + attempt |
| 修改影响面板 | 用户勾选的受影响项 | 局部文本任务或媒体批次 |
| 失败批次 | 明确失败且可重试项 | 原任务重试 / M2 重试批次 |

统一弹窗：修改意见、作用范围、保留项数量；默认保留已采用内容直至新候选被采用。对已有候选提修改意见时必须把该候选正文带给模型，不能只重新发送最初阶段要求。

#### C. 影响分析

复用 `previewSourceImpact` 的来源依赖，补充内容结构关系；不能只查询已经编译过的图片配方，否则尚未生成的槽位会漏掉。

按稳定实体 ID 和字段类别判断，首版不构造复杂语义知识图谱：

| 修改 | 默认影响 |
| --- | --- |
| 角色外观/本次服装/参考图 | 包含该角色的图片槽位；旧 attempt 保持原输入 |
| 角色说话方式/性格 | 该角色参与的文本阶段需复核，不直接重写全部内容 |
| 阶段地点、动作、剧情事实 | 本阶段相关记录、引用事实的槽位；后续阶段列为潜在影响 |
| 某条对白措辞 | 本条记录及回放阅读时长；除非修改了关联事实，不默认让所有图片失效 |
| 图片描述、画风、构图 | 对应槽位，或明确使用全局画风的槽位 |
| 媒体采用结果 | 引用该媒体的回放动作；文本一般不受影响 |
| 活动显示标题等展示字段 | 阅读包/回放展示刷新，不重生成文本和图片 |

界面用列表说明“为什么受影响”，区分确定关联与“剧情连续性可能需复核”。一个槽位被多份历史配方引用时去重，历史来源不冒充当前采用图的来源。

面板提供：仅保存修改、保存并稍后处理、对所选项生成新候选。任何选项都不删除旧结果，不默认启动全部生图。

复核提示绑定“变更后版本或相关指纹”；点击“仍然可用”只确认此次变化，后续再次修改仍会提示。展示用状态可以计算，人工复核决定需要持久化，不只存本地浏览器。

#### D. 候选过期与阶段连续性

- 生成时记录目标阶段/记录的输入指纹，以及实际使用的前序事实/候选依赖。
- 仅有无关展示字段变化时可以允许采用；目标正文、阶段、角色上下文或前序事实变化时提示候选需更新。
- 同一批次按原顺序采用前序阶段属于预期变化：比较已采用候选的语义内容/来源，不能因为 headVersion 增长就判定所有后续候选过期。
- 若用户修改前序候选后再采用，后续依赖旧内容的候选应标为需复核或重新生成；不要自动套用旧后续内容。
- 部分继续生成时使用明确选择的前序上下文：未改变的成功候选或已经采用的当前记录，不同时塞入两个冲突版本。
- 复用 `StageResult.reviewState` 和 `sourceContextHash` 能表达的部分；媒体复核若需要新表，应只存人工确认和相关指纹，不复制配方历史。

### 4.2 M5：活动模板与生产预设

目标：同类型活动第二次创建时，减少重复设置；保持现有人设筛选与 MCP 研究流程。

#### A. 三类复用内容

| 类型 | 保存什么 | 不保存什么 |
| --- | --- | --- |
| 活动模板 | 类型、角色职责槽、阶段标题/说明/关键事件、地点建议、文本风格、媒体数量偏好 | 上一场聊天/朋友圈正文、旧 task/attempt、旧媒体绑定 |
| 生产预设 | 每槽位候选数、图像画风、可用参数、参考图策略、已有用途选择偏好 | API key、固定机器地址、上一场角色 ID |
| 回放预设 | 手机/iPad 显示方案、节奏、图片停留、是否展开视频/评论、混排模式 | 上一场动作的记录 ID 或 assetKey |

生产预设是业务偏好，不是新的模型配置中心；工作流仍由已有用途分配管理，不允许预设绕过公共服务指定任意引擎。

#### B. 页面

- 活动设置页“另存为模板”：展示将保存的阶段和职责，填写名称，确认本场专有信息是否替换成角色职责。
- 创建页在现有内置模板旁加入“我的模板”；选择后填表，用户照常选角色、地点并进入现有企划向导。
- 人物职责例如 `lead`、`guest`、`organizer`，可以多个参与者映射同一职责；与原神/星铁等作品筛选独立。
- 媒体批量面板支持选择/保存生产预设；回放页支持选择/保存回放预设。
- 首版采用一个简单的管理弹窗：改名、另存为、删除。无需新建复杂模板市场页面。

#### C. 数据与实例化

可以用一张新增 `activity_reusable_presets` 表，包含 `id, kind, name, version, schema_version, payload_json, created_at, updated_at`。`kind` 区分三种类型；若当前仓库已有适合扩展的预设存储，则复用并在交付记录说明。

- 保留现有内置模板 ID 和创建逻辑；用户模板使用独立命名空间。
- 模板作用于新活动时，创建新的阶段、关键事件等实例 ID，角色职责解析成本场 actor ID；检查引用闭合。
- 文本中的本场人名不做不可靠的全局替换。模板编辑器显示残留的专名供用户处理；支持有限的职责占位符即可，不使用可执行模板表达式。
- 把本次实际应用的模板版本/配置快照保存在活动或相应生成输入中；修改模板不会追改旧活动。
- 应用生产预设先预览差异；已有槽位的手工覆盖不静默清空，是否应用到这些槽位由用户选择。
- 工作流或模型用途已经不存在时提示重新选择，不直接拿旧 ID 提交。
- 默认不从角色库自动拉取最新人设覆盖现有活动快照；新建活动照常冻结选中的版本。

建议接口：`GET/POST /api/v1/admin/activity-presets`，`GET/PATCH/DELETE /api/v1/admin/activity-presets/:id`；以 `kind` 过滤。正式契约校验 payload，不能用完全无约束的 JSON 充当已完成的数据模型。

## 5. 第三阶段：交付效率和必要维护

### 5.1 M6-A：回放编排与 HyperFrames 导出

这是现有回放/导出能力的增强，不是从头开发视频模块。

#### 用户可选择的播放方式

1. 按阶段：该阶段群聊 → 朋友圈 → 下一阶段，作为默认且稳定的模式。
2. 按故事顺序混排：依据可比较的 `storyOrder` 和明确的排序规则切换视图；同序号采用固定 tie-break，不凭空推断精确时间。
3. 仅群聊 / 仅朋友圈：生成新的回放方案，不删除源内容。

每种方式可以组合手机/iPad 显示预设、阅读速度、是否展开图片、视频和评论。用三个易懂的初始节奏：“快速浏览”“正常阅读”“慢速展示”；具体参数在实现时用真实样例调整。

#### 实施要点

- 复用 `generateAutoPlayback` 和 `PlaybackDocument`；界面只添加业务参数及动作预览。
- 同阶段有多个会话时，按每条消息的 `conversationId` 正确切换，不能仅取第一条消息的会话用于整个阶段。
- 没有原生统一全局顺序的记录，默认保持按阶段顺序；混排规则要明确且可重复，不让模型临时猜顺序。
- 图片展开必须对应当前媒体修订中选择的真实资源；视频要考虑素材时长、截取起点和音量，复用已有动作契约。
- 用真实布局定位消息/帖子；长文本、连续图片、回复和评论不会因固定高度估算而滚到错误位置。
- 更换图或修改文字后，先提示旧回放需要更新。自动重编排创建新 PlaybackRevision，不覆盖用户手工调整的旧版本。
- 首版允许用户选择“保留当前回放”或“重新自动编排”，不要求完成复杂的时间轴局部合并算法。
- 正式预览与 HyperFrames 导出继续使用同一编译实现和同一组选定版本；不要各自再实现一套播放逻辑。
- 如果预览尚有占位媒体，补齐真实加载；若当前已经修复，仅验证，不重复建设。
- 修改 HyperFrames composition/compiler 或进行渲染时，接手模型应先读取当前环境的 HyperFrames skill/项目规范，按实际安装版本验证。本文不固定可能过时的 CLI 命令或运行时写法。

#### 导出页面

保留现有三个真实格式，向用户解释用途：

| UI 名称 | format | 必须包含 |
| --- | --- | --- |
| 阅读分享包 | `reader` | 离线可查看的群聊/朋友圈和所需媒体 |
| 可继续编辑的工作工程 | `project` | 活动数据、选择的历史范围、角色快照、媒体、来源/配方/必要引用关系，支持再导入 |
| 视频制作工程 | `hyperframes-project` | 可渲染工程、选定的记录/媒体/回放快照、本地素材、实际依赖及使用说明 |

导出确认区展示活动名称、内容/媒体/回放版本、图片/视频数量、未补齐的槽位。未补齐图片可以选择导出纯文字或保留明确占位的阅读包；视频工程中的缺失媒体需在导出前选择补齐或明确跳过对应动作，不能生成引用不存在文件的工程。

产物要求：

- 固定一组兼容的修订 ID，不在导出过程读取不断变化的当前版本。
- 所需媒体使用相对路径并实际打包；不依赖应用端授权 URL 或开发机绝对路径。
- 扩展名与实际媒体类型匹配，不把所有图片都假定为 PNG、所有视频都假定为 MP4。
- 工程说明写清外部预览/渲染方法，以及依赖安装是否需要联网；不得声称所有外部环境都零依赖离线渲染。
- 工作工程新增的锁定、复核和模板快照应纳入导出/导入；新活动 ID、记录 ID、槽位 ID 重映射后引用仍然可解析。
- 真实渲染验证至少使用一段带音频的视频；确认图片点开、视频播放和回到记录的行为。没有真实渲染环境则明确记录待验证，不把 HTML 生成成功写成视频验收通过。

### 5.2 M6-B：完整备份

目标是个人使用的可靠备份与整机恢复。首版不做多设备双向同步或增量数据库合并。

在 `scripts/database.ts` 已有命令和清单能力上扩展，或增加一个很薄的 `scripts/portable-backup.ts` 包装，避免重复维护两套数据库备份实现。

- 最简一致性方案：停止服务写入后备份；按实际配置覆盖主数据库、叙事数据库等必要库，不只备份单一文件。
- 从归档的数据库快照生成资源清单，默认打包被当前内容、历史修订、角色、笔记和保留生成记录引用的所有文件，以及用户固定保留的资源。
- 扫描实际存储关系：中央 `artifacts` / `artifact_references`、角色关联、活动资源、尚未中央化的 `note_assets` 等。不能只筛选 `pinned = 1`。
- 已确认可淘汰的临时缓存可排除；数据库仍保留引用却缺少文件的情况必须列入缺失报告。
- 清单包含逻辑资源 ID、归档内相对路径、文件大小/hash 和原存储类别；跨机器恢复时重建路径，不能继续使用原机器的绝对路径。
- 默认不把 API 密钥打进包。提供需重新配置的项目清单；不在首版承诺系统钥匙串可跨设备直接恢复。
- 恢复到新目录，检查后再替换现用数据；服务停止状态下恢复，沿用现有恢复命令的必要确认约定。
- 第一版只有“完整恢复”，没有“增量合并”。导出工作工程仍用于单个活动搬运，和全站备份区分。

### 5.3 按实际需要处理的维护项

以下不阻塞 M1～M5，不要求全部实施后才交付：

- `DEV-001 / DEV-002`：生成核心拆分/适配器。仅在新增批量功能确实需要时抽取小型入口，保持既有任务恢复和幂等行为。
- `DEV-003`：管理服务拆分，属于独立维护，不混进 Generation 改造验收。
- `DEV-007`：优先让 Notebook 新上传资源使用中央 Artifact，再提供旧资源兼容迁移；保留角色已有业务关联。
- GPU 细粒度诊断：基础依赖预检之后，根据真实失败案例补充。

默认暂缓：本地 RAG、移动端离线写入与同步、自动发帖、自动运营、角色关系知识图谱、跨设备数据合并、自动批量视频生成、无人值守全自动采用。

这些方向以后可以独立立项，但不能为了“自动化”在本轮一次性引入。

## 6. 跨模块实现约定

### 6.1 保存、版本与并发

1. 发起文本任务前先完成本地草稿保存，冻结 `draftVersion`、基础内容修订与输入快照；不强迫未确认文本直接成为正式采用版本。
2. 发起媒体批次前，确保用户已采用所需文本，冻结 `contentRevisionId` 与 `imageConfigRevisionId`。仅草稿自动保存成功，不代表文本已采用。
3. 修改草稿使用既有 `expectedDraftVersion`；修改采用内容/媒体使用既有 `expectedHeadVersion`。不能通过直接 SQL 修改 current 指针绕过版本逻辑。
4. 批量文本采用先在内存中对当前文档逐项应用并验证，最后在一个短事务中保存草稿、提交内容修订和标记候选。避免前端循环请求造成采用到一半中断。
5. 网络调用、模型请求和大文件处理不能放进 SQLite 写事务。事务只用于最终状态和关联的一致写入。
6. 版本冲突返回受影响对象和可理解原因；用户的本地输入与历史候选保留。不得用“自动刷新”覆盖尚未保存的编辑。
7. 当前内容变化不应让所有历史资源变成垃圾；已采用、在途、候选和历史版本所需资源继续按现有引用机制保留。

### 6.2 提示词和结果溯源

每个批量生成项同样能够回答：

- 图片用于哪个活动、阶段、聊天/朋友圈和槽位？
- 使用哪版内容、角色快照、图像配置、参考图？
- 哪些文字来自人设、阶段、用户补充或 AI 翻译/润色？
- 预览的编译结果、实际发送内容、工作流版本、有效参数和 seed 分别是什么？
- 这是哪个 attempt 的输出，之后被哪些媒体版本采用？

沿用已有 recipe、compilation、SourceRef、执行快照和派生关系。批次 ID 只是额外关联，不能代替这些实体。

来源面板跳转默认编辑当前活动的相应字段；查看历史时显示冻结值与当前值。需要修改全局角色时进入角色页，并让用户明确选择是否更新本场活动快照。

重新生成使用当前来源创建新配方和尝试；原配方与实际发送快照保持不可变。模型即使使用相同 seed，也不承诺跨版本/引擎得到完全一样的图像。

### 6.3 状态与恢复职责

| 状态 | 真正负责者 | 新功能如何使用 |
| --- | --- | --- |
| 文本任务、候选与逐阶段进度 | 活动 text-jobs/store | 扩展范围与继续机制 |
| 生图提交、远端执行、取消与未知结果 | Generation Core + image-attempts | 批次保存引用并等待原任务状态 |
| 哪些槽位属于一次批量操作 | M2 新增批次 | 保存范围、顺序和未提交项；不复制远端执行状态机 |
| 全局任务状态显示 | M3 查询适配器 | 只读聚合，不修复/覆写原任务状态 |
| 已采用内容、媒体、回放 | 原有 revision/store | 原子提交和明确版本关联 |

首次启动恢复顺序：原模块恢复/对账 → 批次识别已关联任务 → 按用户原选择继续未提交项 → 页面读取汇总。查不到远端提交结果时不要为追求“自动恢复”再发一遍请求。

导入工作工程时，历史任务/批次只作为可选的溯源记录，不恢复成活跃状态，不自动提交新的外部生成任务。用户点击继续创作时创建本环境下的新任务。

| 项目 | 首版默认 |

## 8. 分里程碑开发顺序与交付物

### M0：核对与预检基础

- 交付：当前能力对照、必要现存问题修复、已配置用途的预检结果。
- 完成条件：找到真实使用的契约/接口；单张生成入口具备可判断的就绪信息。
- 不等待项：完整 GPU 诊断、引擎大拆分。

### M1：文本生产入口

- 交付：生产概览、文本候选预览、指定阶段/跳过锁定、部分继续、服务端批量采用。
- 完成条件：三阶段活动可生成并挑选内容，刷新能回到候选，失败后不丢前序成功结果。
- 规模：中；主要风险在候选基线与前序依赖，而不是新增按钮。

### M2：批量生图

- 交付：批次存储与协调、媒体清单、批量准备/提交、状态恢复、挑选/批量采用。
- 完成条件：选择多个槽位后离开页面，回来能看到候选；重复点击不重复提交，换图不影响未选槽位。
- 规模：较大；建议先打通一个槽位的批次形式，再扩到多项、恢复和失败继续。

### M3：任务中心

- 交付：只读聚合适配器、AppShell 抽屉、结果直达、按能力取消/重试。
- 完成条件：离开业务页面仍能看到进度；批次/子任务不重复计数；原有状态语义不被压平。
- 规模：中；独立于 SSE 和新消息总线。

### M4：返工控制

- 交付：记录/媒体锁定、服务端覆盖保护、局部重新生成、影响清单和复核状态。
- 完成条件：修改某个角色的服装，只提示相关图片；已锁定结果被保留；改写一条消息不重建整阶段的 ID。
- 规模：中到较大；优先明确锁定和候选过期，再完善影响提示。

### M5：复用设置

- 交付：用户活动模板、生产预设、回放预设及对应简单管理入口。
- 完成条件：从已有活动保存模板，再用另一组角色创建新活动，不携带上一场记录和任务 ID。
- 规模：中；在流程稳定后做，避免把尚未确定的参数大量存为预设。

### M6：交付完善

- 交付：回放预设落地、必要的混排/多会话修复、清晰的三种导出、完整备份。
- 完成条件：一个含长消息、图片、带音频视频、朋友圈评论的示例能够预览、导出并完成相应验证；备份恢复后所需媒体存在。
- 规模：中到较大，取决于当前编译器真实缺口；维护项另列，不捆绑验收。

不按固定“8～11 周”承诺排期。先完成 M0 和一个真实单图样例，再由执行者依据代码差异给出阶段估时。若需要尽早可用，优先交付 M1+M2，随后补 M3；其余继续按顺序增量交付。

## 9. 必要验收与验证方式

### 9.1 一条完整的手动验收路径

使用一场 3 阶段、至少 3 名角色的生日会或旅行活动，包含两个群聊/会话、朋友圈、长消息、至少 3 个图片槽位及 1 段带音频的已有视频：

1. 从企划创建活动，概览提示生成文本；现有手动创建仍可用。
2. 生成文本，预览实际群聊/朋友圈；采用前原内容不变，采用后记录和槽位关联正确。
3. 锁定一个满意阶段，重新生成其他阶段；被锁定阶段没有被替换。
4. 勾选三个图片槽位，选择一次配置并提交；切换到素材库仍可查看任务进度。
5. 人为模拟一项明确失败，其他成功候选保留；重试只处理失败项。
6. 每槽位选择结果，批量采用；聊天和朋友圈能打开实际图片，旧候选可回看。
7. 修改一个角色的服装，看到相关槽位来源变化；仅重做所选项，并能打开旧提示词快照。
8. 改写一条未锁定聊天，其他记录和媒体关联不变；锁定记录不能被自动覆盖。
9. 自动编排，检查多会话切换、长内容滚动、图片展开、视频声音、朋友圈评论。
10. 导出三种格式，工作工程再导入后关键引用有效；HyperFrames 工程在可用环境完成一次真实渲染。
11. 另存为模板，用新角色创建活动，确认没有旧记录/资源绑定；做一次临时目录备份恢复检查。

没有真实模型或 ComfyUI 时，可以先用可控返回完成业务验收，但交付记录必须分别说明“接口模拟通过”和“真实联调待完成”。不为获得测试结果修改用户实际角色库或现有活动。

### 9.2 应补的少量关键回归

优先扩展现有活动、图像、Generation、Worker 和导出测试，不为每个 UI 文案编写测试。

| 回归 | 必须证明的行为 |
| --- | --- |
| 文本候选采用 | 锁定/过期候选不能覆盖；批量采用失败不留下半批新内容；重复采用不重复追加 |
| 阶段继续生成 | 成功前序候选保留并进入上下文；取消后迟到响应不写入 |
| 媒体批次幂等和恢复 | 同一项只创建一个业务提交；已提交但未写回关联时可找回；未知结果不自动再发 |
| 图片采用 | 未选槽位保留；缺失资源/删除槽位被拒绝；按旧来源生成的结果不会自动覆盖当前绑定 |
| 来源与锁定 | 修改角色只影响有关槽位；锁定阻止自动替换；旧快照不被修改 |
| 模板实例化 | 旧 ID 不泄入新活动；角色映射有效；不带旧任务/聊天正文 |
| 回放和导出 | 多会话定位正确；真实媒体打包；工作工程导入后新增策略/来源引用可解析 |
| 完整备份 | 未 pinned 但被引用的媒体仍在包里；跨目录恢复不依赖旧绝对路径 |

必要命令，按改动范围使用：

```bash
npm run typecheck
npm run test --workspace @sthstart/service
npm run build:portal
```

修改契约、前端纯逻辑或 Worker 时，分别运行已有 `npm run test:contracts`、`npm run test:portal`、`npm run test:windows-worker`；检查修改文件的 lint 和 diff。无需每一步反复运行全部端到端测试，也不以已有测试总数作为完成度指标。
