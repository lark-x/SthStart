## 1. 产品目标与完整使用路径

用户希望持续维护原神、星铁等作品的创作资料，减少每次活动重复查人物关系、地点和剧情的时间。资料也包括社区解读、个人设定和随手笔记。

首次使用：

```text
选定作品和常用角色
  → 写资料 / 引用叙事档案 / 发起专题搜集
  → 保存有出处的原始摘录
  → 按需整理为人物关系、地点等创作资料
  → 企划选择本次参考内容和要求
  → AI 生成多套活动方案并给出主要依据
  → 用户采用方案，进入现有活动制作和导出流程
```

再次使用：

```text
选择主角、作品和主题
  → 推荐已有资料
  → 仅对缺失或近期问题补查
  → 用户确认本次参考范围
  → 生成新的独立活动
```

没有明确主题时仍沿用“话题素材 → 点子 → 企划”。不强制每次活动经过搜集和整理。

### 1.1 各模块的边界

| 模块 | 负责内容 | 不承担的职责 |
| --- | --- | --- |
| 创作资料库 | 可编辑资料、来源关联、个人设定、参考范围 | 不接管全部剧情原文、不自动改人设 |
| 叙事档案 | 批量剧情、任务、台词、实体与原文检索 | 不为每句台词生成一篇笔记 |
| 搜集任务 | 搜索、必要的补读、保存来源、整理候选 | 不直接发布活动、不覆盖用户正文 |
| 话题素材库 | 近期热点、新梗、创作契机 | 不作为长期人物设定的唯一来源 |
| 角色人设库 | 生成时使用的人设、外观和参考图 | 不因资料搜集结果自动变化 |
| 活动企划 | 本次参考内容、要求、方案与依据快照 | 不改变其他活动的设定 |

MCP 是资料访问方式，不是可信度等级；本地资料也不天然准确。官方来源、社区解释、AI 推断和个人设定需要区分。

### 1.2 本计划不做的内容

- 全量原神、星铁百科及所有版本的实时自动同步。
- 自动抓取任意网站的通用爬虫、自动适配未知 MCP 工具。
- 自动推断并维护完整人物关系图。
- 多用户协作、组织权限、审批流、企业审计、高可用调度。
- 离线运行 MCP / LLM；跨设备实时冲突合并。
- 自动把历史活动剧情变为所有活动的共同世界设定。
- 语义检索、知识库聊天问答、资料关系可视化：保留扩展空间，但不计入本次三轮必做项。

### 2.1 已发现的实现注意点

1. 旧笔记种类 `kind` 与阶段 `stage` 已经存在，不能用新枚举粗暴替换。
2. 笔记更新目前会规范化整个请求体；新增字段缺失时不能被旧客户端同步重置。
3. 当前笔记列表有最多 300 条的限制。新分页与服务端检索不能只在这 300 条中筛选。
4. 现有离线同步直接处理 `CreativeNote`，只改服务端会造成元数据丢失或前端响应校验失败。
5. `planning_research_tasks` / `ResearchTask` 需要 `sessionId`，长期搜集定义和执行记录应独立持久化。
6. 当前话题调度面向一组全局设置；多专题任务需要独立的启停、下次时间和运行占用。
7. 叙事库已有实体别名、原文索引和来源结构，优先利用，不另建一份完整剧情数据库。
8. Akasha 的文件路径和原文行号需要准确保留。现有去空行后重新编号不能直接当作远端真实行号；接入引用时需修正或明确保存两种定位。
9. 搜集能读取某个文档不等于能够枚举全站或按版本增量同步。界面必须按实际连接器能力展示操作。

## 3. 全局产品规则

### 3.1 简单记录优先

- 新建资料只要求标题和正文；允许空标题使用默认名称。
- 作品、角色、地点、类型、来源、参考状态均可后补。
- 原“创作笔记”显示名称改为“创作资料库”；优先保留 `/apps/notebook`、内部应用 ID 和旧深链接。
- 第一轮只上线“资料”，第二轮再上线真实可用的“搜集任务”“待整理”，不留假入口。
- 新的自由笔记默认“仅记录”；用户选择资料模式或开启“可供 AI 参考”后进入默认推荐。
- 迁移旧笔记时：`stage=reference` 且非日记可默认参考，其余默认仅记录；不改正文、不自动判定为原作事实。
- 仅记录的内容不自动检索进提示词；用户可以显式选择“仅本次使用”，不用改变全局状态。

### 3.2 来源、整理和推断分开

至少区分三条轴，前端可收起在“资料属性”内：

| 轴 | 建议值 | 说明 |
| --- | --- | --- |
| 内容性质 | 原作资料 / 社区解读 / 个人设定 / 未确认 | 描述内容的性质，不表示审核结论 |
| 形成方式 | 手写 / 原文摘录 / AI 整理 / AI 推断 | AI 摘要可以引用原作，但推断不能冒充原文 |
| 使用状态 | 仅记录 / 待整理 / 可参考 | 控制默认推荐；不设置繁琐审批 |

- 原始摘录保留，AI 摘要不能替代或覆盖原文。
- 一个结论可引用多个来源；不同说法可以并存，不根据出现次数自动判真。
- 来源时间区分发布时间、搜集时间、最后检查时间；不知道的字段留空。
- 来源没有提供版本号时不能拿搜集日期伪装为游戏版本。
- “未找到资料”与“角色之间没有关系”含义不同，前者不能转成后者。

### 3.3 活动独立与引用快照

- 保存引用时冻结实际传给 AI 的内容，不只保存资料 ID。
- 每个企划生成任务、候选及最终采用方案记录自己的依据，不能从当前笔记重算旧候选来源。
- 修改来源不自动修改方案；提示更新，用户主动选择刷新参考后再生成。
- 旧活动没有知识库字段时按空引用处理，全部旧路径可继续使用。
- 历史活动回流资料库必须是用户主动操作，默认标记个人设定，不自动供所有活动参考。
- 出处删除或无法访问时仍可读历史快照，跳转显示“源资料已不可用”。

## 4. 数据与接口设计约定

本节约定必须表达的信息，不要求逐字复制表名。使用现有 SQLite、JSON 字段和简单索引即可，不引入复杂存储系统。

### 4.1 资料元数据

在 `creative_notes` 上增量扩展，或建立以 `note_id` 唯一关联的元数据表。对外作为 `CreativeNote` 的可选 `knowledge` 信息返回。

建议包含：

- `schemaVersion`：元数据格式版本。
- `works`：作品键、显示名称及必要别名。
- `characters`：本地人设 ID（可空）、作品、角色名称；未导入人设也能关联。
- `locations`：作品、地点名称；第一版不要求建立完整地点库。
- `category`：关系、性格表达、喜好、地点、剧情、灵感、其他。
- `nature`、`authorship`、`usage`：对应上一节三条轴。
- `sources`：所引用的来源条目及摘录定位。
- `contentRevision` / `contentHash`：与实际可参考内容相关的版本标记。

不要要求用户把所有已有笔记和角色归一化才能使用。作品名称优先复用现有规范和别名；同名角色不能跨作品自动合并，多张人设卡也不能强制合为一张。

### 4.2 来源条目及版本

建议 `knowledge_sources` 保存来源身份，`knowledge_source_versions` 保存获取到的不同内容版本；也可采用等价结构。

来源身份字段：来源种类（网页、MCP、叙事、话题、手工）、提供方 ID、作品、外部文档键、URL 或定位信息、标题。

版本字段：内容 hash、原始摘录、发布时间、获取时间、可用版本标签、是否截断、出处性质；模型整理文本与原始内容分开。

规则：

- 同一来源身份且内容相同：更新最后检查时间，不新增重复待整理项。
- 同一来源内容变化：保留新旧版本并提示变化，不覆盖已采用摘要。
- 不同 URL 或来源不能只凭相似标题强行合并；允许整理时组合引用。
- 去重不会抹掉结果与本次任务的关联。同一资料可被多个任务发现。
- 正文相同但发布时间等重要元数据变化可以更新元数据，不必伪造正文新版本。
- 被引用的来源版本不能被普通运行日志清理删除；至少保留引用快照。

### 4.3 搜集定义与执行记录（第二轮）

建议独立保存：

| 对象 | 关键字段 |
| --- | --- |
| 搜集定义 | 名称、目标、作品/角色、专题或近期模式、时间范围、资料源绑定、目标笔记、频率、时区、下次运行、启停状态 |
| 执行记录 | 定义 ID、输入配置快照、触发方式、执行状态、进度、预算、错误、起止时间 |
| 结果关联 | 执行 ID、来源版本 ID、是否新增/变化/重复、待整理状态 |
| 整理草稿 | 目标笔记及基线 revision、所选来源版本、生成文本、生成状态、采用状态 |

定义与运行状态分开：“每周搜集”是定义，不应一直显示为运行中的任务。一次性执行同样留下定义和记录，执行后不安排下一次。

建议执行状态：`queued/running/succeeded/partial/failed/cancelled/interrupted`，映射到现有任务中心状态即可。

### 4.4 企划引用快照（第一轮就完成）

建议定义 `PlanningKnowledgeSnapshot`：

```ts
// 示意结构；通过实际公共契约和运行时校验接入，不只添加 TypeScript 类型。
type PlanningKnowledgeSnapshot = {
  schemaVersion: 1;
  capturedAt: string;
  references: Array<{
    id: string;                         // 本次引用的稳定 ID，供方案引用
    sourceKind: 'note' | 'narrative' | 'collection' | 'topic';
    sourceId: string;                   // 仅用于来源解析，不作为唯一内容依据
    sourceVersion?: string;
    contentHash: string;
    title: string;
    usage: 'background' | 'requirement';
    nature: string;
    authorship: string;
    excerpt: string;                    // 实际用于生成的内容
    locator?: Record<string, unknown>;  // 作品、文档、块、台词等定位
    evidence: Array<{
      title: string;
      excerpt: string;
      url?: string;
      locator?: Record<string, unknown>;
      retrievedAt?: string;
    }>;
  }>;
};
```

- 引用快照保存到企划会话，提交生成时复制进任务请求和候选输入，采用后进入 `activity.planningBasis`。
- 方案主要人物、地点和阶段理由可返回 `referenceIds`；服务端只接受本次真实存在的引用 ID。旧输出没有此字段仍兼容。
- 无效 ID 不显示成真实引用，标记依据未匹配；不必因一个引用问题丢掉整个可编辑方案。
- 候选在参考选择改变后沿用已有版本过期规则，不可把新依据错误贴到旧方案上。
- 资料服务在保存时读取权威内容并校验版本，避免“预览的是旧资料，实际生成却用了新资料”。

### 4.5 建议接口范围

沿用当前管理 API 前缀、鉴权与前端 API client。以下是相对资源的职责，具体命名可调整：

| 轮次 | 接口职责 |
| --- | --- |
| 一 | 扩展 `notebook/notes` 的元数据、过滤、分页；资料来源和被引用记录 |
| 一 | `knowledge/search` 查询笔记和本地叙事片段；来源解析、引用预览 |
| 一 | 在已有企划保存/生成接口扩展资料选择与快照，不新建平行企划接口 |
| 二 | `knowledge/collections` 定义 CRUD、执行、暂停；运行详情、取消、重试 |
| 二 | 待整理列表、保留/忽略、整理草稿生成与采用；话题收藏 |
| 三 | `knowledge/recommendations`、引用更新检查、缺失问题补查入口 |
| 三 | 复用叙事导入预览/提交，增加与资料整理和来源更新的联动 |

来源解析、快照编译、搜索建议放在服务端模块供多个路由调用，不在同一后端内部 HTTP 回调自己的接口。

## 5. 第一轮：资料可用于企划

### 5.1 必须交付的功能

1. 创作笔记改名为创作资料库，保留现有编辑和离线体验。
2. 新资料元数据，作品/角色/类型/性质/参考状态筛选。
3. 为资料关联手工出处、已有叙事台词或片段。
4. 企划中搜索并选择笔记和本地叙事摘录。
5. 区分背景参考、本次要求，预览实际引用内容。
6. 生成方案保存并展示主要依据，支持源头跳转。
7. 工程导出导入保留引用；无知识库的旧工程正常打开。

### 5.2 页面设计

资料页延续现有列表与详情布局：

```text
创作资料库                       [新建资料]
[搜索标题、正文、角色…]
[作品] [角色] [资料类型] [更多筛选] [清空]

资料列表                         资料详情
  标题 / 作品 / 参考状态           标题与正文编辑
  摘要                            [资料属性：默认收起]
                                  来源与摘录
                                  [用于企划] [查看引用记录]
```

- 默认不展示多列技术字段、hash、内部 ID 和大段模型配置。
- 正文保留现有文本、图片、链接、角色引用和叙事引用。
- 选作品后缩小角色候选；角色选择尽量复用现有选择控件，不重写角色管理。
- 窄屏先展示列表，点击进入详情，有清晰返回；过滤条件和列表位置尽量保留。
- “用于企划”可以新建企划或选择已有未完成企划，先进入资料选择预览，不静默触发生成。

企划页面：在已有候选资料区域增加“参考资料”，不强制新增一大步。

```text
参考资料（已选 3 条）     [添加资料] [查看本次引用]
□ 人物关系整理           背景参考     来源：笔记
□ 某段任务对话           背景参考     来源：叙事档案
□ 本次地点和相处设定     本次要求     来源：个人设定
```

- 已选资料可移除、换片段、修改用途；来源正文通过新面板或新页编辑，返回后保留企划输入。
- 搜索弹层提供“资料 / 叙事”切换和出处预览；无结果允许继续企划。
- 本轮手动检索即可，自动推荐留给第三轮。
- 未配置 LLM 时，资料编辑、搜索和选择仍可用；生成按钮解释缺少配置并链接现有设置。

### 5.3 后端和生成链路

- 数据迁移递增新增，不重建旧笔记表，不删除旧字段。
- 扩展 `CreativeNote` 契约、API、缓存键、表单、IndexedDB 内容及同步。
- 请求缺少新元数据时保留服务端已有值；显式空值才代表清空。
- 普通离线正文编辑不得顺便清空来源关联。发生可检测的版本冲突时保留本地草稿并提示重新载入，不实现复杂自动合并。
- 新列表采用服务端筛选和分页；兼容旧 `{items}` 消费者，必要时添加可选分页字段。
- `knowledge/search` 在两个数据库各自查询并汇总，不能假设跨库外键或直接 JOIN；搜索为只读，不顺便触发联网。
- 中文一两个字的名称要有 LIKE 或实体匹配回退，不仅依赖 trigram FTS；参数化查询并处理空搜索。
- 按实际选择编译有长度预算的片段，超限明确显示已截取或要求缩小选择，不能假装整篇都已送给模型。
- 不为每次按键建立全文版本库；使用已有 revision、内容 hash 和实际生成时的引用快照即可。
- 方案提示词分开列出原作背景、未确认解释、本次要求，防止资料中的指令覆盖用户要求。
- 本地来源与现有 MCP research、话题 inspiration 可以共存，不能覆盖旧字段。
- 采用方案后引用保持固定，查看引用记录可从企划/活动快照查询，不需要独立图数据库。

### 5.4 导出与备份

- 工程包包含当前活动实际使用的资料快照及其证据，不打包整个个人知识库。
- 新字段进入现有内容契约、导入校验与版本兼容路径；读者包可展示简要出处。
- 导入其他环境时，本地 note / narrative ID 不能意外绑定到目标机器同名或碰巧同 ID 的对象；只有明确来源对应时建立可跳转关联，否则保留外部来源快照。
- 原始角色库 ID、资料源 ID 不要与活动 actor ID 混用或一起重映射。
- 若引用的是图片说明，本轮冻结说明和出处即可；不能自动声称图片像素已被模型读取。活动实际采用的媒体仍走现有资产打包。
- 全局便携备份覆盖新表和现有笔记附件；恢复后检查来源引用是否仍能解析。

### 5.5 第一轮验收清单

- [x] 旧笔记、图片和深链接可用；标题、正文、标签不丢失。（保持 /apps/notebook、内部 ID 与附件路由不变）
- [x] 新元数据保存刷新后保留，离线编辑后同步不会清空它。（缺省=不改动、显式 null 才清空，有回归测试）
- [x] 可按作品、角色和参考状态找到资料；筛选不是只查首批 300 条。（服务端筛选+分页+分面）
- [x] “仅记录”不自动进入检索参考，显式本次使用可行。（默认只查可参考；显式选择可引用仅记录内容）
- [x] 选一篇笔记和一段叙事原文，生成方案后能看到对应依据。（服务端只接受本次真实存在的引用 ID；浏览器已走查）
- [x] 修改来源后旧候选仍显示原快照；重新生成使用明确确认的新内容。（快照不可变 + 更新检查 + 可固定旧内容）
- [x] 取消引用选择不会修改原笔记或其他活动。
- [x] 工程导出再导入仍可查看引用快照；来源不存在时提示清楚。（回归：导出→导入保留快照与证据链；源删除后仍可读、更新检查标记 missing）
- [x] 不选择任何资料时，原有企划流程正常。

完成记录：填写实际修改文件、关键验证、未覆盖的真实服务条件。

## 6. 第二轮：搜集进入资料库

### 6.1 必须交付的功能

1. 搜集任务的定义、一次执行、每天/每周定时、暂停。
2. 专题不限近期与近期指定范围两种模式。
3. 执行记录、阶段进度、部分结果、取消和手动重试。
4. 待整理列表、来源版本去重、保留/忽略和批量操作。
5. AI 将选中资料整理成草稿，用户采用到新资料或已有资料。
6. 话题收藏到资料库；新任务接入现有全局任务中心。

### 6.2 页面设计

资料库顶栏增加三个切换项：“资料 / 搜集任务 / 待整理”。

新建任务弹层：

| 字段 | 默认与行为 |
| --- | --- |
| 任务名称 | 可根据目标自动填入，允许修改 |
| 搜集目标 | 必填，多行自然语言 |
| 作品和角色 | 可选，从来源资料页带入 |
| 模式 | 专题资料，默认不限时间 |
| 时间范围 | 近期模式默认最近七天，可选范围；不要限制所有专题 |
| 资料源 | 已配置且可用的来源；复用绑定，不在此重复录入密钥 |
| 频率 | 一次 / 每天 / 每周；后两者设置当地时间，周任务选星期 |
| 关联资料 | 可选现有笔记；只关联结果，不自动覆盖正文 |

- 主按钮“保存任务”；另提供“保存并立即搜集”，保存不应意外产生联网调用。
- 无资料源时允许保存为暂停任务，提示去现有设置配置。
- 任务卡显示状态、最近一次结果摘要、下次时间、立即执行、暂停和编辑。
- 编辑任务影响之后的运行；正在运行的任务使用启动时配置快照。
- 删除定义前给简短提示；默认保留已保存资料和来源，避免连带删除创作内容。

待整理卡片展示标题、摘要、作品/角色、来源、获取时间和“新增/有变化”标识。详情可以读原始摘录和历史版本。

操作保持简洁：保留、忽略、整理为资料、用于企划。支持多选；已忽略的同版本不要因下次执行再次弹回，新版本可以重新提示。

“保留”表示可在资料搜索中找到这份来源摘录，不强制创建一篇重复笔记；“整理为资料”才生成可编辑笔记正文。

### 6.3 搜集执行与复用边界

- 抽取现有来源调用、工具参数、原始结果规范化等必要公共函数，保持原话题搜集行为。
- 长期资料任务不能强制添加“新梗/近七天”等关键词，也不能要求必须有关联企划会话。
- 对叙事 MCP 的无 URL 结果保留文档键、行范围和来源名，不能因没有网页链接丢弃。
- 工具仅返回摘要或只读到部分文档时明确记录；不伪装成已获取完整正文。
- 先保存原始结果，再调用模型整理。整理失败时资料仍在，可重试整理而不重复全部搜索。
- 不主动探测、调用资料源声明之外的工具；复用当前可用绑定与适配器即可。
- 沿用有限工具次数、时间预算和并发上限。可先以现有 12 次调用、180 秒、同时 2 个来源为可调整默认值，不承诺一定搜齐。
- 达到预算或部分来源失败，已有结果进入 `partial` 并可使用；全部没有结果时区分无匹配与执行失败。
- 用户取消后停止安排新调用，已完成结果保留。任务结束后迟到的返回不能覆盖取消状态。

### 6.4 定时执行

- 服务内轻量调度，复用现有 tick / 时间计算经验；不引入 Redis、系统 cron 或桌面端自动化。
- 单个定义同一时刻只运行一次，手动点击和定时触发共用占用检查；默认全局顺序执行，来源调用可维持小并发。
- 运行前持久化配置快照和下一次时间，避免刷新或重复 tick 产生同一任务。
- 后端重启把未完成记录标记为中断；每个错过时间的启用定义最多补跑一次，不追补停机期间所有周期。
- 暂停停止未来调度，取消当前运行是另一个明确操作。
- 时区默认沿用用户当前设置，没有设置时用 `Asia/Shanghai`；每天/每周按当地时间计算。
- 浏览器关闭不影响任务，后端停止不会执行，页面说明这一实际限制即可。
- 全局任务中心只列执行记录，跳转到对应详情；只暴露已实现的取消/重试能力。

### 6.5 AI 整理与采用

- 用户选择来源、整理方向和目标笔记；模型返回草稿和对应来源 ID。
- 界面分为“原资料 / 建议整理”，新建目标可只显示草稿与来源。
- 提供“保存为新资料”“追加到原资料”；替换指定内容仅在明确展示差异后进行。
- 采用前校验目标笔记 revision；生成期间目标已编辑时保留草稿并要求重新预览，不能覆盖新正文。
- 来源集合和版本随草稿冻结，刷新后可继续采用。
- 不做复杂逐句引用评分，只保证展示的引用属于实际输入且可查回原文。
- 不自动更新角色人设、外观、旧企划和已采用活动内容。

### 6.6 话题收藏

- 在话题卡片增加“收藏到资料库”；保留话题身份、摘要快照和原有来源。
- 重复点击返回已有收藏，不复制第二份。
- 话题后续更新可提示变化，不直接改写用户整理的笔记。
- 现有“话题 → 点子 → 企划”流程继续存在；收藏不是创建活动的强制步骤。

### 6.7 第二轮验收清单

- [x] 一次性专题任务不绑定企划、不限制最近七天，可以得到有来源的结果。
- [x] 每天/每周任务可保存、暂停、执行；刷新可看到历史和下次时间。
- [x] 同任务运行两次，相同内容不重复入待整理，新版本可辨认。
- [x] 多任务发现同一来源，分别保留任务关联，不复制原文版本。
- [x] 搜集部分失败仍可使用成功结果，重试整理不必重新搜索。
- [x] 搜集不会覆盖关联笔记正文，采用草稿时能发现目标已被编辑。
- [x] 未整理条目可显式选入企划，展示未确认状态与来源。
- [x] 取消、重启中断和补跑一次符合页面提示，不出现永久运行中的记录。
- [x] 收藏同一话题两次只得到一份关联资料。
- [x] 现有热点搜集、MCP 企划调研、任务中心继续可用。（话题与企划原测试全绿；任务中心新增资料搜集域）

完成记录：除正常路径外，至少说明一次重复搜集和一次部分失败的实际验证结果。

## 7. 第三轮：推荐、补查、更新与批量维护

### 7.1 必须交付的功能

1. 按作品、角色和主题推荐已有资料，给出简单推荐原因。
2. 企划可以先使用本地资料，再针对缺失问题补查。
3. 显示已引用资料的更新，选择性刷新，不自动重写方案。
4. 复用规范化 JSON / 已有叙事来源完成批量导入与资料整理的联动。
5. 角色详情查看关联资料，活动可主动回流个人设定。
6. 三轮流程完整串通，并补充个人使用说明。

### 7.2 本地推荐

- 输入作品、已选角色、地点、活动主题和用户关键词；不默认查询全部个人笔记。
- 优先级建议：明确关联角色 > 同作品同地点或同主题 > 标题/标签命中 > 正文命中。
- 复用人物别名，跨作品同名分开；没有明确作品时展示分组供选择，不直接合并。
- 优先推荐可参考资料。个人设定单独分组，不自动压过原作；待整理结果只在用户展开时加入。
- 展示“关联主角”“包含地点资料”“匹配生日主题”等原因，不展示虚假的概率或权威评分。
- 默认展示有限数量，允许查看更多；只推荐，不自动全选或触发联网。
- 本地没有找到内容时说“资料库中暂未找到”，不能宣称整个作品没有相关事实。

### 7.3 缺失问题与 MCP 补查

在企划参考区提供“补充搜集”：

```text
现有资料：人物关系 2 条，地点 1 条
可补查的问题：
  □ 是否有与主角相关的近期剧情？
  □ 是否有能支持该地点安排的资料？
  [自行填写问题]
[仅用已有资料生成] [搜集所选问题]
```

- “缺失”是本次检索范围中的缺口；简单分类检查即可，不要求全面事实评估模型。
- 可选让模型起草问题，但模型失败时用户仍能手动填写并继续。
- 补查复用第二轮任务，可附加企划会话 ID 用于返回，不以会话 ID 作为任务存在的前提。
- 结果存入待整理并返回当前企划选择区；生成前由用户选择，不自动纳入所有结果。
- 保留用户已选人物、地点、阶段和其他表单输入；返回或刷新可以继续。
- 近期动态提示检查资料日期，但不每次打开页面自动联网。
- 现有企划 research 入口保留；避免同一点击同时启动旧调研和新补查两份任务。

### 7.4 来源更新与活动返工

- 用户打开已有企划或点击“检查资料更新”时比较本地引用内容 hash / revision，不逐条联网检查。
- 收藏、标题之外的可参考正文或引用原文变化才构成内容更新；收藏星标变化不提示所有活动返工。
- 显示旧摘要、新摘要和来源状态；可以选择部分引用更新，或继续使用旧版本。
- 更新参考会修改企划输入版本，旧候选保留并按已有机制提示过期，不改写候选输入。
- 对已创建活动，先保存明确的新依据版本；需要重构方案时进入带原资料和活动设置的企划草稿，再明确采用。
- 若只调整活动某段内容，沿用现有编辑/局部返工入口。无法定位具体影响时列出涉及引用的范围供用户选择，不把全部镜头自动加入生成队列。
- 普通资料更新本身不启动文本生成、生图或回放重建。
- 源头跳转支持定位到笔记块、来源条目、叙事台词或网页；定位失效时展示快照并说明原因。

### 7.5 批量导入与作品维护

本轮保证至少一条确定可用的批量路径：**已有规范化 JSON 叙事导入 → 预览差异 → 提交 → 本地检索 → 选片段整理为资料 → 用于企划**。

- 沿用现有 `NarrativeImportBundle` 和导入接口，不要求适配任意原始游戏数据仓库。
- 从资料库提供导入入口跳到现有预览流程，导入后回到对应作品的资料视图。
- 预览新增、变更和不变内容；重复导入同一数据不重复生成知识笔记。
- 原文按稳定来源键和版本更新；已有引用快照不变。用户整理文本只提示来源更新。
- 允许选多个原文片段整理一篇资料，或小批量按主题生成草稿；每篇保留来源。
- 资料库可显示“原神相关资料”筛选视图，不新增强制维护的项目层级。
- 本地角色与叙事实体建议匹配，存在多个候选时由用户选择；未匹配不阻止导入。
- 已配置 Akasha 时复用搜索、读取、按需收藏。不承诺其具备全量枚举或增量版本接口。
- 对 `readAll` 页数上限、剩余字符和真实行号做必要处理；截断结果必须如实显示。
- 原神/星铁之外的作品允许手动命名和规范 JSON 导入，不把所有 UI 写死为两款游戏。

### 7.6 角色关联与活动回流

- 角色详情增加“相关资料”入口，按角色与作品查询；可从该角色发起专题搜集。
- 资料可以关联尚未导入人设库的人物，不要求先创建人设卡。
- 修改人设继续走原有编辑流程。资料可提供参考，但不实现自动覆盖或全角色批量重写。
- 活动提供轻量“整理为个人设定”：选择片段、预览新资料、保存；默认仅记录，用户可再开启参考。
- 新资料注明来自哪个活动及当时版本，不能冒充原作剧情。

### 7.7 第三轮验收清单

- [x] 选择同作品常用角色后能推荐已有相关资料，并显示可理解的原因。
- [x] 跨作品同名角色不会默认混用，未选资料不暗中加入提示词。
- [x] 从企划发起补查，结果进入待整理，返回后原企划输入不丢。（补查只走弹层，不离开页面；结果可回填参考资料）
- [x] 资料不足或 MCP 失败时仍可仅用已有资料生成。
- [x] 修改已引用正文显示更新，修改收藏状态不产生无意义更新。
- [x] 选择更新一个引用不会替换其他引用，也不会自动改旧活动。
- [x] 同一规范 JSON 导入两次不产生重复知识笔记；变更原文可被发现。（回归：重复导入只保留一份原文、导入不生成资料；上游改文后重新导入仍只有一份，引用更新检查能发现变化并保留旧摘要）
- [x] 原始片段 → 整理资料 → 企划方案的出处能逐层跳转。
- [x] 活动回流明确为个人设定，不自动成为其他活动的背景。
- [x] 角色人设、话题点子、活动返工、工程导出和普通离线笔记没有明显回归。（契约 16 / 服务端 274 / 门户 10 全绿，构建通过）

完成记录：用一个完整活动演示“首次积累、再次复用、只补查缺口”的路径。

## 8. 实施顺序与文件组织建议

每轮遵循：契约与迁移 → 服务层 → API → 前端 → 关键回归 → 使用说明。不要先堆完三个页面再补后端。

可新增 `apps/service/src/knowledge/`，按实际复杂度拆分：

- `store.ts`：资料元数据、来源版本、引用关系。
- `search.ts`：资料与叙事联合检索、第三轮推荐。
- `references.ts`：引用解析、快照编译、更新检查。
- `collections.ts`、`scheduler.ts`：第二轮定义、执行与定时。
- `organize.ts`：第二轮整理草稿与采用。
- `routes.ts`：新增接口，保持旧 notebook 路由兼容。

前端可继续在 `app/features/notebook/` 扩展，抽取资料选择器供企划和其他入口共用。不为了文件夹名称重构整个应用。

必要关联改造：

- `server.ts`：应用显示名称、路由注册、服务启动与调度停止。
- `database.ts`：迁移按最新编号递增，旧库启动正常。
- `packages/contracts/src/index.ts`：数据和响应校验、任务类型、企划引用兼容。
- `app/lib/query-keys.ts`：筛选、分页、资料更新后的缓存失效。
- `planning.ts`：输入编译、任务、候选、采用和恢复会话贯通。
- `tasks/adapters.ts`：新执行记录映射，过滤查询与按钮能力一致。
- 导出、导入与便携备份：核对 schema 白名单、数据清单、跨环境引用。

关键检索与资料快照服务直接接收数据库依赖；避免把多个领域职责全部塞进现有巨大文件。

## 9. 适合个人项目的验证要求

### 9.1 必须做的验证

只覆盖容易造成资料丢失、错误引用和任务重复执行的关键逻辑，不要求测试覆盖率数字。

建议少量自动回归覆盖：

1. 旧笔记新增元数据后的保存与旧请求兼容。
2. 同源同内容去重、同源变化保留版本。
3. 快照不随源笔记更新，候选采用使用原任务依据。
4. 整理期间目标笔记被编辑，不静默覆盖。
5. 同一个搜集定义避免重复运行；重启、取消保留已有结果。
6. 活动工程跨环境导入不误绑定本地来源。

其余页面行为可手动走查，不需要为按钮外观、字段映射等可逆小改动逐项写测试。

适用命令以当前脚本为准：

```sh
npm run typecheck
npm run test:contracts
npm run test --workspace @sthstart/service
npm run build
```

开发中优先运行受影响测试；整体完成后运行上述适用检查。修改前端公共工具时补相应已有测试。无需反复运行无关邻舍、GPU 或全部浏览器矩阵。

### 9.2 三个手动场景

**场景 A：普通记笔记**

写一篇随记，插入图片，离线编辑后恢复连接。正文与资料属性保留，没有被自动加入企划或触发网络搜集。

**场景 B：生日活动首次积累**

准备一个作品、两三名角色及几个地点的样本。搜集或导入关系资料，整理一篇笔记，选择一个原文片段，生成多个企划方案，查看依据，采用并导出工程。

**场景 C：第二次活动复用**

为同一批角色建立旅行或聚餐活动。推荐已有资料，只补查一个问题。更新一篇来源后，新企划可采用更新，旧活动仍保留原依据。

样本可以是明确标记的虚构测试资料，不能把模型编造的角色关系作为真实游戏知识交付。

### 9.3 不要求的验收

- 不要求企业级压力测试、性能 SLA、渗透测试、复杂灾难恢复。
- 不要求多个浏览器和设备完整矩阵；桌面主路径加一次窄屏检查即可。
- 不要求真实 ComfyUI、生图质量或视频成片作为本计划完成前提。
- 不要求完整收录某款游戏或人工逐条验证所有游戏事实。
- 真实 MCP 不可用时可通过模拟适配器验证功能，但交付明确标出“真实来源未联调”，不能宣称已经实测。

## 10. 完整交付与完成判定
