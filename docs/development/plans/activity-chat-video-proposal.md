# 活动工作室方案修订：聊天内容与 HyperFrames 视频

状态：讨论稿。供模型直接实施的完整规格已汇总至 [独立应用开发规格与模型交接计划](ACTIVITY_STUDIO_IMPLEMENTATION_SPEC.md)，请以该文件为准。用户已选择第一版由应用导出可渲染的 HyperFrames 工程，在外部生成视频；应用内一键 MP4 不进入第一版。

## 1. 最新目标与架构结论

用户需要图片、视频、群聊记录、朋友圈记录，主要以聊天与动态形式呈现；之后用 HyperFrames 制作模拟手机或 iPad 录屏视频，包含文字滚动、展开图片、播放消息内视频、切换朋友圈等片段。

保留已明确需求：独立活动、主题/人物/地点选择、至少两个可增删的阶段、阶段内容可空白或指定、基于人设的 AI 预览、编辑/重做/恢复历史、完整媒体打包。

建议定位为 SthStart 的独立“活动聊天创作与回放应用”。邻舍不再是运行依赖，不增加其数据库、群聊引擎或朋友圈写入改造；可选的一次性静态人设导入与核心隔离。

内容生产和视频表现分别管理：

```text
活动设定 + 角色快照 + 阶段要求
          ↓
AI 生成可编辑的聊天/朋友圈记录与媒体需求
          ↓
采用内容版本 + 选定图片/视频
          ↓
回放脚本 + 手机/平板模板 + 固定素材
          ↓
HyperFrames HTML 工程 → MP4
```

不要求每场活动在后台持续模拟角色生活。AI 可以按阶段批量生成多角色记录，再根据用户编辑继续扩写；活动事实和摘要足以作为第一版一致性基础。

## 2. 三类数据，分别版本化

### 2.1 内容记录：发生了什么

保存活动、阶段、角色与外观快照、会话、消息、帖子、评论、媒体引用、阶段事实摘要。

消息具有稳定 ID、说话角色、所属会话、文字、媒体引用和故事时间；帖子和评论同样具有稳定 ID。保留来源阶段与采用版本。

AI 输出结构化记录，不直接生成整段 HTML，也不把聊天记录烘焙为图片。规则校验角色身份、消息顺序、事实约束和媒体引用，用户可逐条修改。

必要的旁白可以显示为时间分隔、系统消息或转场卡，不把独立图文实录作为核心内容页。群聊与朋友圈的完整记录始终可独立导出，不能只剩最终 MP4。

### 2.2 媒体资产：记录引用什么

中央 Artifact 保存原图、原视频、头像和必要参考素材；消息、帖子和版本对媒体建立引用保护。

分开记录镜头需求与最终选片。图片/视频可生成或上传；一次重拍只创建媒体候选，不重写整个阶段。

区分“消息里的视频素材”和“最终模拟录屏视频”：前者来自 AI 视频工作流或上传，后者由 HyperFrames 合成。即使没有可用的 AI 视频模型，只要已有视频素材，仍可制作包含视频播放画面的最终成片。

### 2.3 回放脚本：观众如何看到

建议定义应用自己的 `playback.json`；它不是 HyperFrames 原生输入格式，必须由导出器编译成 HyperFrames HTML composition 和对应时间轴。

回放动作包括：打开会话、显示新消息、滚动到消息、阅读停留、展开图片、关闭图片、展开视频、播放指定片段、返回会话、切换朋友圈、滚动到帖子、展示评论、阶段转场。

每个动作记录稳定目标 ID、开始时间、时长和动作参数。视频动作另记录素材起点、播放时长、音量与裁切方式。仅使用屏幕像素坐标会在文字修改和设备变更后失效，因此优先引用消息/帖子/媒体 ID，由模板计算布局。

明确两种回放模式：

- 阅读历史：记录已存在，镜头通过滚动、展开媒体和切页进行观看。
- 模拟实时聊天：消息按脚本逐条出现，可显示打字提示、发送动作和通知。

二者可以混合，但需要在片段中明确，避免所有历史记录都被误做成新消息。

记录的故事时间、实际生成时间、视频播放时间分别保存；活动过了两小时，不代表视频必须播放两小时。

## 3. 产品界面收敛

建议保留四个工作区：

1. 活动设定：主题、人物、地点、阶段与锁定要求。
2. 记录编辑：群聊/朋友圈切换，预览、逐条修改、生成候选、采用和恢复版本。
3. 媒体：镜头、生成/上传、选片、检查消息和帖子中的引用。
4. 成片预览与导出：设备、观看身份、播放顺序、阅读速度、展开哪些媒体、导出范围。

群聊、朋友圈是主呈现方式。相册作为素材管理工具；独立活动实录页可省略或退为自动导出的附属文档。

模拟屏幕需要“观看身份”：同一条记录从不同人的设备查看，自己的气泡位置、头像及部分可见内容可能不同。第一版默认一个固定观看身份，切换身份只改变展现，不能重新生成故事。

第一版建议一个固定的手机界面模板，提供画幅和文字大小等必要参数；平板模板随后补充。这里是成片模板，不是恢复邻舍旧主题系统。

编辑界面继续使用现有 React。视频预览与导出共享独立的 HTML 模板和布局规则，可嵌入应用；不把整个门户或 React 编辑器迁移到 HyperFrames。

## 4. HyperFrames 可行性与需实测部分

已查阅官方资料：

- [官方仓库](https://github.com/heygen-com/hyperframes)：支持 HTML/CSS/媒体与可定位时间的动画，CLI/Producer 可渲染 MP4。
- [Compositions](https://hyperframes.heygen.com/concepts/compositions)：composition 定义时间轴，可组合图片、视频、音频和子场景。
- [Producer](https://hyperframes.heygen.com/packages/producer)：完整捕获、编码和音频处理入口。
- [Player](https://hyperframes.heygen.com/packages/player)：可嵌入页面的预览组件。

因此模拟设备里的聊天、滚动、图片展开和视频播放有可行的技术基础，但目前尚未在本仓库渲染验证，不把官方基础能力当成已经完成的聊天模板。

实现原则：

- 画面由播放时刻决定；直接跳转到第 20 秒也应得到正确屏幕，无须先执行前 19 秒的真实点击。
- 图片弹窗、页面切换、手指/触点提示与滚动是可定位时间的状态或动画。
- 视频/音频片段交给 HyperFrames 的媒体时间轴管理；不依赖真实点击调用 `video.play()` 或自由运行定时器。
- 相对路径素材、固定字体与已测依赖版本进入工程，减少换机后布局和渲染差异。
- 渲染过程中不调用 LLM，也不从实时聊天接口读取内容；先固定采用版本和素材再渲染。
- 字体、气泡换行、长文停留、长列表滚动、图片预加载、视频展开时的画面与声音同步需要专门验证。
- 手机与平板按各自布局重新计算内容位置，不能只把手机画面拉宽。

正式开发前先制作一个短技术样片：群聊 → 滚动 → 展开图片 → 返回 → 展开并播放视频 → 切换朋友圈。验证随机时间跳转、首尾帧与音画同步，再确定模板实现和实际工作量。

## 5. 回溯可以简化，但不能取消

采用“内容版本 + 媒体选片版本 + 回放版本”的组合，比恢复长期运行的邻舍角色状态更直接。

- 改文字：创建内容新版，检查后续阶段事实，重算受影响消息的布局和建议阅读时间。
- 重做阶段：保留旧阶段和后续版本；从旧前文事实摘要生成新候选。
- 换照片：保留文本，仅替换选片并更新相关回放。
- 改滚动速度、展开顺序：只改回放版本，不重新调用 AI。
- 换设备模板：只重排画面与回放，不重新写聊天。
- 恢复旧版：同时恢复该内容版本的媒体选择与可用回放脚本。

AI 上下文仍需活动与版本隔离，未采用候选与被放弃的摘要不得进入后续内容。回放动作引用已删除消息时，应显示待修复项目并提供重建建议，不静默跳到另一条消息。

第一版用不可变阶段修订、有效版本指针、阶段事实摘要和任务版本绑定即可，不要求实现通用事件溯源平台、角色后台定时器或复杂情绪模拟。

## 6. 打包扩展为内容包与 HyperFrames 工程

```text
活动项目.zip
  manifest.json          # 格式版本、固定内容版本、文件清单与校验
  activity.json          # 主题、角色快照、阶段和事实
  records.json           # 完整会话、消息、帖子、评论
  playback.json          # 本应用定义的回放动作
  media/                 # 原图、视频、头像及使用的音频
  reader/                # 可离线阅读完整记录
  hyperframes/
    index.html           # 实际可渲染的 composition
    compositions/        # 手机界面、聊天、朋友圈、媒体场景
    assets/              # 可解析的相对路径素材与固定字体
    README.md            # 已验证版本、预览和渲染方法
  history/               # 可选历史
```

逻辑结构如上；打包实现可通过统一的根素材目录避免冗余文件，前提是验证 HyperFrames 的相对路径解析。普通阅读包无需包含工程所需的所有工具依赖。

完整活动内容包包含全部选定记录与素材；回放脚本可选择只呈现其中一部分。视频不必展示每条记录，原始记录也不能因剪辑而丢失。

不能把 `records.json + 图片` 标为“可直接渲染的 HyperFrames 工程”；必须实际生成模板和时间轴，并完成一次解压后渲染验收。

## 7. 代码改动范围

本次分析基于当前仓库结构，尚未实现或测量最终代码行数。按职责评估，属于中等规模新功能，主要新增模块，现有业务边界修改较集中。

| 范围 | 改动方式 | 相对规模 |
| --- | --- | --- |
| 邻舍子模块 | 无必需修改 | 无 |
| 现有角色库 | 复用结构化人设与版本，补快照读取与必要素材授权 | 小 |
| 公共 LLM/媒体服务 | 新活动身份、用途配置、记录与任务关联 | 小到中 |
| 活动与内容后端 | 阶段、预览、生成、修订、摘要和恢复 | 中 |
| 活动前端 | 表单、记录编辑、群聊/动态、媒体选片 | 中 |
| 回放编译器与模板 | 播放动作、布局、可定位时间的动画、媒体展开 | 中，是新增重点 |
| 导出/导入 | 内容与工程打包、实际媒体收集、完整性校验 | 中 |
| 应用内 MP4 渲染 | 可选渲染任务与独立子进程、进度、资源限制、恢复 | 额外中等工作量 |

建议新增目录：

- `app/apps/activities/`：入口。
- `app/features/activities/`：编辑与管理组件。
- `apps/service/src/activities/`：活动、文本生成、版本与导出。
- `packages/activity-playback/`：纯数据回放规则、模板与 HyperFrames 编译；具体打包形式由样片验证决定。

现有边界需调整：应用入口注册、服务路由注册、数据库迁移、共享 contracts、Generation 消费者及内容关联。`generation_context_links` 目前只允许 `character/narrative`，需扩展或增加活动专属关联表；无须为此重写 Generation 引擎。

减量来源：移除邻舍双向同步、长期生活模拟、全局关系回滚与通用可视化工作流编辑器。新增量：可复用录屏模板与回放编译器。不会因为不用邻舍而变成“只做导出按钮”；聊天界面和生成逻辑仍需新增，但可围绕成片目标实现。

## 8. 三种交付深度

| 选择 | 交付 | 改动与使用成本 |
| --- | --- | --- |
| 仅内容包 | 记录 JSON/Markdown + 图片/视频 | 最少应用代码，但每次还需另写录屏模板和时间轴，不建议作为完整目标 |
| 可渲染工程（用户已选定） | 编辑、回溯、媒体、回放规则、预览和 HyperFrames 工程导出 | 模板开发一次，多场复用；最终渲染由用户在外部运行 |
| 应用内一键成片 | 在上一项上增加本地 HyperFrames 渲染与 MP4 归档 | 更便捷，增加进程管理、长任务、资源调度和失败恢复 |

不把完整 HyperFrames Studio 或通用剪辑器嵌入应用作为第一版前提。第一版可用片段列表与参数控制顺序、停留、滚动和媒体展开；如后续确需精细剪辑，再评估编辑器整合。

## 9. 调整后的开发顺序

1. 技术样片：手写固定记录与媒体，完成手机录屏链路和 HyperFrames 本地渲染；先验证风险最高的模板与视频播放部分。
2. 活动与记录：至少两阶段、角色快照、结构化聊天/朋友圈生成、AI 预览、修改与采用；版本结构同时建立。
3. 修订与媒体：阶段重做、恢复历史、事实摘要隔离、图片/视频生成或上传、选片、晚到任务绑定。
4. 回放编辑：自动生成回放脚本、阅读速度、媒体展开选择、固定观看身份、手机模板；平台化后增加平板模板。
5. 正式交付：完整内容包、HyperFrames 工程包、离线阅读、项目再导入与解压渲染验证。
6. 可选增强：应用内一键 MP4、精细时间轴、多模板、实时参与模式、邻舍静态人设导入。

前五步为建议的完整第一版，交付深度已经选定为可渲染工程导出。工期和行数在技术样片与模板细节明确后估算；现阶段不以未经实现的精确行数或复用百分比作为承诺。

## 10. 验收重点

- 同样角色的两场活动无内容或摘要串用；邻舍停止时全链路可工作。
- 用户指定阶段行动不被 AI 擅自改写；自由模式可生成至少两阶段。
- 改动文字后气泡换行、滚动位置与停留合理；不存在引用失效的回放动作。
- 内容版本与回放版本分别恢复；改变滚动速度不触发 LLM/媒体重生成。
- 直接跳到任意播放时间，与从头播放到该时间得到一致画面。
- 图片可展开返回，嵌入视频按指定片段播放且音画同步，之后正确进入朋友圈。
- 完整导出保留未进入成片的选定聊天/动态记录和媒体；工程导出可用已验证版本真正渲染。
- 断线、重试、服务重启和旧任务迟到不会覆盖已采用版本。
- 模板与字体版本固定；手机/平板使用稳定目标 ID，按布局计算位置。
