适用范围：SthStart 独立活动工作室，个人创作使用

## 0. 执行目标与范围

本轮完成四项能力，优先级从高到低：

1. 修改影响提示：知道修改影响了什么，决定哪些需要返工。
2. 候选对比与局部采用：只采用满意部分，保留已满意内容。
3. 模板职责映射：换一组角色就能复用活动结构。
4. 常用创作配置：复用常用生成、回放和导出偏好。

目标路径：

```text
修改本场设定或记录
  → 保存新版本并查看影响
  → 确认保留 / 稍后处理 / 选择返工范围
  → 生成文本候选，或把图片加入待处理清单
  → 对比并采用所选内容
  → 提醒更新回放
```

ComfyUI 不可用时，上述流程仍应可以使用：图片返工只保存待处理项，不发起真实图片生成；文本可用现有模型，开发回归可以使用模拟返回。导出继续交付 HyperFrames 工程，不新增应用内视频渲染系统。

本轮明确不做：自动发布、自动无限重试、通用工作流编辑器、全量语义知识图谱、联网搜索改造、角色库重构、邻舍改造、ComfyUI 升级、另一套任务队列或版本系统。

## 2. 产品规则

### 2.1 保存和返工分开

- 编辑继续使用现有自动保存草稿，不在每次输入时弹确认框。
- 草稿状态可显示轻量影响预览，明确标注“尚未成为采用版本”。
- 点击“保存新版本”后，持久化本次影响；保存不自动生成、不自动更换图片。
- “保存新版本”和“生成所选内容”是两个明确操作。
- 候选采用、检查点恢复、图片配置提交也要进入同一套影响计算，不能只覆盖某个前端保存按钮。

### 2.2 区分影响程度与执行状态

| 用户标签 | 意义 | 默认处理 |
| --- | --- | --- |
| 引用已失效 | 目标、资源或强依赖已删除，当前结构无法正确解析 | 显示具体缺失对象，修复相关引用；不能靠“确认保留”跳过 |
| 生成依据已变更 | 该结果确实使用了已修改的输入，例如镜头使用了角色旧服装 | 提示复核，可确认保留；不宣判旧图片一定不好 |
| 可能受影响 | 结构关联或已有文本上下文提示需要检查，但不能证明内容冲突 | 默认不勾选重新生成 |
| 回放需更新 | 文本、媒体、顺序或会话改变，使旧回放版本落后 | 提供更新回放入口，旧回放保留 |

独立展示“已锁定”“任务进行中”“等待图片服务”等状态。锁定不是影响程度，服务不可用也不是生成失败。

### 2.3 用户决定应持续有效

支持四种操作：

- **确认保留**：当前变化下仍保留此结果。
- **稍后处理**：保持待复核，关闭页面不丢失。
- **加入返工**：进入该活动的待处理列表，尚未提交模型任务。
- **查看/修改源头**：定位本场角色、阶段、记录、镜头或图像配置。

确认针对具体变更与具体结果生效。以后源头再次变化，应产生新的复核项；不能永久豁免某个角色或镜头。刷新后不反复提示已确认的同一次变化。

### 2.4 满意内容和历史结果保留

- 锁定阶段/记录不能被生成、采用或普通保存绕过；解锁继续走现有明确操作。
- 锁定媒体允许看到影响，但不默认进入替换流程。
- “确认保留旧图”不改写它的 prompt、seed、recipe 或 source fingerprint。显示“按旧设定生成，已确认保留”。
- 生成成功不自动采用，也不自动消除对应复核项。采用与本次变更匹配的结果后才自动完成该项。
- 无法读取的文件、已删除对象等结构性问题，仍按原有导出/引用校验处理。

## 3. 模块 A：修改影响与待处理清单

### 3.1 统一分析入口

建议新增 `apps/service/src/activities/change-impact.ts`，保留 `image-impact.ts` 的现有接口作为兼容入口或图片分析适配器。

核心分析器接收前后文档和相关版本，返回结构化结果，不直接执行任务：

```ts
analyzeActivityChanges({
  beforeContent, afterContent,
  beforeImageConfig, afterImageConfig,
  currentMediaRevision, currentPlaybackRevision,
  adoptedAssetProvenance,
}): ActivityChangeImpact
```

先实现确定性规则。首版不调用 AI 分析每次修改，不引入向量库或语义分类服务。

### 3.2 比较对象和规则

按稳定 ID 比较实体与字段，忽略更新时间、任务进度、锁定切换等不会改变生成内容的管理字段。只格式化 JSON 或调整对象键顺序不应产生变化；正文、顺序、参与者等有意义内容正常比较。

| 修改 | 直接影响 | 可能影响 | 通常不影响 |
| --- | --- | --- | --- |
| 角色本场服装/外观参考 | 使用该字段的图片配方及对应采用图 | 包含角色、但无来源快照的旧图片 | 没有该角色的图片、无外观描述的聊天 |
| 角色说话风格/身份/关系 | 实际以这些字段为输入的未采用候选 | 有关角色发言、动态及相关阶段 | 不相关角色和未使用这些字段的视觉输出 |
| 阶段地点 | 明确使用该地点的图像/候选 | 同阶段描述地点的记录 | 有独立固定地点的其他阶段 |
| 活动默认地点 | 继承默认地点的阶段与镜头 | 未记录明确地点来源的旧内容 | 已显式覆盖地点的阶段 |
| 阶段关键事实/事件 | `sourceFactIds` 等显式引用该事实的对象 | 生成时读取过此前序上下文的后续阶段 | 无关联的前序阶段 |
| 一条聊天的措辞 | 该记录对应回放 | 只有在被后续输入引用时提示后续检查 | 无直接依赖的全部图片 |
| 图片镜头描述 | 当前槽位图片与相应候选 | 引用该镜头叙事的记录 | 其他镜头 |
| 图像全局画风/负向词 | 实际继承这些字段的图片 | 缺乏配置来源的旧图片 | 文本、明确使用槽位覆盖配置的相关字段 |
| 消息顺序/会话、媒体采用结果 | 回放 | 依赖顺序的内容 | 已生成图片本身 |
| 删除消息、动态、事实、槽位 | 显式引用已删除对象的记录、候选和回放动作 | 有相关上下文的内容 | 无关联实体 |

同一目标被多条规则命中时合并展示，保留多个具体原因。原因应为“这张图片使用了甘雨的服装描述”，而不是“依赖哈希发生变化”。

没有完整来源的旧内容只能标注“可能受影响/来源不完整”，不得伪造精确依赖。对未编译镜头可以使用角色、阶段、事实等结构关系提示，但不能声称它已经使用了某份旧配方。

### 3.3 文本依赖的最小增强

在现有生成请求快照/候选 scope 中增加可选、带版本号的依赖描述：

```ts
type GenerationDependency = {
  entityKind: 'actor' | 'relationship' | 'stage' | 'fact' | 'message' | 'post' | 'activity';
  entityId: string;
  fieldPaths: string[];
  valueHash: string;
  usage: 'target' | 'explicit_reference' | 'context';
};
```

- 由服务端构造提示词时记录实际读取的实体，不让模型自报作为唯一依据。
- 目标正文/结构改变可导致候选冲突；纯上下文变化用于复核和可解释的过期判断。
- 修改指纹前同时核对提示词实际范围。若提示词仍包含全部角色，就如实记录；要减少无关失效，应先缩小实际输入范围。
- 整场逐阶段生成继续保存前序候选上下文；依赖前序候选时记录候选 ID/内容哈希，不能假装读取的是当时尚不存在的正式事实 ID。
- 首版不用让每条聊天都生成事实标注。缺乏记录级证据时，最多提示有关阶段“可能受影响”。
- 现有 `needs_review` 保留兼容，逐步改为从未处理影响项汇总；避免旧逻辑继续无条件把所有后续阶段标脏。

### 3.4 保存与持久化边界

采用以下实现顺序：

1. 草稿预览以当前采用内容与待提交草稿比较，仅计算，不写任务、不写持久待处理项。
2. 保存新内容版本时，使用服务端实际旧版本与新版本计算影响；复用外层事务写入修订和复核项。
3. 图像配置变更采用对应配置版本对比；媒体采用和回放保存分别触发自身相关分析。
4. 候选采用通过同一内容提交入口产生新的影响。刚采用的内容不能因为使用其旧目标做比较而被自己标成过期。
5. 检查点恢复后重新计算当前状态，重新校验历史确认决定；不直接把新版本的确认记录搬回旧检查点。

建议新增一张 `activity_review_items` 表，兼作轻量待处理清单，避免再造返工任务系统：

| 字段组 | 建议字段与用途 |
| --- | --- |
| 归属 | `id`, `activity_id`, `target_kind`, `target_id` |
| 本次变化 | `change_key`, `severity`, `reasons_json`, `source_snapshot_json` |
| 版本依据 | `content_revision_id`, `image_config_revision_id`, `target_value_hash`, `source_value_hash` |
| 处理决定 | `decision`：pending / keep / rework / resolved / superseded；`decision_note` 可选 |
| 执行关联 | `requested_action`、`job_id` / `batch_id` / `attempt_id` 等引用，可用 JSON 存储 |
| 时间 | `created_at`, `updated_at`, `resolved_at` |

`change_key` 由目标、来源变化、对应结果等稳定信息构造，并加活动范围唯一约束；轮询、重复请求和刷新不能生成重复项。一个目标的新变化替代旧待处理项时记录 `superseded`，不要删除历史。图像字段改变后又改回原值，重新计算实际结果来源匹配状态，避免无休止叠加提醒。

决定请求提交 `changeKey`、目标/来源哈希和当前版本；服务端验证后更新。旧页面确认不能悄悄消除新变化。

### 3.5 待处理清单与生成衔接

列表按文本、图片、回放分组，不新增独立全局任务页面。可在活动详情中显示“待处理 5 项”，点击展开侧栏。

- 文本：优先将已有消息/动态交给 `rewrite-records`；需要整段重写时明确选择阶段替换。
- 图片：加入返工清单后显示“等待手动开始”；服务未就绪时说明原因，仍可编辑源头和上传替代素材。
- 回放：一个活动合并为一项“回放需更新”，列出变化原因，不每改一条消息就创建一个新任务。
- 开始处理前保存必要版本，重新校验目标、锁定、来源和在途状态。已删除、已锁定、已有任务的项给出逐项原因。
- 文本任务和图片批次继续使用现有执行器。清单只是用户选择与业务任务的关联层。
- 选择多项生成时，先做一次预览；同一目标只提交一次，并把稳定幂等键和创建结果写回清单。
- 用户离开页面后，可在全局任务中心看到已开始任务；未开始清单不能计入“正在运行”。
- 服务重新上线不自动执行历史待处理图片。用户再次点击开始时重新冻结最新选择的配置，旧配置仅作为历史参考。
- 执行失败保留清单、旧结果和任务链接；执行成功但未采用显示“候选待采用”。

## 4. 模块 B：候选对比与局部采用

### 4.1 第一版采用单位

这是控制代码量和引用一致性的关键：

| 候选类型 | 对比方式 | 第一版允许的采用单位 |
| --- | --- | --- |
| `whole-text` 的多个阶段候选 | 按阶段对比 | 选择一个或多个完整阶段，复用批量采用 |
| 单阶段替换候选 | 当前阶段与候选阶段对比 | 完整阶段；若只想改几句，转入局部重写 |
| `rewrite-records` | 每条消息/动态显示修改前后 | 单条或多条文本修改，保持原记录 ID |
| invite / wish / moment / shot 等追加候选 | 新增内容预览 | 首版以现有完整追加候选为单位 |
| 图片候选 | 当前采用图与候选并排 | 每槽位选择一张，复用已有批量采用 |

不要直接从整阶段原始 JSON 中截取几条消息就写入正式内容。阶段候选通常带有临时 ID、事实、评论和媒体槽位，任意拆选会产生孤立引用。以后确有需求再做通用依赖组合采用。

### 4.2 页面表现

优先改造 `generation-modal.tsx`，必要时拆出 `candidate-review-panel.tsx` 和纯展示组件，保留当前生成入口。

宽屏：左侧当前采用版本，右侧候选；顶部显示角色、阶段、候选生成时间及“依据是否有变化”。窄屏：同一条记录上下排列，或切换当前/候选，不能横向挤压文字。

具体要求：

- 使用聊天气泡、朋友圈卡片和人物名称；不把 JSON 当默认预览。
- 逐条标出新增/修改/删除。文本比较可先按句子或整段，不必开发复杂字符级 diff 引擎。
- 默认不替用户确认采用；允许“选择所有可采用项”“清空”。
- 显示“选中 3 条，将修改 3 条，其他记录保留”。
- 锁定项显示锁图标与原因，不能勾选。
- “仅看变化”开关；完整上下文可展开，辅助判断对话是否连贯。
- 阶段整段替换必须显示删除/替换的记录和媒体影响摘要，不能只展示新增句子。
- 发现候选过期时保留预览，明确阻止相关采用并提供重新生成入口。
- 历史候选可打开比较；提供“收起此候选”或“不采用”状态，不能用 adopted=true 假装它被采用。
- 用户调整勾选后，失败或切换到来源编辑再返回应尽量保留选择；至少当前弹窗不丢，刷新可根据候选 ID 恢复部分采用情况。

### 4.3 部分采用的数据与事务

保留候选原始 payload，不删除已采用条目、不修改原生成结果。新增服务端生成的采用操作清单：

```ts
type CandidateApplicationUnit = {
  id: string;                    // 稳定、候选内唯一，由服务端生成
  candidateId: string;
  kind: 'replace_stage' | 'rewrite_message' | 'rewrite_post' | 'append_candidate';
  targetId: string;
  beforeHash: string;
  dependencyHashes: Record<string, string>;
  applied: boolean;
};
```

建议新增 `activity_candidate_applications` 表，记录 `activity_id, candidate_id, unit_id, request_key, content_revision_id, applied_entity_ids_json, created_at`，对 `(activity_id, candidate_id, unit_id)` 唯一。已有 `adopted` 保持兼容，仅所有可采用单元完成时设为 true；响应额外派生 none / partial / full。候选收起可增加轻量独立字段，不混用采用记录。

请求示意：

```json
{
  "candidateId": "candidate_example",
  "unitIds": ["rewrite_message_msg_1", "rewrite_message_msg_3"],
  "expectedHeadVersion": 12,
  "expectedDraftVersion": 18,
  "idempotencyKey": "application_example"
}
```

服务端流程：

1. 读取候选、当前版本和采用记录。前端仅传单元 ID，不接受前端自由构造写入正文。
2. 检查所有选择属于当前候选、活动及合法作用范围，验证当前目标和输入依赖。
3. 先校验全部锁定和引用，再构造新文档。任一选中项冲突时整次采用失败，不半成功。
4. 已采用单元重复提交返回既有结果，不重复追加；尚未采用单元独立处理。
5. 在同一事务写入新修订、采用记录、候选采用状态及影响项。
6. 成功后刷新详情、生产概览、候选、媒体与回放摘要；刷新失败不能向用户谎报业务采用失败并重新提交。

第一次采用部分记录后，第二次采用剩余记录应可继续。不能仅因为整个候选仍指向旧 `draftVersion` 就全部拒绝，也不能无条件跳过版本保护：请求仍使用最新 CAS；未采用目标按各自 beforeHash 和真实依赖检查，之前由本候选造成的已采用变化有明确记录。

阶段之间存在前序候选依赖时，在服务端校验依赖是否已经采用或包含在本次完整阶段选择里。不能跳过必要前序阶段后假装事实已存在。需要补选时说明具体阶段，由用户决定。

旧候选没有精确单元/依赖元数据时，显示“旧候选，需按原范围采用”，继续走原兼容路径，不伪造安全拆选能力。

### 4.4 局部重写严格边界

首版逐条采用只修改消息/动态正文：保留记录 ID、说话人/作者、会话、阶段、顺序、媒体槽位、评论和点赞。模型返回范围外的记录、重复 ID 或结构字段不直接写入。

更换说话人、移动会话、删除记录、新增事实等仍通过现有编辑或整阶段候选完成，必须触发对应影响分析。后续如开放更多字段，再按字段增加明确的操作单元。

## 5. 模块 C：模板职责映射

### 5.1 模板保存

扩展已有“另存为模板”，在弹窗里展示：

- 模板名称、类型、主题、地点、活动规则。
- 阶段列表和说明，至少两个阶段，可增删。
- 职责列表：如寿星、组织者、来宾、摄影者，可改名、增删。
- 每个职责是否必选、是否允许多人；默认数量限制保持简单。
- 每个阶段和关键事件使用哪些职责。

默认从当前活动参与者生成职责建议，但保存前让用户看到映射。角色姓名、人设、头像、聊天正文、媒体结果、任务 ID 都不自动进入结构模板。

### 5.2 普通说明中的角色引用

采用简单、可视化插入的占位符，例如 `{{role.birthday}}`、`{{role.organizer}}`、`{{role.guests}}`。编辑时可点“插入职责”，不要求用户记语法。

示例：

```text
{{role.organizer}} 提前准备场地，{{role.guests}} 到齐后迎接 {{role.birthday}}。
```

- 采用模板时替换为当前映射角色名称；多人使用自然的名称列表。
- 只解析明确占位符，不对整份文字做不加区分的人名替换。
- 保存旧活动为模板时可提示说明中出现了原角色姓名，提供逐处替换建议；不默默替换引用、别名或普通词语。
- 模板仍然写死旧人名的地方，预览中提示检查。首版无需用 AI 自动识别人名。
- 不执行模板表达式；这里只是固定格式的文本替换。

### 5.3 创建活动与企划两条入口共同使用

在“我的模板”选中后增加职责映射区域，复用同一前端组件和服务端转换逻辑：

```text
模板：惊喜生日会 · 第 3 版
寿星（必选、单人）    [选择当前角色]
组织者（必选、单人）  [选择当前角色]
来宾（可选、多人）    [选择多个角色]

阶段预览：
准备惊喜：……
寿星到场：……
```

- 角色来自当前人设选择列表和本场临时角色；继续使用已有角色搜索/筛选组件。
- 自动匹配只能作为建议。寿星标记可预选到寿星职责，映射结果必须可见可修改。
- 同一角色可以兼任不同职责；同一职责内去重。
- 必选职责缺人时不能完成实例化；可选职责可为空。
- 可选职责为空时，明确省略该参与者；若导致阶段无参与者，提示补人或手动调整，不悄悄变成全体角色参与。
- 换模板只更新模板相关字段，沿用现有覆盖预览，保留用户的角色选择。
- 人设选择变动后重新验证映射；被移除角色不能残留在映射和阶段引用中。

### 5.4 契约与快照

模板 payload 建议增加 `schemaVersion: 2`，使用明确类型：

```ts
type TemplateRoleSlot = {
  id: string;
  label: string;
  required: boolean;
  multiple: boolean;
};
type TemplateActorMappings = Record<string, string[]>;
```

- 旧 `Record<string, string>` 输入在服务端归一化为数组，保留旧接口兼容。
- 表单角色使用 characterId/本场临时角色键，服务端冻结角色后转换为 actorId；不要把两种 ID 混用。
- 模板保留职责引用，实例化后的活动保留真实 actorId。
- `templateSnapshot` 保存 presetId、版本、payload 和本次映射；模板更新/删除不改变旧活动或旧企划会话。
- 修改已创建活动不反向更新模板，更新模板是独立明确操作。
- 新建的阶段、关键事件等生成新 ID，映射不能携带上一场媒体绑定、候选或执行任务。
- 创建页和 `planning.ts` 使用同一实例化规则。不要再让手动创建和 AI 企划各写一套角色映射算法。
- 无模板的手动活动、内置旧模板和旧会话仍可继续使用。

## 6. 模块 D：常用创作配置

### 6.1 复用已有预设，增加一个组合入口

已有 `activity_template`、`production_preset`、`playback_preset` 继续有效。新增“创作配置”只是常用默认值的组合，可在原预设表中增加 `creation_profile` 类型，无需新建预设数据库或复杂配置中心。

可保存的设置：

| 分组 | 内容 |
| --- | --- |
| 文本 | 默认生成范围选择方式、偏好说明，例如简洁/热闹；不固定某场活动的 recordId/stageId |
| 图片 | 每镜头候选数、全局风格/负向提示词、已有支持的默认参数 |
| 回放 | 现有支持的编排模式、是否展开媒体、已有阅读速度/停留时间等参数 |
| 导出 | 默认阅读包/工作工程/HyperFrames 工程，以及现有支持的画面尺寸、帧率等设置 |

只开放实际执行链路支持的字段。先检查现有回放/导出契约，不要显示没有后端处理的阅读速度或渲染参数。配置不保存凭据、真实活动 ID、种子结果、采用资产及节点绝对路径。

### 6.2 应用优先级

```text
系统默认值 < 创作配置快照 < 当前活动显式设置 < 本次操作显式覆盖
```

- 空值与“用户明确清空”需要区分，避免空字符串被错误补回默认文案。
- 配置只在用户选择套用时填充，不随页面轮询重新覆盖。
- 套用现有活动时显示将改变的参数和影响，允许取消；不改现有采用图片和文本。
- 从已有生产/回放预设组合时，保存已解析的值和来源版本，不仅存可变的预设 ID。
- 当前活动冻结配置快照；后续修改全局预设不影响已排队任务或历史活动。
- “设为默认”沿用项目现有设置存储，可只新增一个默认 profile ID；删除默认配置时清空引用并回退系统默认。
- 不因用户选择图片偏好就探测或连接 ComfyUI。到实际准备生成时再做用途与参数校验。
- 若更换后端工作流后参数不兼容，准备页面明确列出不兼容项，不能静默改成另一种生成方式。

### 6.3 页面位置

- 新建活动顶部提供紧凑的“创作配置：默认 / 我的配置”。
- 原“模板与预设”弹窗增加创作配置管理，不另开庞大的设置页面。
- 活动设置里显示当前使用的配置快照，可查看、另存或明确重新套用。
- 生成和回放页面继续允许本次覆盖，清楚显示实际生效值。

## 7. 前端信息架构与状态

保留活动现有四个 Tab：设置、记录、媒体、回放。

| 位置 | 改造内容 |
| --- | --- |
| 活动顶部生产概览 | 增加“待复核/待处理”计数和入口；按真实采用与复核状态建议下一步 |
| 设置 Tab | 角色/阶段变更后显示影响摘要；模板映射和配置快照入口 |
| 记录 Tab | 原多选局部改写入口接入候选对比；定位受影响记录 |
| 媒体 Tab | 待返工筛选、当前图与旧来源标识；待处理清单可转现有批次 |
| 回放 Tab | 显示旧回放关联版本及落后原因；手动更新 |
| 活动侧栏 | 按文本、图片、回放查看复核/待处理项，批量选择和处理 |
| 全局任务抽屉 | 已执行任务展示对应活动与清单入口，不加入无执行动作的“假任务” |

### 7.1 必须覆盖的界面状态

- 无变化：显示“没有发现需要复核的内容”，不显示空错误框。
- 只有可能影响：允许直接保存并稍后查看，不强迫重生成。
- 全部锁定：允许查看/确认保留，生成按钮禁用并给出原因。
- 已有执行任务：保留任务链接，不重复发起。
- ComfyUI 未就绪：明确“已加入待处理，尚未生成”，可继续文本与模板工作。
- 候选过期：仍可比较，采用按钮解释不可用的原因。
- 部分候选已采用：显示数量与具体记录，继续选择剩余项。
- 保存冲突：展示当前状态并允许重新载入/比较，不静默覆盖。
- 资源或实体被删除：定位具体引用，提供现有修复/替换入口。
- 移动窄屏：侧栏转抽屉、前后对比纵向排列，主要按钮保持可见。

### 7.2 来源跳转

统一使用活动内部实体定位参数，例如 `tab=records&stageId=...&recordId=...`、`tab=media&slotId=...`、`tab=settings&actorId=...`；这是拟新增约定，须贯通页面实际读取逻辑，不能只构造 URL。

跳转后切换到正确 Tab、滚动并短暂高亮目标。不存在的目标提示已删除。默认修改本场角色快照，不直接跳进全局人设库修改公共角色。

## 8. 服务接口与数据边界

以下是建议接口，实施时优先扩展现有同职责接口，避免重复端点。新路径均为规划，不代表当前已经存在。

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/admin/activities/:id/change-impact/preview` | 按当前版本预览待提交内容/配置变化，不写持久任务 |
| `GET /api/v1/admin/activities/:id/review-items` | 读取该活动复核/待处理项，可按目标、决定、严重程度筛选 |
| `POST /api/v1/admin/activities/:id/review-items/decide` | 对所选项确认保留、稍后处理、加入返工；验证变化键和版本 |
| `POST /api/v1/admin/activities/:id/review-items/start` | 将已选待处理项转换为现有业务任务，返回实际任务 ID 和未启动原因 |
| `GET /api/v1/admin/activities/:id/candidates/:candidateId/comparison` | 返回当前/候选对比、采用单元、已采用情况和冲突原因 |
| `POST /api/v1/admin/activities/:id/candidates/:candidateId/apply-selection` | 原子采用所选合法单元，生成内容修订 |
| 已有模板实例化接口 | 扩展多人职责、映射预览和快照 |
| 已有预设 CRUD | 增加带类型校验的创作配置 payload、默认配置引用 |

前端 `api.ts` 仍走 `/api/admin/...` 代理，服务端用 `/api/v1/admin/...`；确认实际代理路由可到达。

### 8.1 最小数据库变更

原则上新增两张业务表即可：`activity_review_items`、`activity_candidate_applications`。其他信息优先增加到既有候选元数据、生成输入快照、模板/配置 payload 和活动快照。

不要先建立通用依赖表、返工批次表、任务调度表、审批流表再连接页面。只有确认 JSON 查询或关联需求无法满足时再调整，并在实施记录解释原因。

### 8.2 版本兼容与导入导出

- 新字段尽量可选，旧文档按“来源未知、无额外确认记录”读取。
- 工作工程导出保留候选采用状态和用户复核决定所需信息；导入时重映射活动、实体、候选和结果 ID。
- 不能安全迁移的运行中任务引用不恢复执行，作为历史来源显示；不得导入后自动生成。
- 复核决定的哈希/键需要在 ID 重映射后重算或验证；无法证明仍匹配时保留历史说明并回到待复核，不能错误消除提醒。
- 阅读包/HyperFrames 工程只使用采用内容和采用媒体；待返工候选不自动进入最终结果。
- “确认保留旧图”的语义可保留在工作工程中，不改写图像来源，不在视频画面中暴露内部哈希和任务 ID。
- 便携备份复用整库机制，自然覆盖新增表；不增加另一种整机备份格式。

## 10. 开发顺序与每步交付

### R0：核对基线与建立样例

交付：简短基线记录及一份临时样例活动，至少三阶段、三角色、聊天、朋友圈、图片槽位。可使用已有本地素材，不连接真实 ComfyUI。

核对重点：草稿提交链路、批量采用事务、来源指纹、模板快照、回放指针和现有预设字段。先确认已有能力，不重写上一阶段已经完成的批次和任务中心。

### R1：影响计算与持久复核

交付：规则分析器、复核项存储、影响侧栏、确认保留/稍后处理、生产概览数量。

完成条件：修改角色服装只提示有关图片；修改普通聊天措辞不会默认标记全场图片；保存并确认保留后刷新不重复提醒；来源再次修改会重新提示。

这是第一段可独立使用的成果，完成后即可交付，不必等待全部模块。

### R2：候选对比与选择采用

交付：阶段对比、局部文本对比、采用单元及事务记录，锁定/过期说明。

完成条件：三条局部改写只采用两条，第三条及媒体引用保持不变；之后能采用剩余条目；重复请求不重复写入；任一选中项冲突时不留下半次采用。

### R3：返工清单与现有生成流程衔接

交付：加入返工、所选文本生成、图片待处理状态、任务链接、采用后更新复核状态、回放更新提醒。

完成条件：ComfyUI 未配置或不可用时，清单可保存并跨刷新恢复，文本工作不被阻断；使用模拟生图返回验证任务关联与采用衔接，但不宣称真实 GPU 出图已验收。

### R4：模板职责映射

交付：模板职责编辑、占位符、创建/企划共用映射、角色变化后的校验、版本和映射快照。

完成条件：同一个生日模板用两组不同角色创建活动，阶段参与者和占位符文本正确；必选职责缺人有提示；不带上一场记录或任务；修改模板不影响已创建活动。

### R5：创作配置与交付收尾

交付：类型明确的创作配置、套用预览、默认设置、冻结规则、工作工程导入导出兼容、实施记录。

## 11. 必要验证

保持个人项目尺度，优先扩展现有测试，不为每个按钮或文案新增测试。

| 关键回归 | 必须证明 |
| --- | --- |
| 影响准确性 | 无变化不产生项；无关角色/字段不扩散；旧来源不假装精确；显式缺失引用可定位 |
| 确认持久化 | 同次变化确认后刷新不重复；再次变化重新出现；旧请求不能确认新变化 |
| 部分采用 | ID/媒体引用保留、只写所选正文、重复无新增、二次采用剩余项可行、冲突事务回滚 |
| 锁定和过期 | 直接 API 请求也不能绕过；加入清单后再锁定的对象不能被派发替换 |
| 待处理与服务缺失 | 无 ComfyUI 时不实际提交、不无限重试；清单与真正执行状态分开 |
| 模板映射 | 单人/多人、缺少必选、移除角色、占位符、旧格式兼容及新实体 ID |
| 配置快照 | 默认值与本次覆盖正确，修改全局预设不改变活动/已排队任务 |
| 导入与回放 | 重映射后引用有效；旧回放显示需更新；仅采用版本进入阅读/视频工程 |

主要检查命令按改动范围使用：

```bash
npm run typecheck
npm run test --workspace @sthstart/service
npm run test:contracts
npm run test:portal
npm run build:portal
git diff --check
```

只需对改动文件做必要 lint。前端实际打开窄屏/宽屏各看一次：影响列表、局部对比、职责映射是否可操作、文案是否可理解。不要把“构建通过”当成“页面操作已经验收”。

真实 LLM、ComfyUI 出图、最终 HyperFrames 音画渲染分别记录已验证/未验证。本轮 ComfyUI 暂不可用属于已知边界，不要求用户升级后才能继续实现其他内容。
