# 开发日志维护规范

本规范适用于参与 SthStart 开发的开发者和 Agent。开发日志的目标是保留可接手的上下文，而不是复制 Git diff。

## 何时更新

- 跨模块功能、架构调整、数据库迁移或用户可见能力：新增一份阶段日志。
- 小型修复：可追加到当日日志；如果没有当日日志则新建。
- 只修改注释或排版且不影响行为：通常不需要新日志。
- 发现但不处理的问题：加入 `BACKLOG.md`，并在本轮日志中说明。
- 决定延后的测试或真实环境验证：加入 `DEFERRED_VALIDATION.md`。

## 每轮开发结束时

1. 使用 `templates/DEVELOPMENT_LOG_TEMPLATE.md` 创建 `logs/YYYY-MM-DD-short-topic.md`。
2. 记录目标、完成内容、关键决策、已知限制和实际执行过的验证。
3. 更新 `CURRENT_STATUS.md` 中受影响模块的状态。
4. 更新 `BACKLOG.md`：新增、关闭或调整相关编号。
5. 如有延后验收，同步更新 `DEFERRED_VALIDATION.md`。
6. 检查所有相对链接有效，且文档中没有密钥、Token、个人路径或敏感请求内容。

## 记录原则

- 使用事实描述，不写“应该没问题”“基本完成”一类无法核对的结论。
- 明确区分“已实现”“已测试”“已在真实环境验证”。
- 只列出有助于接手和决策的文件、接口或迁移，不逐行复述改动。
- 日志创建后原则上不重写历史；事实错误可以修正，并在文末注明修正日期和原因。
- `CURRENT_STATUS.md` 是实时视图，可以随开发变化更新。
- Backlog 编号不得复用；关闭事项的结果必须能在某份日志中找到。
- 测试失败要记录失败范围和原因，不能通过删除失败结果将模块标为已完成。

## 提交建议

代码、测试和对应开发日志应在同一提交或同一合并请求中更新。提交信息不需要重复日志全文，但日志应写明关联的 Backlog 编号；提交完成后可补充 commit 短哈希。
