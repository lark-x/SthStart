## 4. 已证实 vs 未证实（严格区分）

**已证实**

1. 业务库确实损坏，且可稳定复现（宿主只读连接）。
2. 损坏范围是 2 个 btree、100 个页面，不是全库不可读——迁移版本与表清单仍可读出。
3. 叙事库健康。
4. 容器与宿主使用**相同**的 SQLite 版本（3.51.3）。
5. 容器以 rw 挂载同一 data 目录，且容器自报 healthy。

**未证实（不得当作结论）**

1. **损坏原因未知。** 不能从「迁移到 49」推导出「迁移导致损坏」——本阶段没有任何证据指向迁移。
2. **容器与宿主结果差异的原因未知。** 已排除 SQLite 版本差异（两者都是 3.51.3）。剩余差异是 Node 主版本（v22 vs v24，`node:sqlite` 封装可能不同）与运行环境，均**未验证**。
3. **损坏发生在主库文件还是 WAL 中未知。** 本阶段未把两者分开测试（分开测试需要复制文件，属于取证操作，见 §6）。
4. **是否仍在恶化未知。** 只有一次采样。
5. 上一轮审查记录的「容器报 `file is not a database`」本次**未能复现**——容器这次报的是 `database disk image is malformed`。

## 6. 对真实数据操作的结论与需用户确认的事项

**本阶段不做任何修复。** 按计划 §3.3／§4.3：

1. **禁止**启动会自动迁移真实库的本地服务。
2. **禁止**向真实活动写入测试任务、修改提示词策略、注册工作流、调用真实模型。
3. **禁止**用部署／重启来「试试看数据库是否恢复」。
4. **禁止**在原文件上执行 `VACUUM`／`REINDEX`／恢复／`.recover`。

**需要用户确认后才能做（本轮均未做）**

- **保留现场取证**：需先说明要暂停的写入者（容器 `sthstart`、以及任何宿主 node 进程）与影响，取得确认后停止写入，再把 `.db` 与现有 `-wal/-shm` 一起复制到新的取证目录并记录哈希。取证副本**不是**已验证可恢复的业务备份。
- **分析与恢复**：应在副本中进行；验证恢复结果与新增数据损失范围后，再请求批准切换。
- **停止容器**：会中断 `127.0.0.1:3099` 与 `9320` 上的服务，属用户可见影响，需确认。

## 7. 本轮诊断的一个副作用（如实记录）

用 `DatabaseSync(readOnly)` 打开 WAL 数据库时，SQLite 仍需访问 `-shm`。诊断前后 `sthstart.db-shm` 的 mtime 由 `10:45:05Z` 变为 `11:27Z`。**本次诊断修改了 SHM 的时间戳**，未修改 `.db` 与 `-wal`（两者 mtime 未变）。如实记录，避免后续误判。
